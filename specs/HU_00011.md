# HU_00011 — Scene Management and Scene Selection

## 1. User Story

**As an** artist using the 2D animation editor,  
**I want** to create, select, rename, and delete scenes within a project,  
**So that** I can organize different animations and drawing sequences within the same project.

## 2. Objective

Replace the current single-scene workflow with a scene management system that supports multiple independent scenes within a project.

Users must be able to select existing scenes, create new scenes, rename scenes, and delete scenes through a scene selector located in the editor's top toolbar, immediately before the **Save** button in the upper-right corner.

Each scene must maintain its own animation content, including frames, layers, and associated drawing data, according to the existing project architecture.

The implementation must reuse the project's existing scene model, project manifest, persistence mechanisms, and editor services wherever possible.

## 3. Scope

### 3.1. In Scope

- Support multiple scenes within one project.
- Add a scene selector dropdown to the top toolbar.
- Display the active scene's name in the selector.
- Allow users to switch between existing scenes.
- Allow users to create new scenes.
- Allow users to rename existing scenes.
- Allow users to delete scenes.
- Preserve scene-specific frames, layers, and drawing content.
- Persist scene metadata and scene content.
- Integrate scene switching with save, undo/redo, playback, and existing editor tools.
- Provide confirmation and validation for destructive or invalid operations.
- Preserve compatibility with existing single-scene projects.

### 3.2. Out of Scope

- Scene transitions and transition effects.
- Timeline sequencing across multiple scenes.
- Playback of an entire project by automatically moving between scenes.
- Reusing or linking the same frame or layer across multiple scenes.
- Scene templates or presets.
- Scene folders, tags, or nested scene hierarchies.
- Importing and exporting individual scenes as separate project files.
- AI-assisted scene generation.
- Collaborative editing of scenes.

These capabilities may be introduced in future user stories.

## 4. Scene Selector UI

### 4.1. Location

Add a scene selector dropdown to the editor's top toolbar.

The selector must appear immediately before the **Save** button in the upper-right corner.

The expected order is:

`[Scene Selector ▼] [Save]`

The selector must follow the existing toolbar's visual style, spacing, sizing, and theme.

It must not overlap or displace existing toolbar controls in a way that makes them inaccessible at supported window sizes.

### 4.2. Selector Appearance

The selector must display the name of the currently active scene.

When clicked, it must open a dropdown containing:

1. All existing scenes in the current project.
2. An action to create a new scene.
3. An action to rename the active scene.
4. An action to delete the active scene.

Scene management actions must be visually distinguishable from scene selection entries.

The active scene must have a visible selected state.

The dropdown must close after a successful scene selection or management operation, except when a dialog or inline form must remain open to complete the action.

If the project contains no available scenes, the selector must provide an appropriate empty state and a clear action to create the first scene.

### 4.3. Scene Names

Each scene must have a user-visible name.

Scene names must:

- Be required.
- Be trimmed of leading and trailing whitespace.
- Reject empty or whitespace-only values.
- Have a reasonable maximum length, recommended at 100 characters.
- Reject duplicate names within the same project using case-insensitive comparison.
- Preserve the user's intended capitalization.
- Support Unicode characters.
- Avoid changing the scene's stable identifier when renamed.

Names must be validated before the operation is committed.

Validation errors must be displayed clearly without losing the user's input.

## 5. Scene Data Model

### 5.1. Scene Identity

Each scene must have a stable, unique identifier independent of its display name.

Renaming a scene must not change its identifier or invalidate references to its frames, layers, drawings, or other scene-owned resources.

Scene identifiers must remain stable across project saves, application restarts, and scene renames.

### 5.2. Scene Metadata

The scene metadata should contain at least:

- `id`: stable unique identifier.
- `name`: user-visible scene name.
- `createdAt`: scene creation timestamp.
- `updatedAt`: timestamp of the most recent scene metadata or content update, according to the existing project conventions.

Additional metadata may be included when required by the current project architecture.

The existing project manifest or scene registry must be reused if one already exists. Do not introduce duplicate scene registries or competing sources of truth.

### 5.3. Scene-Owned Content

Each scene must own or reference its own:

- Frames.
- Layers within those frames.
- Drawing and curve content.
- Scene-specific animation settings, if already supported by the editor.
- Other scene-specific resources defined by the existing architecture.

Scene-owned content must remain isolated from other scenes.

Changing the active scene must never merge, overwrite, or move drawing content between scenes.

### 5.4. Active Scene State

The editor must maintain a reference to the currently active scene using its stable identifier.

The active scene identifier must be validated whenever a project is opened or its scene collection changes.

The implementation must not rely exclusively on a scene's display name to identify the active scene.

If the active scene is renamed, it must remain active.

If the active scene is deleted, the editor must select another valid scene according to the rules defined in Section 8.

## 6. Creating a Scene

### 6.1. Creation Workflow

When the user selects **Create New Scene**:

1. Display a dialog or inline form requesting the new scene name.
2. Validate the name according to Section 4.3.
3. Create a new scene with a unique identifier.
4. Initialize the scene using the existing scene initialization mechanism.
5. Create the minimum required empty frame and layer structure according to the current editor conventions.
6. Persist the new scene and its metadata.
7. Set the new scene as the active scene.
8. Update the scene selector and editor workspace.

The new scene must start empty.

It must not inherit the frames, layers, drawings, curves, or other animation content of the previously active scene unless the existing architecture explicitly defines certain resources as shared project resources.

The user must be able to cancel creation without modifying the project.

### 6.2. Initial Scene Settings

The new scene must use the existing default settings for a new scene.

If the project defines canvas dimensions globally, the new scene must use the project's canvas dimensions.

If the editor already supports scene-specific animation settings, the new scene must initialize those settings using the established defaults.

Do not introduce scene-specific canvas dimensions or new animation settings as part of this user story unless they are already supported by the existing architecture.

### 6.3. Persistence

A successfully created scene must remain available after saving and reopening the project.

Scene creation must be handled as a logical operation. If persistence fails, the application must report the failure and avoid leaving the UI in a state that claims a scene was successfully created when it was not.

## 7. Selecting and Switching Scenes

### 7.1. Selection Workflow

When the user selects an existing scene from the dropdown:

1. Identify the target scene by its stable identifier.
2. Resolve any pending changes to the currently active scene.
3. Persist pending changes according to the editor's existing save behavior.
4. Deactivate the current scene's editing context.
5. Load or activate the target scene's frames, layers, and drawing content.
6. Update the active scene identifier.
7. Refresh the canvas, timeline, layer panel, Tool Options dependencies, and other scene-dependent UI.
8. Update the scene selector to display the target scene's name.

Scene switching must not modify scene content merely because the user navigated between scenes.

### 7.2. Unsaved Changes

If the active scene or project has unsaved changes, the editor must follow the existing unsaved-changes policy.

If no suitable policy exists, the user must be prompted to choose one of the following:

- **Save and Switch:** save pending changes and activate the target scene.
- **Discard and Switch:** discard pending changes according to the application's established semantics, then activate the target scene.
- **Cancel:** remain in the current scene without losing changes.

If the save operation fails, the editor must remain in a safe state and must not silently discard changes.

The application must not show an unnecessary confirmation dialog when there are no unsaved changes.

### 7.3. Scene State Restoration

Switching away from a scene and returning to it must preserve its content.

Where supported by the existing architecture, the editor should restore scene-specific editing state such as:

- Selected frame.
- Current frame playback position.
- Selected layer.
- Canvas zoom and pan position.
- Other non-destructive editing context.

Restoring editing state must not override persisted artwork or alter the actual scene content.

If a previously selected frame or layer no longer exists, the editor must select a valid default.

### 7.4. Playback Behavior

Scene switching must stop playback of the previously active scene before activating the target scene.

The new scene must not unexpectedly begin playing because the previous scene was playing.

The active scene's frame navigation and playback must remain independent of other scenes.

## 8. Renaming and Deleting Scenes

### 8.1. Renaming a Scene

When the user selects **Rename Scene**:

1. Display the current scene name in an editable dialog or inline form.
2. Allow the user to enter a new name.
3. Validate the new name.
4. Update the scene metadata without changing the scene identifier.
5. Persist the change.
6. Refresh the dropdown and any other UI that displays the scene name.

Renaming must not modify frames, layers, strokes, curves, assets, or scene content.

Canceling the rename must leave the existing name unchanged.

Renaming to the current name, ignoring leading/trailing whitespace and case, may be treated as a no-op.

### 8.2. Deleting a Scene

When the user selects **Delete Scene**:

1. Display a confirmation dialog identifying the scene by name.
2. Explain that the scene's animation content will be removed from the project.
3. Allow the user to cancel the operation.
4. If confirmed, remove the scene and its scene-owned content according to the existing project data model.
5. Persist the change.
6. Update the active scene and editor workspace.

Deleting a scene must not delete unrelated project assets or content belonging to other scenes.

If scene-owned resources are stored in separate files or directories, their cleanup must follow the project's resource ownership and safe deletion rules.

### 8.3. Preventing Invalid Project States

The editor must not allow the user to delete the last remaining scene.

When only one scene exists, the Delete Scene action must be disabled or unavailable, and the UI should communicate that at least one scene must remain in the project.

The user must create another scene before deleting the current one if they want to replace it.

### 8.4. Deleting the Active Scene

If the active scene is deleted and other scenes exist, the editor must activate a valid remaining scene.

The preferred fallback is the next scene in the existing selector order. If there is no next scene, activate the previous scene.

The deletion workflow must ensure that the new active scene is fully initialized before the deleted scene's editing context is discarded.

If deletion or persistence fails, the application must retain a recoverable state and must not leave the editor pointing to a nonexistent scene.

## 9. Scene Ordering

Scenes must have a deterministic order in the dropdown.

For the initial implementation, use the order defined by the existing scene collection or registry.

If the current architecture has no defined order, preserve creation order.

Reordering scenes through drag-and-drop is out of scope.

Creating, renaming, selecting, or deleting a scene must not unpredictably reorder the remaining scenes.

## 10. Save and Project Persistence

### 10.1. Save Integration

The existing **Save** button must save the active scene and any other pending project metadata required by the established persistence architecture.

Scene creation, renaming, and deletion must be persisted using the existing project persistence mechanisms.

The editor must maintain a clear distinction between:

- Active scene state.
- Scene metadata.
- Scene content.
- Project-level metadata.
- Application-level preferences.

The implementation must not store scene content in application preferences or treat scene metadata as transient UI state.

### 10.2. Atomicity and Failure Handling

Scene management operations must avoid partially committed states.

Where supported by the current storage architecture, use atomic metadata updates or transactional persistence.

If a scene operation fails:

- Display a clear error message.
- Preserve the last known valid scene collection.
- Keep the active scene reference valid.
- Avoid silently deleting scene data.
- Allow the user to retry where appropriate.

### 10.3. Project Reopening

When opening a project:

1. Load the scene registry or existing scene collection.
2. Validate scene identifiers and metadata.
3. Resolve the active scene using the existing project-opening policy.
4. If the project has a valid saved active scene identifier, restore it when appropriate.
5. Otherwise, select the first valid scene according to the established scene order.
6. Load the selected scene's content into the editor.

A missing or invalid active scene reference must not prevent an otherwise valid project from opening.

## 11. Backward Compatibility and Migration

Existing projects may have been created when only one scene was supported.

The implementation must inspect the current project schema before deciding whether migration is necessary.

If existing projects already contain a scene registry or scene directory structure, reuse that structure and avoid redundant migration.

If older projects store their content directly at the project level, introduce a migration that represents the existing content as a scene without losing data.

Migration requirements:

- Preserve the original drawing content.
- Preserve frames, layers, and scene-owned metadata.
- Generate a stable scene identifier if one does not already exist.
- Assign a valid default scene name, such as `Scene 1`, only when no suitable name exists.
- Update project metadata and schema version according to existing migration conventions.
- Avoid duplicating scene content if migration is interrupted or retried.
- Preserve unrelated project assets and exports.
- Ensure the migrated project can be saved and reopened successfully.

Migration must be idempotent where possible and must not modify completed historical user-story specifications.

## 12. Performance and Resource Management

- Scene switching must not reload unrelated project assets unnecessarily.
- Cached resources must be associated with the correct scene or shared project scope.
- Scene-specific caches must not display content from a previously active scene.
- Temporary rendering resources must be released when appropriate.
- Large scenes must not cause unnecessary loading of all other scenes' drawing data.
- If lazy loading is supported by the existing architecture, it should be used without complicating the initial implementation unnecessarily.

## 13. Acceptance Criteria

### Scene Selector

- [ ] The scene selector appears immediately before the Save button in the upper-right toolbar.
- [ ] The selector displays the active scene's name.
- [ ] The dropdown lists all scenes in the current project.
- [ ] The active scene has a visible selected state.
- [ ] The dropdown provides actions to create, rename, and delete scenes.
- [ ] Scene order is deterministic.

### Scene Creation

- [ ] The user can create a scene by providing a valid name.
- [ ] Duplicate names are rejected using case-insensitive comparison.
- [ ] A new scene receives a unique, stable identifier.
- [ ] A new scene starts with the required empty frame and layer structure.
- [ ] Existing scene content is not copied into the new scene.
- [ ] The new scene becomes active after successful creation.
- [ ] Canceling creation leaves the project unchanged.

### Scene Selection and Isolation

- [ ] The user can switch between existing scenes.
- [ ] Each scene retains its own frames, layers, drawings, and curves.
- [ ] Switching scenes does not merge or overwrite scene content.
- [ ] Unsaved changes are handled according to the defined policy.
- [ ] Playback of the previous scene stops during scene switching.
- [ ] Scene-specific editing state is restored when supported.
- [ ] The scene selector always reflects the active scene.

### Renaming and Deletion

- [ ] The user can rename a scene.
- [ ] Renaming preserves the scene identifier and content.
- [ ] Invalid or duplicate names are rejected with a clear message.
- [ ] The user must confirm scene deletion.
- [ ] Deleting a scene does not delete unrelated project assets or other scenes.
- [ ] The last remaining scene cannot be deleted.
- [ ] Deleting the active scene activates a valid remaining scene.
- [ ] Failed operations do not leave the project in an invalid state.

### Persistence and Compatibility

- [ ] Scene creation, renaming, and deletion survive project reopening.
- [ ] The Save button persists the active scene and relevant project metadata.
- [ ] Existing single-scene projects remain usable.
- [ ] Required migration preserves existing drawings, frames, layers, and assets.
- [ ] Invalid active-scene references are recovered safely.
- [ ] Project persistence failures are reported clearly.
- [ ] Scene switching does not affect existing brush, Bézier curve, undo/redo, or export behavior.

## 14. Testing Requirements

Automated tests must cover:

- Scene registry loading and validation.
- Scene creation and unique identifier generation.
- Scene name validation and case-insensitive duplicate detection.
- Scene selection and active scene state.
- Scene content isolation.
- Scene renaming.
- Deletion confirmation and last-scene protection.
- Active scene fallback after deletion.
- Unsaved-change handling.
- Playback stopping during scene switching.
- Save/reopen consistency.
- Persistence failures and recovery.
- Backward compatibility and project migration.
- Scene-specific cache isolation.
- Integration with frames, layers, brushes, Bézier curves, and export.

Manual testing must verify the complete workflow through the top toolbar, including creating multiple scenes, switching between them, renaming them, deleting them, and reopening the project.

## 15. Implementation Notes

- Inspect the existing project manifest, scene registry, scene directories, and scene-related services before implementation.
- Reuse the scene model already established by the project architecture.
- Do not create a second source of truth for scenes.
- Keep scene management logic outside UI components.
- Follow the existing Electron security architecture and typed IPC/preload API conventions.
- Keep filesystem operations in the Electron main process or existing privileged project service.
- Do not expose unrestricted filesystem access to the renderer.
- Do not refactor unrelated editor features.
- Preserve historical user-story specifications.
- Document any necessary migration or architecture changes in the implementation notes.

## 16. Definition of Done

This user story is complete when users can create, select, rename, and delete scenes through the top-toolbar dropdown, each scene maintains independent animation content, scene operations are persisted safely, existing projects remain compatible, and the complete workflow passes the acceptance criteria and automated tests.
