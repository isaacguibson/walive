# HU_00005 — Editor Navigation, Resizable Panels, Asset Management, and AI Chat Panel

**Status:** Proposed
**Priority:** High
**Type:** Feature Enhancement / Editor Architecture
**Related HUs:** HU_00001, HU_00002, HU_00003, HU_00004

---

# 1. Overview

Enhance the existing Animation Project Editor with four capabilities:

1. Canvas panning using the middle mouse button.
2. Resizable editor panels.
3. Project-wide asset management.
4. A dedicated AI chat panel prepared for future AI agent integrations.

These enhancements must extend the existing editor without replacing the functionality established by previous HUs.

The editor must continue to support the four primary areas defined in HU_00004, while introducing additional navigation, layout customization, asset management, and AI-oriented UI foundations.

---

# 2. Goals

This HU must:

* Allow users to pan the canvas by holding the middle mouse button and moving the mouse.
* Allow users to resize the frame management area.
* Allow users to resize the right-side inspector panel.
* Introduce a project-wide Asset Manager.
* Allow users to view, import, rename, and delete project assets.
* Keep assets associated with the project rather than individual scenes or frames.
* Introduce a dedicated AI Chat panel adjacent to the existing right-side panel.
* Provide a visual chat interface without implementing AI functionality.
* Prepare the architecture for future integrations with MCP-compatible AI agents and external coding assistants.
* Preserve the existing editor tools, timeline, canvas, layers, and playback functionality.

---

# 3. Non-Goals

This HU does not implement:

* AI model integration.
* MCP server implementation.
* OpenCode integration.
* GitHub Copilot integration.
* External AI provider authentication.
* Sending messages to AI agents.
* AI-generated images.
* AI-powered drawing modifications.
* Asset generation using AI.
* Asset versioning.
* Asset cloud synchronization.
* Asset marketplace.
* Advanced asset tagging or categorization.
* Advanced canvas navigation gestures.
* Persistent customization of every panel layout across application restarts, unless already supported by the existing application architecture.

These features may be introduced by future HUs.

# 5. Feature 1 — Canvas Panning

## 5.1 Overview

The user must be able to move the visible canvas viewport by holding the middle mouse button and moving the mouse.

This is particularly important when the canvas is zoomed in and portions of the drawing extend beyond the visible workspace.

Canvas panning changes the viewport position only. It must not modify:

* The project's logical canvas dimensions.
* Drawing coordinates.
* Frame contents.
* Layer contents.
* The configured canvas resolution.
* The current zoom level.

---

## 5.2 Interaction

The required interaction is:

1. The user places the pointer over the canvas workspace.
2. The user presses and holds the middle mouse button.
3. The user moves the mouse.
4. The visible canvas moves in the same direction as the pointer movement.
5. The user releases the middle mouse button.
6. Panning stops.

Example:

```text
Middle Mouse Button Down
          ↓
Track Pointer Movement
          ↓
Update Canvas Viewport Offset
          ↓
Middle Mouse Button Up
          ↓
Stop Panning
```

---

## 5.3 Panning Behavior

The panning operation must:

* Work when the canvas is zoomed in.
* Work when the canvas is zoomed out.
* Work at the default zoom level.
* Preserve the current zoom level.
* Preserve all drawing data.
* Avoid creating drawing strokes.
* Avoid triggering the selected drawing tool.
* Stop correctly when the middle mouse button is released.
* Handle pointer movement outside the canvas bounds when practical.

The canvas should follow the pointer naturally.

---

## 5.4 Interaction with Drawing Tools

Middle mouse button panning must work regardless of the selected drawing tool.

For example, if the Brush tool is selected, pressing the middle mouse button must pan the canvas rather than draw a stroke.

The panning interaction must not interfere with:

* Brush.
* Eraser.
* Fill Tool.
* Eyedropper.
* Selection Tool.

The existing primary drawing input behavior must remain unchanged.

---

## 5.5 Interaction with Zoom

Panning and zoom must work together.

The user must be able to:

1. Zoom in using the existing zoom controls.
2. Pan the canvas using the middle mouse button.
3. Zoom out again.
4. Continue drawing at the correct logical coordinates.

The canvas coordinate transformation must correctly account for both zoom and viewport offset.

Conceptually:

```text
Screen Coordinates
       ↓
Inverse Viewport Translation
       ↓
Inverse Zoom Transformation
       ↓
Logical Canvas Coordinates
```

Drawing must remain aligned with the visible canvas regardless of its viewport position.

---

## 5.6 Panning State

The editor should maintain viewport state conceptually equivalent to:

```ts
interface CanvasViewport {
  zoom: number;
  offsetX: number;
  offsetY: number;
}
```

The existing zoom implementation from HU_00004 should be extended rather than replaced.

The internal implementation may differ, but zoom and panning must share a consistent viewport transformation.

# 6. Feature 2 — Resizable Panels

## 6.1 Overview

The editor must allow the user to resize selected workspace areas by clicking and dragging their boundaries.

This enables users to allocate more space to the parts of the interface they currently need.

At minimum, the following areas must be resizable:

* The bottom Frame Management / Timeline area.
* The right Inspector panel containing tool properties and layers.

The implementation should use visible or discoverable resize boundaries.

---

## 6.2 Frame Management Area Resizing

The boundary separating the canvas workspace from the bottom Frame Management area must be draggable.

Example:

```text
┌───────────────────────────────────────────┐
│                                           │
│                  Canvas                   │
│                                           │
├════════════ Drag Boundary ═════════════════┤
│                                           │
│              Frame Management             │
│                                           │
└───────────────────────────────────────────┘
```

Dragging the boundary upward must increase the height of the Frame Management area.

Dragging the boundary downward must decrease its height.

The canvas workspace must automatically adapt to the remaining available space.

---

## 6.3 Inspector Panel Resizing

The boundary between the central canvas workspace and the right Inspector panel must be draggable.

Example:

```text
┌──────────────────────────────┬──────────────┐
│                              │              │
│                              │ Inspector    │
│            Canvas            │              │
│                              │              │
└──────────────────────────────┴──────────────┘
                               ↑
                         Drag Boundary
```

Dragging the boundary toward the center must increase the Inspector panel width.

Dragging it toward the right edge must decrease the Inspector panel width.

The central canvas must adapt to the available space.

---

## 6.4 Resize Interaction

Resize boundaries must:

* Be visually discoverable.
* Display an appropriate resize cursor.
* Respond to pointer dragging.
* Update the layout continuously while dragging.
* Prevent panels from becoming unusably small.
* Prevent panels from exceeding the available application window space.
* Avoid accidental clicks on neighboring controls.
* Stop resizing when the pointer interaction ends.

The exact minimum and maximum dimensions may be chosen during implementation, provided they are reasonable and enforced consistently.

---

## 6.5 Layout Constraints

Resizing must preserve the overall editor layout.

The application must not allow:

* Panels to overlap unintentionally.
* The canvas to become completely inaccessible.
* The timeline to cover the canvas.
* The Inspector to extend outside the application window.
* The AI Chat panel to overlap the Inspector.

The central canvas should receive the remaining available space after panel dimensions are applied.

---

## 6.6 Layout State

The layout system should centralize panel dimensions rather than allowing unrelated UI components to modify each other's dimensions directly.

Conceptually:

```ts
interface EditorLayoutState {
  timelineHeight: number;
  inspectorWidth: number;
  aiChatWidth: number;
  assetPanelVisible: boolean;
  aiChatVisible: boolean;
}
```

This model is illustrative. The exact state structure may be adapted to the existing application.

The implementation must avoid introducing duplicate sources of truth for panel dimensions.

# 7. Feature 3 — Project Asset Manager

## 7.1 Overview

The application must provide a dedicated area for managing assets belonging to the current project.

Assets are project-wide resources.

They must not belong exclusively to a particular scene, frame, or layer.

Examples of project assets include:

* Images.
* Textures.
* Audio files.
* Video files.
* Fonts.
* Other supported resource types introduced by the application.

The Asset Manager must allow users to view existing assets, import new assets, rename assets, and delete assets.

---

## 7.2 Asset Manager Access

The Asset Manager must be accessible from the project editor.

It may be implemented as:

* A dedicated panel.
* A tab within an appropriate editor sidebar.
* A dedicated project-assets workspace section.

The chosen layout must remain consistent with the existing editor design.

The Asset Manager must remain separate from the layer hierarchy.

The layer panel represents drawing layers belonging to a frame.

The Asset Manager represents reusable resources belonging to the project.

---

## 7.3 Asset List

The Asset Manager must display the assets available in the active project.

At minimum, each asset entry should display:

* Asset name.
* Asset type or file extension.
* A suitable icon or thumbnail when available.

Image assets should display thumbnails when practical.

For unsupported preview formats, the application may display a generic file-type icon.

The user must be able to distinguish individual assets.

---

## 7.4 Asset Import

The user must be able to import new assets into the current project.

The Asset Manager must provide an import action.

Example:

```text
Project Assets

[ + Import Asset ]

┌────────────────────────────┐
│ [Thumbnail] character.png  │
│ [Thumbnail] background.jpg │
│ [Icon]      music.mp3      │
└────────────────────────────┘
```

The import workflow must use a native file picker or an equivalent appropriate desktop file-selection mechanism.

The Electron main process must handle privileged filesystem operations.

The renderer must not access the filesystem directly.

---

## 7.5 Import Behavior

When the user imports an asset:

1. Open the native file-selection dialog.
2. Allow the user to select one or more supported files.
3. Copy the selected files into the active project's asset directory.
4. Register or index the imported assets using the project's asset-management abstraction.
5. Refresh the Asset Manager UI.
6. Display the imported assets.

The implementation must prevent silent overwriting of existing assets.

If a file with the same name already exists, the application must resolve the conflict safely.

Acceptable strategies include:

* Asking the user how to resolve the conflict.
* Generating a unique destination filename.
* Providing an explicit replacement operation with confirmation.

The application must not silently destroy an existing asset.

---

## 7.6 Project Asset Directory

Imported assets must be stored within the project directory.

The implementation should use the existing project structure defined in HU_00001.

The default asset location is:

```text
<ProjectName>/
├── project.json
├── scenes/
├── assets/
│   ├── images/
│   ├── audio/
│   ├── video/
│   └── fonts/
├── drawings/
├── exports/
└── .cache/
```

Assets must remain project-owned resources.

The implementation may introduce an asset registry or metadata file if necessary, but it must not conflict with the existing project manifest.

A possible future extension is:

```text
assets/
├── images/
├── audio/
├── video/
├── fonts/
└── registry.json
```

The registry is not mandatory if the existing architecture can reliably enumerate and manage project assets without it.

---

## 7.7 Asset Types and Storage

The implementation must identify the asset type from reliable file metadata, such as the file extension and, where appropriate, file content.

Supported asset types should align with the existing project directory categories.

At minimum, the architecture must accommodate image assets.

Audio, video, and font assets should be supported by the Asset Manager when the import infrastructure can safely handle them.

Unsupported file types must be handled explicitly rather than silently treated as valid assets.

The asset model should not depend solely on the current UI representation.

---

## 7.8 Rename Asset

The user must be able to rename an asset from the Asset Manager.

The rename operation must:

* Allow the user to enter a new name.
* Validate the name.
* Prevent invalid filesystem names.
* Prevent unintended collisions with existing assets.
* Preserve the asset's file extension unless the application explicitly supports a safe extension change.
* Update the asset listing after a successful rename.

Renaming an asset must not silently overwrite another asset.

If an asset is already referenced by another project resource, the implementation must preserve reference integrity.

The asset should have a stable identity independent of its display name or filename whenever the asset model supports it.

The application must not rename a file in a way that leaves known internal references broken.

---

## 7.9 Delete Asset

The user must be able to delete an asset from the Asset Manager.

Deletion must require a clear user action.

The application should display a confirmation dialog before permanently deleting an asset.

If an asset is referenced by a known scene, drawing, or other project resource, the application must not silently break that reference.

In such cases, the application should either:

* Prevent deletion and explain that the asset is in use; or
* Ask the user to confirm a clearly explained deletion that identifies the consequences.

The chosen behavior must be consistent.

Deleting an asset must not delete the entire project or unrelated resources.

---

## 7.10 Asset Selection

Clicking an asset must select it and display a clear selected state.

The Asset Manager may provide a preview area or a details section.

At minimum, selection must identify the asset and make its available operations accessible.

Double-click behavior may open a preview for supported asset types, but advanced preview and editing functionality are outside the scope of this HU.

---

## 7.11 Project-Wide Ownership

Assets must be owned by the project, not by a scene or frame.

For example:

```text
Project
├── Assets
│   ├── character.png
│   ├── background.png
│   └── music.mp3
│
├── Scenes
│   ├── Scene 1
│   └── Scene 2
│
└── Drawings
```

Both Scene 1 and Scene 2 must be able to reference the same project asset in the future.

This HU does not require implementing scene-level asset references, but the Asset Manager architecture must not prevent them.

---

## 7.12 Asset Model

The implementation should use a structured asset model.

Conceptually:

```ts
type ProjectAssetType =
  | "image"
  | "audio"
  | "video"
  | "font"
  | "other";

interface ProjectAsset {
  id: string;
  name: string;
  type: ProjectAssetType;
  relativePath: string;
  extension: string;
}
```

Additional metadata may be introduced when needed.

The asset ID should remain stable when the asset is renamed, where supported by the chosen asset registry design.

Project-owned asset paths should be relative to the project directory.

The renderer must not construct unrestricted filesystem paths or directly manipulate asset files.

---

## 7.13 Asset Management API

Asset operations must be implemented through a dedicated service or domain API.

Conceptually:

```ts
interface AssetManagementAPI {
  listAssets(): Promise<ProjectAsset[]>;
  importAssets(): Promise<ProjectAsset[]>;
  renameAsset(
    assetId: string,
    newName: string
  ): Promise<ProjectAsset>;
  deleteAsset(assetId: string): Promise<void>;
}
```

The exact signatures may differ according to the existing architecture.

The important requirement is that asset-management logic must not be implemented entirely inside UI components.

The API should be reusable by:

* The Asset Manager UI.
* Future scenes and drawing workflows.
* Automated tests.
* Future plugins.
* Future AI agents.
* Future MCP tools.

# 8. Feature 4 — AI Chat Panel

## 8.1 Overview

The editor must include a dedicated AI Chat panel.

This panel is a visual placeholder for future integrations with AI agents and tools.

The chat must not communicate with an AI provider in this HU.

Its purpose is to establish the panel layout and initial user interface while preserving a clear path for future MCP-based integrations.

---

## 8.2 Position

The AI Chat panel must be positioned to the right of the existing Inspector panel.

Conceptually:

```text
┌─────────────────────┬─────────────────────┐
│                     │                     │
│   Inspector         │      AI Chat        │
│                     │                     │
│   Tool Properties   │                     │
│   ───────────────   │                     │
│   Layers            │                     │
│                     │                     │
└─────────────────────┴─────────────────────┘
```

The Inspector and AI Chat must be distinct panels.

The AI Chat must not replace the existing tool-properties or layer-management functionality.

---

## 8.3 Chat Interface

The initial chat interface must include:

* A panel title.
* A message history area.
* An empty-state message.
* A text input area.
* A send button.

A conceptual layout is:

```text
┌─────────────────────────────────┐
│ AI Assistant                    │
├─────────────────────────────────┤
│                                 │
│                                 │
│                                 │
│       Start a conversation      │
│                                 │
│                                 │
├─────────────────────────────────┤
│ [ Ask something...          ]   │
│                            [↑]  │
└─────────────────────────────────┘
```

The exact visual styling may be adapted to the existing application.

---

## 8.4 Placeholder Behavior

The chat is visual only.

The following requirements apply:

* The user can see the chat panel.
* The user can type text into the input.
* The send button is visible.
* The UI may support local visual message previews if needed to demonstrate the layout.
* No message may be sent to an external service.
* No AI provider credentials are required.
* No network requests are made for chat functionality.
* No MCP server is started.
* No AI-generated response is simulated as if it came from a real model.

If local message previews are implemented, they must be clearly understood as local UI behavior rather than real AI responses.

The application must not mislead the user into believing that an AI agent is connected.

---

## 8.5 Empty State

When no messages exist, the panel should display a clear empty state.

Example:

```text
AI Assistant

Your AI assistant will be available here
in a future release.

AI integrations are not configured yet.
```

The wording may be adapted to the product's final design.

The empty state should make it clear that AI integration is not yet available.

---

## 8.6 Input Behavior

The chat input should:

* Accept multiline text where practical.
* Allow typing and editing.
* Support normal text selection and copy/paste.
* Provide a clear placeholder.
* Remain visually consistent with the editor theme.

Because the chat is a placeholder, the input does not need to execute commands.

The send button may be disabled until chat functionality is implemented, or may add a local-only preview message if explicitly implemented as a visual prototype.

No network communication is permitted for this HU's chat functionality.

---

## 8.7 Chat State

The chat UI may maintain local transient state.

Conceptually:

```ts
interface ChatMessage {
  id: string;
  role: "user" | "assistant";
  content: string;
  createdAt: string;
}

interface AIChatState {
  messages: ChatMessage[];
  inputValue: string;
}
```

This model is illustrative and does not require persistent chat history.

The chat must not require AI credentials or external connections.

Persistent conversations are outside the scope of this HU.

---

# 9. Future AI Integration Compatibility

Although the chat is visual only, its architecture should not make future integrations unnecessarily difficult.

The UI should be separated from any future AI provider implementation.

A future architecture may follow:

```text
AI Chat UI
     ↓
AI Integration Service
     ↓
Agent / Provider Adapter
     ↓
MCP Client or Other Integration
     ↓
External AI Agent
```

Potential future integrations include:

* OpenCode.
* GitHub Copilot and its supported extension/integration mechanisms.
* MCP-compatible agents.
* Custom AI agents.
* Local AI models.
* Other providers supported by future HUs.

This HU must not assume that every provider uses the same protocol.

MCP is one possible integration mechanism, not a requirement for all future providers.

The UI must not be directly coupled to a specific AI vendor.

---

# 10. AI Chat Extension Points

The implementation should preserve clear extension points for future capabilities, including:

* Sending messages to an agent.
* Receiving streaming responses.
* Displaying tool execution status.
* Showing confirmation requests.
* Displaying errors.
* Associating conversations with the active project.
* Providing the active frame, layer, or canvas context to an agent.
* Allowing an agent to invoke approved application APIs.

These capabilities must not be implemented in HU_00005 unless required for the visual placeholder.

---

# 11. MCP Compatibility

Future MCP integration must use application/domain APIs instead of directly manipulating the editor's DOM.

For example, future AI tools may need to:

```text
get_current_project
get_current_frame
get_selected_layer
get_canvas
get_project_assets
import_asset
create_frame
duplicate_frame
create_layer
```

The asset-management API and editor-domain abstractions should remain accessible independently of the UI.

This HU does not implement MCP tools or an MCP server.

---

# 12. Interaction Between the New Features

The new capabilities must coexist with the existing editor.

## Canvas Panning and Resizing

Resizing the Inspector or Timeline must not reset the canvas viewport unexpectedly.

Panning must continue to work after panel resizing.

## Asset Manager and Editor State

Opening the Asset Manager must not destroy the current frame or layer selection.

Importing or renaming assets must not reset the active drawing context.

## AI Chat and Editor State

Opening or using the AI Chat panel must not modify the animation or frame selection.

The chat panel must not interfere with canvas pointer events when the pointer is inside the chat.

## Panel Resizing

Resizing one panel must not unintentionally resize unrelated panels unless required by the layout constraints.

# 13. Electron Architecture and Security

The existing Electron architecture established in HU_00001 and HU_00002 must remain intact.

The intended structure is:

```text
Renderer
    ↓
Typed Preload API
    ↓
Explicit IPC
    ↓
Electron Main Process
    ↓
Project / Asset Services
    ↓
Project Filesystem
```

Requirements:

* The renderer must not access Node.js filesystem APIs directly.
* The renderer must not receive unrestricted filesystem access.
* Asset import must use an approved IPC workflow.
* Asset rename and delete must be validated by the service layer.
* Filesystem paths must be resolved and validated by trusted application code.
* Asset operations must be restricted to the active project's asset directories.
* The existing `contextIsolation: true` and `nodeIntegration: false` security settings must be preserved.

The chat placeholder must not introduce unnecessary network permissions or external service dependencies.

---

# 14. Error Handling

The application must handle errors gracefully.

Examples include:

* Asset import failure.
* Unsupported file type.
* Duplicate asset name.
* Invalid asset name.
* Asset rename failure.
* Asset deletion failure.
* Attempting to delete an asset that is in use.
* Failure to load the asset list.
* Invalid panel dimensions.
* Canvas panning interruption.
* Failure to enter or exit fullscreen, if affected by layout changes.

Error messages must be understandable to users.

Failed asset operations must not silently corrupt the project.

---

# 15. Performance Considerations

The new features must not noticeably degrade drawing performance.

Requirements:

* Canvas panning must not trigger unnecessary drawing-data serialization.
* Panel resizing must avoid unnecessary recreation of the animation engine.
* Asset thumbnails should be loaded efficiently.
* Large asset collections should not require decoding every full-resolution image simultaneously.
* Asset import must not block the renderer unnecessarily.
* The chat placeholder must not create background network activity.
* Asset operations must not force the entire project to be reloaded unless necessary.

The implementation should remain suitable for projects containing large canvases and many frames.

# 19. Architectural Principle

HU_00005 extends the editor through independent subsystems rather than coupling unrelated features together.

The intended architecture is:

```text
Animation Project Editor
          │
          ├── Canvas Viewport
          │       ├── Zoom
          │       └── Pan
          │
          ├── Layout Manager
          │       ├── Timeline Size
          │       ├── Inspector Size
          │       └── AI Chat Size
          │
          ├── Asset Management
          │       ├── Asset Repository
          │       ├── Import Service
          │       ├── Rename Service
          │       └── Delete Service
          │
          └── AI Chat UI
                  └── Future AI Integration Service
```

Each subsystem must have a clear responsibility.

The canvas viewport manages how the user sees the drawing surface.

The layout manager controls workspace dimensions.

The Asset Manager manages project-owned resources.

The AI Chat panel provides the future interaction surface for AI agents.

The existing project and animation services remain responsible for project data and animation state.
