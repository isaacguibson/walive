# HU_00007.md — Stroke Stabilization and Animation Keyboard Shortcuts

## 1. Overview

**ID:** HU_00007
**Title:** Stroke Stabilization and Animation Keyboard Shortcuts
**Status:** Proposed
**Priority:** High
**Type:** Feature Enhancement
**Related HUs:** HU_00001, HU_00002, HU_00004, HU_00005, HU_00006

### 1.1. Objective

Introduce stroke stabilization for the Brush Tool and keyboard shortcuts for navigating animation frames and controlling playback.

This user story aims to improve drawing precision, accelerate frame navigation, and provide a more efficient animation workflow without requiring frequent interaction with toolbar buttons.

The following features must be implemented:

1. **Stabilize Stroke:** Add a toggle to the Brush Tool Options that smooths brush strokes to reduce unintended tremors while preserving the artist's intended movement.
2. **Next Frame (`Ctrl + W`):** Navigate to the next frame or create a new empty frame when the current frame is the last frame.
3. **Previous Frame (`Ctrl + A`):** Navigate to the previous frame, without performing any action when the first frame is already selected.
4. **Play/Pause (`Space`):** Start animation playback when paused or pause playback when the animation is running.

---

## 2. Scope

### 2.1. In Scope

* Add a **Stabilize Stroke** toggle to the Brush Tool Options.
* Implement real-time stroke stabilization while drawing.
* Reduce unintended tremors and abrupt movements in brush strokes.
* Preserve the original brush configuration, including brush size, color, and pen pressure settings.
* Implement the `Ctrl + W` shortcut for next-frame navigation and automatic creation of an empty frame at the end of the timeline.
* Implement the `Ctrl + A` shortcut for previous-frame navigation.
* Implement the `Space` shortcut for animation playback toggling.
* Ensure keyboard shortcuts coexist with the existing Editor interactions and do not interfere with text inputs or other controls.
* Maintain compatibility with existing drawing, frame management, animation playback, and undo/redo functionality.

### 2.2. Out of Scope

* Advanced stabilization configuration, such as user-defined smoothing algorithms or multiple stabilization modes.
* Dedicated stabilization sliders or numeric configuration fields.
* Automatic correction of completed strokes after drawing.
* Changes to existing brush properties unrelated to stroke stabilization.
* New animation playback controls beyond the specified keyboard shortcut.
* Changes to the animation frame rate or playback engine.
* Customizable keyboard shortcut mappings.

# 3. Feature 1 — Stabilize Stroke

## 3.1. Description

The application must provide a **Stabilize Stroke** toggle in the Brush Tool Options panel.

When enabled, the application must process the artist's pointer or pen movement to reduce unintended tremors and produce smoother, more controlled brush strokes.

Stroke stabilization is a common feature in digital drawing and illustration applications. It helps users create smoother lines, particularly when drawing long curves, contours, and precise details.

When disabled, the Brush Tool must preserve its existing drawing behavior without additional stabilization processing.

## 3.2. User Interface

Add a toggle control to the Brush Tool Options panel with the following label:

**Stabilize Stroke**

### Requirements

* The toggle must be visible whenever the Brush Tool is selected.
* The control must have clearly distinguishable enabled and disabled states.
* A tooltip must explain that the feature smooths brush strokes and reduces unintended tremors.
* The control must follow the visual conventions of the existing Tool Options panel.
* Enabling or disabling stabilization must not reset other brush properties.
* The feature must work independently of the existing **Use Pen Pressure** setting defined in HU_00006.
* The feature must not modify the configured brush size, color, or other brush settings.

The toggle should be disabled by default unless an existing application-wide brush preference convention explicitly requires another default.

## 3.3. Behavior When Enabled

When **Stabilize Stroke** is enabled, the application must smooth the movement used to generate the brush stroke.

### Requirements

* Reduce small, unintended variations in pointer or pen movement.
* Produce smoother lines and curves than the equivalent unstabilized input.
* Process the stroke progressively while the user draws.
* Keep the displayed stroke responsive to the artist's movement.
* Preserve the general direction, shape, and intent of the original movement.
* Apply stabilization consistently to supported pointer and pen input.
* Avoid abrupt jumps or discontinuities when the stroke starts, changes direction, or ends.
* Preserve the final stabilized stroke after the user releases the pointer or pen.
* Ensure that stabilization does not modify previously completed strokes.

The stabilization algorithm may use input smoothing, interpolation, filtering, or another appropriate technique supported by the existing drawing engine.

The implementation must balance smoothness and responsiveness. Excessive smoothing that causes noticeable delays or makes the brush difficult to control should be avoided.

## 3.4. Behavior When Disabled

When **Stabilize Stroke** is disabled:

* The Brush Tool must use its existing input-to-stroke behavior.
* Pointer and pen movement must not receive additional stabilization processing from this feature.
* Existing brush rendering behavior must remain unchanged.
* Other brush settings, including pen pressure sensitivity, must continue to operate according to their respective configurations.

Disabling stabilization must not alter strokes that were previously drawn with stabilization enabled.

## 3.5. Integration with Pen Pressure

Stroke stabilization must be compatible with the pressure-sensitive brush sizing functionality defined in HU_00006.

### Requirements

* Stabilization must not disable pen pressure support.
* Pressure data must remain associated with the corresponding input samples throughout the stroke.
* Brush size must continue to respond to pressure when **Use Pen Pressure** is enabled.
* The stabilization process must not introduce unexpected pressure spikes or cause the effective brush size to fluctuate incorrectly.
* The final stroke must preserve both its stabilized geometry and its intended pressure-dependent appearance.

The implementation must determine an appropriate processing order for pointer coordinates and pressure samples. The chosen approach must produce a smooth stroke while maintaining a consistent relationship between the artist's input and the resulting brush size.

## 3.6. Stroke Lifecycle and Persistence

The stabilization process must integrate with the existing stroke generation and persistence architecture.

### Requirements

* A stroke must begin when the user initiates a drawing gesture.
* Stabilization must be applied while the gesture is in progress.
* The stroke must be finalized when the drawing gesture ends.
* The final stroke must not change unexpectedly after completion.
* Undo must remove the completed stroke correctly.
* Redo must restore the same stabilized stroke.
* Saving and reopening the project must preserve the stroke's appearance.
* Copying or duplicating frame content must preserve the appearance of stabilized strokes.
* Exported images must render the finalized stroke consistently with the canvas.

The implementation may store the final stabilized geometry or another representation supported by the drawing engine. Reproducing a completed stroke must not require the original input device or the stabilization algorithm to run again.

## 3.7. Performance and Responsiveness

* Stabilization must operate efficiently enough for continuous drawing.
* The canvas must remain responsive during long strokes.
* The implementation must avoid unnecessary allocations or expensive processing for every input event.
* Stroke smoothing must not cause noticeable visual lag under normal operating conditions.
* When stabilization is disabled, the drawing pipeline should avoid unnecessary stabilization processing.
* The implementation must remain compatible with canvas zooming, panning, and existing coordinate transformations.

# 4. Feature 2 — Next Frame Shortcut (`Ctrl + W`)

## 4.1. Description

The `Ctrl + W` keyboard shortcut must navigate to the next frame in the timeline.

If the currently selected frame is the last frame in the timeline, the application must create a new empty frame immediately after it and select the newly created frame.

This shortcut is intended to support rapid frame-by-frame animation workflows.

## 4.2. Keyboard Shortcut

**Shortcut:** `Ctrl + W`

### Requirements

* The shortcut must work when the Editor is active.
* If a frame exists after the currently selected frame, select that next frame.
* If the currently selected frame is the last frame, create a new empty frame immediately after it.
* Automatically select the newly created frame.
* Update the timeline selection and canvas to reflect the newly active frame.
* Ensure that all related Editor panels display the state associated with the newly selected frame.
* Preserve the contents of all existing frames.
* Integrate with the existing frame creation and selection mechanisms rather than implementing a separate frame creation process.

## 4.3. Creating a New Empty Frame

When the current frame is the last frame and the user presses `Ctrl + W`, the application must create an empty frame.

### Requirements

* The new frame must be inserted immediately after the current last frame.
* The new frame must be selected automatically.
* The new frame must contain no copied drawing content from the previous frame.
* The new frame must follow the existing frame model and default layer initialization rules.
* If the application requires every frame to contain at least one layer, the new frame must include the required empty layer or layers.
* The new frame must respect the project's canvas dimensions and existing animation settings.
* The new frame must be persisted according to the existing project document-state rules.
* The creation operation must integrate with the application's undo/redo history.

The new frame must be genuinely empty. It must not duplicate or inherit visible drawing content from the previous frame.

The existing Onion Reference behavior defined in HU_00006 must remain intact. If Onion Reference is enabled, the newly created frame may display the previous frame as a visual reference, but that reference must not become part of the new frame's editable content.

## 4.4. Navigation Behavior

When another frame exists after the currently selected frame:

* Select the immediately following frame.
* Do not create a new frame.
* Do not modify the content of either frame.
* Update the canvas to display the selected frame.
* Preserve the existing frame selection and navigation conventions.

The shortcut must follow the current timeline order, including any supported frame reordering.

## 4.5. Boundary Conditions

* If no project is open, the shortcut must not create a frame.
* If no valid frame is selected while a project is open, the shortcut must follow the Editor's established frame selection rules and must not create duplicate or invalid frames.
* If the current frame is the last frame, create exactly one new frame per shortcut activation.
* Repeated activations must not be lost or duplicated due to stale timeline state.
* If frame creation fails, display an appropriate error or feedback message and preserve the existing project state.

## 4.6. Interaction with Existing Frame Commands

The shortcut must reuse the same frame creation operation used by the existing timeline controls wherever possible.

It must remain consistent with the frame management behavior defined in HU_00004, including:

* Frame selection.
* Empty frame creation.
* Timeline ordering.
* Undo and redo.
* Onion Reference rendering.
* Frame content isolation.

# 5. Feature 3 — Previous Frame Shortcut (`Ctrl + A`)

## 5.1. Description

The `Ctrl + A` keyboard shortcut must navigate to the immediately preceding frame in the timeline.

If the first frame is already selected, pressing the shortcut must not perform any action.

## 5.2. Keyboard Shortcut

**Shortcut:** `Ctrl + A`

### Requirements

* The shortcut must work when the Editor is active.
* If the selected frame is not the first frame, select the immediately preceding frame.
* If the first frame is selected, do nothing.
* Do not create or remove frames.
* Do not modify the contents of any frame.
* Update the canvas to display the newly selected frame.
* Update any frame-dependent Editor panels consistently.
* Preserve the current timeline ordering.
* Maintain compatibility with the Onion Reference feature.

## 5.3. Navigation Behavior

When the selected frame has a preceding frame:

* Select the preceding frame.
* Update the timeline's active selection.
* Display the selected frame on the canvas.
* Update the automatic Onion Reference, if enabled and no manual reference has been designated.

If a manually designated Onion Reference exists, the reference must remain designated regardless of frame navigation, according to HU_00006.

## 5.4. Boundary Conditions

* If no project is open, the shortcut must not perform any project operation.
* If the first frame is selected, the shortcut must not change the selection.
* The shortcut must not move the selection outside the valid timeline range.
* The shortcut must not create an additional frame when the first frame is selected.
* If no valid frame is selected, the shortcut must follow the Editor's established navigation rules without modifying project content.

# 6. Feature 4 — Animation Playback Shortcut (`Space`)

## 6.1. Description

The `Space` key must toggle animation playback.

* If the animation is paused, pressing `Space` must start playback.
* If the animation is playing, pressing `Space` must pause playback.

The shortcut must use the existing playback functionality and remain synchronized with the play/pause button defined in HU_00004.

## 6.2. Keyboard Shortcut

**Shortcut:** `Space`

### Requirements

* The shortcut must work when the Editor is active and a valid project is open.
* If playback is paused, start animation playback.
* If playback is running, pause animation playback.
* Update the play/pause button's visual state immediately.
* Maintain synchronization between the shortcut and the existing playback controls.
* Respect the configured animation FPS.
* Preserve the existing playback loop configuration.
* Do not create, delete, or modify frames as a side effect of toggling playback.
* Avoid starting multiple concurrent playback loops.
* Avoid leaving the playback state inconsistent between the animation engine and the UI.

## 6.3. Playback State Management

The shortcut must delegate to the existing animation playback controller or equivalent shared service.

The application must not implement a separate playback mechanism specifically for the keyboard shortcut.

The resulting state must be reflected consistently in:

* The animation playback engine.
* The play/pause toolbar button.
* The current playback position.
* The timeline and canvas display.
* Any existing playback-related UI indicators.

When playback is paused, the animation must stop advancing and preserve the current playback position according to the existing playback behavior.

When playback resumes, the animation must continue according to the existing playback rules.

## 6.4. Interaction with Frame Navigation

The `Ctrl + W` and `Ctrl + A` shortcuts are intended for editing and frame navigation.

If the application is currently playing the animation, frame navigation must follow the existing playback and timeline interaction conventions. The implementation must avoid inconsistent states in which the animation engine continues advancing while the Editor incorrectly displays a different manually selected frame.

If required by the existing playback architecture, the application may pause playback before performing a frame navigation operation, provided this behavior is implemented consistently and documented.

## 6.5. Keyboard Focus and Input Handling

The `Space` shortcut must not interfere with normal text entry or other controls that use the space character.

### Requirements

* When the user is typing in a text input, textarea, or another editable text control, pressing `Space` must insert a space instead of toggling playback.
* When a UI control explicitly uses `Space` for its standard keyboard interaction, the shortcut must not unintentionally override that behavior.
* The shortcut must be handled through the application's centralized keyboard shortcut mechanism or an equivalent shared Editor-level input handler.
* The shortcut must not trigger multiple playback toggles from a single key press.
* The application must prevent unintended default browser or renderer behavior only when the shortcut is actually handled by the Editor.

# 7. Keyboard Shortcut Management

## 7.1. Centralized Shortcut Handling

All shortcuts introduced by this user story must be implemented through a consistent keyboard shortcut handling mechanism.

The implementation must avoid registering duplicate listeners when the user switches frames, changes tools, opens or closes panels, or enters and exits the Editor.

### Requirements

* Register shortcuts only when the relevant application context is active.
* Remove or deactivate listeners when the relevant context is destroyed or no longer applicable.
* Prevent duplicate event handling.
* Ensure that shortcuts work across the supported operating systems, subject to platform-specific modifier conventions.
* Ensure that keyboard shortcuts do not interfere with text inputs, editable fields, dialogs, or other controls that require normal keyboard interaction.
* Reuse existing Editor command handlers wherever possible.

## 7.2. Platform Compatibility

The requested shortcuts use `Ctrl` as the specified modifier.

The implementation must support the requested `Ctrl` combinations on platforms where `Ctrl` is the expected modifier. If the application already has a platform-specific shortcut convention, such as using `Command` on macOS, the implementation must resolve that convention consistently and document any platform-specific behavior.

The implementation must not introduce conflicting shortcut behavior without evaluating existing application commands.

## 7.3. Shortcut Summary

| Shortcut   | Action                    | Boundary Behavior                                                              |
| ---------- | ------------------------- | ------------------------------------------------------------------------------ |
| `Ctrl + W` | Select the next frame     | Creates and selects a new empty frame when the current frame is the last frame |
| `Ctrl + A` | Select the previous frame | Does nothing when the first frame is selected                                  |
| `Space`    | Toggle animation playback | Starts playback when paused and pauses playback when playing                   |

The shortcut implementation must account for any conflicts with existing commands or platform-level behavior and must ensure that the intended Editor action is executed only in the appropriate context.

# 8. Architecture and Implementation Considerations

## 8.1. Stroke Stabilization

Stroke stabilization must be implemented within the existing drawing pipeline.

The implementation should conceptually separate:

* **Input sampling:** Collection of pointer or pen coordinates and associated input data.
* **Stabilization:** Processing of input coordinates to reduce unintended tremors.
* **Brush processing:** Application of brush settings, including size, color, and pressure sensitivity.
* **Stroke generation:** Production of the resulting stroke geometry or drawing representation.
* **Persistence:** Storage of the finalized stroke for rendering, undo/redo, and export.

The exact processing order may depend on the existing drawing engine, but it must preserve the intended relationship between stabilized geometry and pressure-sensitive brush sizing.

The UI toggle must delegate to the drawing system rather than implementing stabilization independently inside the renderer component.

## 8.2. Frame Navigation

Frame navigation must use the existing frame management service or equivalent application API.

The implementation should reuse shared operations for:

* Getting the current frame.
* Finding the next or previous frame.
* Selecting a frame.
* Creating a new empty frame.
* Updating the timeline and canvas.
* Recording changes in undo/redo history.

Frame navigation must be based on the current timeline order and stable frame identifiers, rather than relying exclusively on hard-coded frame indexes.

## 8.3. Playback Control

Playback toggling must use the existing animation playback controller.

The keyboard shortcut must not independently implement frame timing, frame advancement, or playback scheduling.

The playback controller remains the source of truth for whether the animation is playing or paused.

## 8.4. Electron and Renderer Architecture

The implementation must follow the existing Electron security and application architecture.

* Keyboard shortcuts should be handled in the appropriate Editor context.
* UI components must delegate drawing, frame navigation, and playback operations to the appropriate services.
* Renderer components must not gain unrestricted filesystem or Node.js access.
* Existing `contextIsolation: true` and `nodeIntegration: false` requirements must remain intact.
* Any required communication between the renderer, preload, and main process must use explicit, typed APIs and IPC channels according to the existing architecture.

# 9. Error Handling and Edge Cases

## 9.1. Stroke Stabilization

* Missing input samples must not cause the drawing pipeline to crash.
* The stroke must finalize correctly when the user releases the pointer or pen.
* Abrupt input termination must not leave an unfinished stroke in the canvas state.
* Switching tools during a drawing gesture must follow existing drawing cancellation or completion rules.
* Enabling or disabling stabilization must not modify previously completed strokes.
* Pressure-sensitive brush sizing must continue to work when stabilization is enabled.

## 9.2. Frame Navigation

* Navigation must remain within the valid timeline boundaries.
* `Ctrl + W` must create only one empty frame when invoked at the end of the timeline.
* Failed frame creation must not corrupt the project or leave an invalid selection.
* Frame selection must remain consistent between the timeline and canvas.
* Undo must restore the previous state after a frame is created through `Ctrl + W`, according to the existing frame history conventions.
* Onion Reference behavior must remain correct after navigation or frame creation.

## 9.3. Playback

* Pressing `Space` repeatedly must not create multiple playback loops.
* Playback must not start when no valid project or animation context is available.
* Pausing must stop frame advancement according to the playback controller's existing behavior.
* Playback controls and keyboard shortcuts must remain synchronized.
* Key events received while the user is typing must not trigger unintended playback actions.

# 13. Architectural Principles

* **Drawing quality:** Stroke stabilization must improve line smoothness without substantially compromising responsiveness or artistic intent.
* **Independent brush settings:** Stabilization and pen pressure must operate together without interfering with each other's configuration.
* **Shared frame operations:** Keyboard navigation must reuse the same frame management logic as the existing Editor controls.
* **Shared playback controller:** The `Space` shortcut must delegate to the existing playback system.
* **Context-aware shortcuts:** Keyboard shortcuts must not interfere with text entry or unrelated controls.
* **Consistent state:** Timeline selection, canvas content, playback state, and UI indicators must remain synchronized.
* **Safe frame creation:** Automatically created frames must be empty and must not modify existing frame content.
* **Historical specification integrity:** HU_00007 extends previous requirements without modifying the historical contents of HU_00001 through HU_00006. Any future corrections or architectural changes must be documented in a new user story.
