# HU_00016 — GitHub Copilot SDK Provider Integration

## 1. Objective

Integrate GitHub Copilot into Animation Studio as a fully functional AI agent provider, using the official GitHub Copilot SDK for TypeScript whenever supported by the current SDK version.

The integration must provide an experience comparable to the GitHub Copilot provider in OpenCode, including:

- Connecting a GitHub account.
- Authenticating with GitHub Copilot.
- Discovering available models dynamically.
- Selecting the active model.
- Streaming assistant responses.
- Maintaining conversations and agent sessions.
- Invoking custom tools to inspect and modify animation projects.
- Displaying tool execution progress and results.
- Supporting cancellation, error recovery, and user approvals.

The integration must follow the application's existing AI architecture and must not introduce a separate, incompatible agent framework.

## 2. Scope and Dependencies

This requirement depends on the following existing specifications:

- `HU_00014 — AI Agent Workspace and Provider Integration`
- `HU_00015 — Internal Editing API and Command System`

The provider adapter must integrate with the existing provider registry, model registry, conversation service, agent workspace, credential management, and approved editing API.

If any dependency has not yet been implemented, the integration must introduce only the minimum required interfaces or identify the dependency explicitly. It must not assume that previously specified functionality already exists in the codebase.

## 3. Technical Approach

### 3.1. Preferred SDK

Use the official GitHub Copilot SDK for TypeScript:

`@github/copilot-sdk`

Before implementation, inspect the current stable SDK version, its license, supported authentication methods, model-discovery API, tool-registration API, session lifecycle, and Electron compatibility.

Pin a compatible version and document the upgrade procedure.

The SDK's agent runtime should handle model interaction and tool-call orchestration. Animation Studio must provide the application-specific tools and user experience.

Do not reimplement Copilot's protocol or duplicate its agent loop unless a documented SDK limitation requires a separate adapter.

### 3.2. Provider Abstraction

Implement a provider adapter named `GitHubCopilotProviderAdapter` that conforms to the existing `AIProviderAdapter` contract.

The adapter must:

- Identify itself using the stable provider ID `github-copilot`.
- Report connection and authentication status.
- Retrieve the available models.
- Validate the selected model.
- Create, resume, and end supported agent sessions.
- Stream messages and execution events.
- Register approved Animation Studio tools.
- Propagate cancellation requests.
- Normalize SDK events and errors into the application's existing AI event format.

The rest of Animation Studio must not depend directly on SDK-specific data structures.

### 3.3. Separation of Responsibilities

Keep the following responsibilities separate:

- `GitHubCopilotProviderAdapter`: provider-specific integration.
- `GitHubCopilotRuntimeService`: SDK client and runtime lifecycle.
- `GitHubCopilotAuthenticationService`: connection state and authentication workflow.
- `GitHubCopilotModelService`: model discovery and selection.
- `GitHubCopilotSessionService`: session lifecycle and conversation mapping.
- `AIToolRegistry`: approved tool definitions.
- `AIConversationService`: application-level conversation persistence.
- `SecureCredentialService`: credential storage and access.

These are logical responsibilities; the implementation may consolidate services when that better matches the existing codebase.

## 4. Authentication and Account Management

### 4.1. Connection Flow

Add GitHub Copilot to the existing AI provider configuration interface.

The user must be able to:

1. Open AI provider settings.
2. Select GitHub Copilot.
3. Start the supported GitHub authentication flow.
4. Complete authentication using the supported browser, device authorization, or CLI-backed workflow.
5. Return to Animation Studio and see the resulting connection status.
6. Load the models available to the authenticated account.

Use the authentication mechanism documented by the selected SDK version.

If authentication requires the Copilot CLI, use the SDK's supported CLI integration and lifecycle management. Do not assume that an arbitrary GitHub access token automatically grants Copilot entitlement.

If the SDK supports a GitHub OAuth App flow appropriate for this application, evaluate it as an alternative. Do not create an OAuth application or request scopes without documenting the required permissions and registration process.

### 4.2. Authentication States

Represent at least the following states:

- Not connected.
- Connecting.
- Connected.
- Authentication required.
- Missing Copilot entitlement.
- Connection error.
- Disconnected.

Display actionable error messages when authentication fails or the account does not have access to Copilot Chat or the selected model.

Do not repeatedly prompt the user to authenticate when a valid session already exists.

### 4.3. Disconnecting

Provide a Disconnect action in provider settings.

Disconnecting must:

- Stop active provider sessions.
- Prevent new requests from using the disconnected account.
- Clear application-managed session references and cached account-specific model data.
- Revoke credentials only when supported and explicitly intended by the selected authentication mechanism.
- Avoid deleting unrelated GitHub CLI credentials or credentials used by other applications.

Clearly distinguish disconnecting Animation Studio from signing out of GitHub globally.

## 5. Model Discovery and Selection

### 5.1. Dynamic Discovery

Retrieve the models currently available to the authenticated Copilot account using the SDK's supported model-discovery functionality.

Do not hardcode a fixed list of model names as the primary source of truth.

The model list must reflect the current account's entitlement and the provider's supported capabilities.

Each model entry should include, where available:

- Stable model identifier.
- Display name.
- Availability status.
- Supported capabilities.
- Context-window information.
- Multimodal or image-input support.
- Relevant capability metadata required by the agent workspace.

Do not fabricate missing model capabilities or assume that every model supports every feature.

### 5.2. Model Selector

Integrate the discovered models into the existing model selector.

The selector must:

- Display the model name and provider.
- Show the currently selected model.
- Support refreshing the model list.
- Preserve the selection when it remains valid.
- Choose a valid fallback only when the existing application policy allows it.
- Explain when a previously selected model is no longer available.

The model selector must not display unavailable models as selectable.

### 5.3. Model Capabilities

Use model capability metadata to determine whether to enable supported options, such as image input or effort controls.

If a model does not support an option, hide or disable that option and explain the limitation where appropriate.

Do not infer that model selection guarantees access to a feature that the account or SDK does not support.

## 6. Agent Workspace Integration

### 6.1. Chat Experience

The provider must work with the existing AI workspace.

Support:

- Sending user messages.
- Streaming assistant responses.
- Displaying formatted responses.
- Showing the selected model.
- Showing agent activity and tool execution status.
- Stopping an active request.
- Displaying recoverable and non-recoverable errors.
- Resuming supported sessions.

Do not introduce a separate chat interface exclusively for GitHub Copilot.

### 6.2. Streaming Events

Translate SDK events into the application's standard event model.

Handle, where supported:

- Assistant response started.
- Text content received.
- Tool call requested.
- Tool execution started.
- Tool execution completed.
- Tool execution failed.
- Agent turn completed.
- Session state changed.
- Request cancelled.
- Provider error occurred.

The UI must not claim that a tool succeeded until the corresponding execution result confirms success.

### 6.3. Effort and Agent Options

Expose supported model effort or reasoning controls only when the SDK and selected model provide them.

Use the existing workspace option selector where possible.

The application must not send undocumented parameters or assume that options accepted by another provider are compatible with Copilot.

## 7. Animation Studio Tool Integration

### 7.1. Custom Tools Only

Register the approved Animation Studio tools through the SDK's supported custom-tool interface.

The provider must use the internal editing API specified in HU_00015 for all project modifications.

The following categories should be exposed incrementally as the corresponding editing API capabilities become available:

- Project and editor context inspection.
- Scene inspection and management.
- Frame inspection and management.
- Layer inspection and management.
- Drawing creation and modification.
- Supported brush and style operations.
- Bézier curve operations.
- Supported transformations.
- Preview rendering.
- Saving through the normal project persistence service.

### 7.2. Restrict Built-in Tools

The SDK may expose its own first-party tools by default. Explicitly configure the SDK so the application does not unintentionally grant unrestricted access to filesystem, terminal, or other general-purpose tools.

Disable built-in tools that are not needed.

Only enable tools explicitly approved for Animation Studio's use case.

The initial integration must not allow the agent to execute arbitrary shell commands, write arbitrary project files, run arbitrary scripts, or bypass the internal editing API.

### 7.3. Tool Execution and Approval

Before a tool call is executed:

1. Validate the tool name and arguments.
2. Validate the target project and object identifiers.
3. Check the required permission level.
4. Request user approval when required by the application's policy.
5. Execute the operation through the appropriate service.
6. Return a structured result to the agent.
7. Publish the execution status to the workspace.

Read-only operations should not require confirmation unless the user or application policy requires it.

Destructive operations and operations with a broad impact must require explicit approval.

The approval mechanism must be enforced by Animation Studio, not delegated entirely to model instructions.

### 7.4. Context Injection

Provide relevant project context to the agent, including:

- Project metadata.
- Active scene, frame, and layer.
- Relevant drawing and asset metadata.
- Available editing operations.
- Current operation results.
- Rendered previews where supported.

Use targeted context instead of sending the entire project on every request.

Do not include credential values, unrelated filesystem contents, or unrelated project data in model prompts.

## 8. Session and Conversation Management

Keep application-level conversations separate from SDK-specific session identifiers.

Where supported by the SDK, associate a Copilot session with an Animation Studio conversation.

Support:

- Creating a new conversation.
- Continuing an existing conversation.
- Resuming a compatible SDK session.
- Cancelling an active session or turn.
- Ending a session.
- Handling invalid or expired sessions.
- Starting a fresh session when the previous session cannot be resumed.

Persist only the session metadata and conversation information needed by Animation Studio.

Do not assume that an SDK session can be resumed after every application restart. Implement and test the supported persistence behavior for the selected SDK version.

## 9. Runtime Lifecycle and Electron Architecture

### 9.1. Runtime Management

Manage the SDK and Copilot CLI lifecycle through a dedicated runtime service.

The service must:

- Initialize the SDK lazily when GitHub Copilot is first used.
- Reuse a healthy runtime when appropriate.
- Avoid spawning duplicate CLI processes.
- Detect startup failures.
- Stop active sessions on shutdown.
- Release resources and terminate managed child processes cleanly.
- Recover from unexpected runtime termination.

### 9.2. Process Boundaries

Keep privileged operations out of renderer code.

The renderer must communicate through narrow, typed application interfaces. The main process or a dedicated trusted service must own the provider runtime, credential access, and privileged operations.

Maintain the existing Electron security configuration:

- `contextIsolation: true`.
- `nodeIntegration: false`.
- Explicitly validated IPC messages.
- No arbitrary IPC channel invocation from the renderer.

Do not assume that the SDK's default runtime placement is automatically suitable for Electron. Verify its process requirements and choose a compatible, isolated execution arrangement.

### 9.3. Packaging

Verify that the Copilot SDK and its required CLI runtime work in packaged macOS builds, not only in development mode.

The implementation must address:

- Application resource paths.
- Bundled runtime or supported CLI discovery.
- Executable permissions.
- Code signing and notarization implications.
- Process termination.
- Application updates.
- Platform-specific failures.

Do not depend on a development-only path or an undocumented local CLI installation.

If a supported packaged setup cannot be established, document the limitation and provide a clear connection/setup error instead of silently failing.

## 10. Credential Security and Privacy

- Never store credentials in renderer state, local storage, conversation history, logs, or project files.
- Use the operating system's secure credential storage or the existing `SecureCredentialService`.
- Prefer the SDK's supported authentication and credential mechanisms.
- Never extract or copy private tokens from another application's internal files using undocumented techniques.
- Do not log authorization headers, access tokens, refresh tokens, or secret values.
- Do not send credentials to the model as prompt context.
- Clearly communicate that prompts, attachments, and relevant project context may be sent to the selected provider.
- Respect the user's account permissions, organization policies, and applicable Copilot terms.

Authentication diagnostics must report useful error categories without exposing secret data.

## 11. Usage, Limits, and Errors

Handle:

- Network failures.
- Authentication failures.
- Missing Copilot entitlement.
- Model unavailability.
- Rate limits and usage limits.
- Unsupported model capabilities.
- SDK startup failures.
- Tool execution errors.
- Cancelled requests.
- Unexpected CLI termination.

Display clear, actionable messages.

Do not automatically retry non-idempotent editing operations after an ambiguous failure. Use operation identifiers or other deduplication mechanisms when supported by the editing API.

Where the SDK exposes usage or budget information, display it only when the information is reliable and documented.

Do not promise unlimited usage or assume that all models are included in every Copilot plan.

## 12. Configuration

Expose the provider through the existing AI settings.

The user must be able to:

- Connect or disconnect GitHub Copilot.
- View connection status.
- Refresh available models.
- Select a default model.
- View relevant authentication and connection errors.
- Inspect the integration's supported capabilities.

Avoid introducing provider-specific settings that duplicate existing global AI workspace options.

Persist non-sensitive preferences through the application's normal settings service.

## 13. Testing Requirements

### 13.1. Unit Tests

Test:

- Provider registration.
- Authentication state mapping.
- Model list normalization.
- Model selection validation.
- SDK event normalization.
- Error mapping.
- Tool registration and filtering.
- Cancellation behavior.
- Session lifecycle handling.

Use mocks for SDK-dependent unit tests.

### 13.2. Integration Tests

Test the real SDK integration with a valid GitHub Copilot account in a controlled environment.

Verify:

- Successful connection.
- Model discovery.
- Selecting and using a model.
- Streaming a response.
- Registering and invoking a custom Animation Studio tool.
- Receiving structured tool results.
- Cancelling a running request.
- Recovering from an authentication or runtime error.

Do not require real credentials in automated pull-request tests.

### 13.3. End-to-End Acceptance Scenario

Using a real authorized Copilot account:

1. Open Animation Studio.
2. Connect GitHub Copilot.
3. Load the available models.
4. Select a model.
5. Open an animation project.
6. Ask the agent to inspect the active scene.
7. Ask the agent to create a frame and add a simple supported drawing.
8. Review the proposed operations and approve any required changes.
9. Verify that the frame and drawing appear in the editor.
10. Request a preview.
11. Undo the changes using the normal editing history.
12. Verify that the project remains consistent after saving and reopening.

The test must use actual editing operations rather than simulated UI success messages.

## 14. Implementation Phases

### Phase 1 — SDK Feasibility and Foundation

- Inspect the current official SDK documentation and stable release.
- Verify Electron compatibility and packaged macOS runtime requirements.
- Add the SDK dependency.
- Implement the runtime lifecycle service.
- Register the GitHub Copilot provider.
- Establish authentication state handling.
- Document any SDK limitations.

### Phase 2 — Authentication and Models

- Implement the supported authentication flow.
- Add connection and disconnection UI.
- Implement model discovery.
- Connect model selection to the existing workspace.
- Add error handling for account and model availability.

### Phase 3 — Chat and Agent Runtime

- Implement streaming.
- Connect session lifecycle and conversation handling.
- Implement cancellation.
- Normalize SDK events.
- Display progress and errors in the existing workspace.

### Phase 4 — Editing Tools

- Register approved tools from the internal editing API.
- Restrict built-in SDK tools.
- Implement approval and permission handling.
- Execute a complete editing workflow.
- Render and inspect the resulting preview.

### Phase 5 — Packaging and Hardening

- Test packaged macOS builds.
- Test runtime shutdown and recovery.
- Complete security, privacy, and regression tests.
- Document setup, authentication, known limitations, and troubleshooting.

## 15. Acceptance Criteria

- GitHub Copilot appears as a provider in Animation Studio.
- The user can authenticate through a supported mechanism.
- Available models are discovered dynamically.
- The user can select and use a model.
- Assistant messages stream into the existing chat interface.
- Tool calls and execution progress are visible.
- The agent can invoke approved Animation Studio tools.
- Project modifications are performed through HU_00015's internal editing API.
- Unsupported and destructive operations are handled according to the application's permission policy.
- Unrestricted built-in filesystem and terminal tools are disabled unless separately approved in a future specification.
- Credentials are not exposed to renderer code, logs, prompts, or project files.
- Active operations can be cancelled.
- The provider runtime shuts down cleanly.
- The integration works in a packaged macOS build.
- A real end-to-end project editing workflow passes.
- Existing providers and AI workspace functionality remain operational.

## 16. Out of Scope

- Reimplementing GitHub Copilot's proprietary or internal protocols.
- Copying OpenCode's source code or provider implementation.
- Using undocumented endpoints or reverse-engineering private authentication mechanisms.
- Circumventing Copilot subscriptions, entitlements, quotas, or organization policies.
- Providing unrestricted terminal or filesystem access to the agent.
- Implementing other AI providers.
- Implementing the entire editing API specified in HU_00015.
- Guaranteeing that every Copilot model supports every tool or multimodal capability.

## 17. Definition of Done

The feature is complete when GitHub Copilot can be connected and used as a provider in Animation Studio, models can be discovered and selected, streamed responses and tool calls work, and an authenticated agent can successfully modify an animation project through approved internal editing operations.

The integration must be documented, tested, secure, and functional in the packaged macOS application.
