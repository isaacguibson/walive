# HU_00015 — Editor Integration API and Agent Tooling

## 1. Objective

Ensure that Animation Studio exposes a complete, consistent, and secure set of programmatic capabilities that allows AI agents to inspect, create, modify, and manage animation projects.

Before implementing new functionality, the development team must inspect the existing codebase to identify editing services, application APIs, agent tools, MCP integrations, and other mechanisms that already provide these capabilities.

The implementation must reuse and extend existing functionality wherever possible, creating new components only when necessary.

The final result must allow an AI agent to interact with the editor as an actual assistant, performing editing operations and inspecting their results rather than merely providing instructions to the user.

## 2. Mandatory Codebase Audit

Before making architectural changes, inspect the entire relevant application codebase.

Identify and document existing implementations related to:

- Project and scene management.
- Frame creation, duplication, deletion, and reordering.
- Layer management.
- Drawing and brush operations.
- Bézier curves.
- Selection and transformations.
- Style modification.
- Rendering and previews.
- Save, undo, and redo.
- Agent tool registration and execution.
- MCP clients, servers, and tool adapters.
- Existing IPC channels and preload APIs.
- Existing command registries, editing services, and event systems.

For each capability, classify its current state as:

- **Implemented:** working functionality already exists.
- **Partially implemented:** functionality exists but has missing behavior or limitations.
- **Missing:** no suitable implementation exists.
- **Unknown:** available evidence is insufficient to establish its status.

Inspect the actual implementation and tests where available. Do not consider a feature implemented merely because it appears in a specification, interface, placeholder, or TODO comment.

Produce a capability inventory before starting implementation.

The inventory must identify:

- Existing implementation and its location in the codebase.
- Current public interface or invocation mechanism.
- Whether an agent can use it today.
- Missing behavior or limitations.
- Recommended action: reuse, extend, refactor, or implement.

Do not rewrite or replace existing working functionality solely to conform to a proposed architecture.

## 3. Architecture and Integration Strategy

Establish or consolidate a shared, typed integration layer between the editor and its AI agents.

The implementation must follow these principles:

- Reuse existing editing services whenever possible.
- Keep editor functionality independent of specific AI providers.
- Make the same underlying editing operations available to the UI and approved agent tools.
- Reuse existing MCP integrations where appropriate.
- Avoid creating multiple tools that perform the same operation through different implementations.
- Keep project data and editing state under the control of the application.
- Use explicit, validated commands rather than simulated mouse and keyboard interactions.
- Do not expose arbitrary code execution as a substitute for missing editor capabilities.

If a suitable internal API already exists, extend it instead of creating a parallel API.

If agent tools or MCP tools already exist, reuse their contracts where practical and document any compatibility changes.

## 4. Required Capability Categories

The audit must establish whether each capability below is already available and accessible to agents. Implement or complete only the missing parts required to achieve the intended workflows.

### 4.1. Project and Editor Context

The agent must be able to:

- Identify the active project.
- Inspect project metadata and canvas dimensions.
- List and inspect scenes.
- Identify the active scene.
- Inspect frames and their ordering.
- Identify the active frame.
- Inspect layers and their ordering.
- Identify the active layer.
- Retrieve relevant brush and editor settings.
- Discover which editing operations are supported.

Every operation that modifies content must identify its target explicitly or use a validated editor context. The API must never silently target an unintended scene, frame, or layer.

### 4.2. Scene Operations

Where supported by the existing application, expose:

- Create a scene.
- Inspect a scene.
- Rename a scene.
- Select a scene.
- Duplicate a scene.
- Delete a scene.

Destructive operations must follow the existing approval policy.

Do not implement operations that the current project model cannot support safely without first addressing the underlying limitation.

### 4.3. Frame Operations

Expose:

- List and inspect frames.
- Create an empty frame.
- Duplicate a frame.
- Copy supported frame content.
- Delete a frame.
- Reorder frames.
- Update supported timing properties.
- Retrieve relevant frame content and metadata.

The agent must be able to create and modify animation sequences without relying on UI automation.

### 4.4. Layer Operations

Expose supported operations for:

- Creating layers.
- Inspecting layers.
- Renaming layers.
- Reordering layers.
- Duplicating layers.
- Deleting layers.
- Changing supported layer properties.

Preserve unrelated layers and their content.

### 4.5. Drawing and Artwork Operations

Provide programmatic drawing capabilities through the existing rendering and drawing architecture.

The agent must be able to:

- Create artwork on a specified frame and layer.
- Draw using supported brush types.
- Provide stroke geometry as structured point data.
- Specify supported color, size, opacity, and other brush properties.
- Inspect drawing metadata.
- Modify supported properties of existing artwork.
- Remove selected drawing elements.
- Apply supported transformations.

Reuse the existing drawing engine and brush implementations. Do not create a second drawing engine specifically for agents.

Clearly distinguish operations that modify existing artwork from operations that only change the settings used for future strokes.

### 4.6. Visual Style Modification

The agent must be able to inspect supported visual properties and apply changes through explicit operations.

Examples include:

- Changing stroke color.
- Changing opacity or size.
- Applying supported brush types.
- Modifying supported drawing properties.
- Transforming existing artwork.
- Regenerating artwork when a suitable regeneration capability exists.

A change to brush settings must not be represented as a change to existing artwork unless the artwork itself was actually modified.

If a requested style transformation is unsupported, the API must report the limitation rather than returning a misleading success result.

### 4.7. Bézier Curves and Selection

Where the corresponding editor features are implemented, expose programmatic operations for:

- Creating and editing Bézier curves.
- Updating anchor points and handles.
- Inspecting curve geometry.
- Selecting supported artwork or regions.
- Moving, resizing, or transforming selected content.
- Committing or cancelling supported transformations.

Preserve the editor's existing geometry model, transparency, and undo/redo behavior.

### 4.8. Preview and Rendering

The agent must be able to inspect the visual results of its work.

Reuse existing rendering services to provide, where supported:

- A preview of a frame.
- A preview of a scene or frame sequence.
- Relevant render metadata.
- Structured rendering errors.

Previews must not modify project content and should follow the same rendering rules as the editor and export pipeline.

If previews are already exposed through an agent or MCP tool, reuse that implementation.

### 4.9. Persistence and History

Ensure that agent-driven changes use the application's normal persistence mechanisms.

The integration must support, where available:

- Saving changes.
- Reporting unsaved changes.
- Undoing agent operations.
- Redoing agent operations.
- Grouping related operations into a coherent history entry.
- Reporting operation results and failures.

Do not bypass the existing history system or introduce a separate history that conflicts with the editor.

## 5. Agent Tool Registry

Audit and reuse any existing tool registry.

If no suitable registry exists, implement a centralized mechanism for defining and exposing approved editor operations to agents.

Each tool must provide:

- A stable identifier.
- A description of its purpose.
- A typed input schema.
- Validation rules.
- Required permissions.
- A structured result schema.
- Relevant error codes.
- An indication of whether the operation changes project content.
- An indication of whether the operation is destructive.
- Cancellation behavior where applicable.

Tool descriptions must be explicit enough for a model to understand when to use each operation and what its limitations are.

Do not expose duplicate tools that have different names but perform the same underlying operation.

## 6. MCP Compatibility

Inspect existing MCP integration before adding any MCP-related infrastructure.

If an MCP server, client, or tool adapter already exposes editor functionality:

- Preserve its working functionality.
- Reuse its existing contracts where appropriate.
- Extend the available tools to cover missing editor capabilities.
- Keep MCP tool execution connected to the same underlying editing services.
- Avoid introducing a second implementation of editing operations.

If MCP integration is absent, do not make MCP a prerequisite for the internal editing API. Establish the shared editing services and tool contracts first, so MCP can be connected through an adapter when needed.

All MCP-exposed operations must follow the same validation, authorization, project-boundary, and error-handling rules as other agent tools.

MCP must not create an unrestricted alternative pathway into Electron internals.

## 7. Command Execution and Consistency

Use a shared command execution mechanism if one already exists. Otherwise, introduce one where necessary.

Requirements:

- Validate every request.
- Validate project, scene, frame, and layer identifiers.
- Return structured results.
- Report failures without claiming success.
- Preserve unrelated content.
- Avoid duplicate execution after ambiguous failures where deduplication is possible.
- Support cancellation for long-running operations where appropriate.
- Group logically related changes into coherent undo steps.
- Roll back failed operations when the underlying operations support safe rollback.

Batch execution may be added or extended where it materially enables complete agent workflows. Do not create a new batch framework if an adequate implementation already exists.

## 8. Security and Electron Boundaries

Preserve the application's existing Electron security model.

- Keep `contextIsolation: true`.
- Keep `nodeIntegration: false`.
- Do not expose unrestricted filesystem APIs to agents.
- Do not permit arbitrary shell commands or dynamic JavaScript/TypeScript execution.
- Validate IPC requests at the privileged boundary.
- Expose only explicitly approved capabilities.
- Keep credentials out of project data, prompts, logs, and tool results.
- Require approval for destructive actions according to the application's agent policy.

If the existing implementation violates these requirements, document and remediate the relevant issue without unnecessarily redesigning unrelated components.

## 9. Implementation Plan

### Phase 1 — Audit and Capability Inventory

- Inspect the actual codebase.
- Identify existing editor APIs, services, commands, agent tools, and MCP integrations.
- Test existing capabilities where feasible.
- Produce the capability inventory.
- Identify the minimum changes needed to enable agent-driven editing.

Do not begin by recreating every operation listed in this specification.

### Phase 2 — Consolidate and Complete the Integration Layer

- Reuse existing editing services.
- Refactor UI-coupled functionality only where necessary.
- Establish or extend typed command interfaces.
- Complete missing context queries and capability discovery.
- Ensure UI and agent operations share the same underlying behavior.

### Phase 3 — Complete Missing Agent Capabilities

Implement the missing operations needed to support the required workflows, prioritizing:

1. Inspect project, scene, frame, and layer state.
2. Create and duplicate frames.
3. Create or modify supported artwork.
4. Apply supported style changes.
5. Render and inspect previews.
6. Save changes and integrate with undo/redo.

Extend scene, layer, curve, and transformation operations based on the audit findings and existing application support.

### Phase 4 — Connect Existing Agent and MCP Infrastructure

- Reuse existing agent-tool registration.
- Reuse existing MCP tools and adapters where possible.
- Expose newly implemented capabilities through the established mechanisms.
- Verify that every invocation reaches the shared editing services.
- Remove or consolidate redundant pathways when safe.

### Phase 5 — Validation

- Test the UI after API-driven modifications.
- Test saving and reopening projects.
- Test undo/redo.
- Test invalid identifiers and malformed requests.
- Test failure handling and cancellation.
- Test that operations cannot modify unrelated scenes, frames, or layers.
- Verify that existing agent and MCP workflows continue working.

## 10. Required End-to-End Acceptance Scenario

Using an agent connected through an existing or supported provider:

1. Open an existing animation project.
2. Ask the agent to inspect the active scene.
3. Ask it to create a new frame.
4. Ask it to create a simple drawing using a supported brush.
5. Ask it to modify a supported visual property of that drawing.
6. Request a rendered preview.
7. Inspect the result in the actual editor.
8. Save the project.
9. Undo the agent's changes using the normal history mechanism.
10. Redo the changes.
11. Reopen the project and verify that the saved result is preserved.

The workflow must use actual programmatic editing operations, not mocked success responses or simulated mouse interactions.

If any step is unsupported by the existing editor, implement the missing capability or document the precise limitation and its dependency.

## 11. Acceptance Criteria

- A documented capability inventory exists.
- Existing implementations have been inspected before new components are created.
- Existing working editing services and MCP integrations are reused wherever practical.
- No unnecessary duplicate editing APIs or agent tools are introduced.
- The agent can inspect project and editor state through structured operations.
- The agent can create frames and modify artwork through supported programmatic operations.
- The agent can inspect rendered results.
- Changes persist after saving and reopening the project.
- Supported operations integrate with undo/redo.
- Invalid requests fail safely.
- Agent operations respect project boundaries and permissions.
- The existing UI and agent interfaces remain consistent.
- Existing provider integrations continue working.
- The required end-to-end workflow passes, or any remaining blocker is explicitly documented.

## 12. Definition of Done

This requirement is complete when the actual codebase has been audited, existing functionality has been reused or extended appropriately, and the missing integration capabilities have been implemented and tested.

The final implementation must enable a real AI agent to inspect and edit animation projects through approved programmatic operations, with observable results, persistence, and appropriate safeguards.

The implementation report must list:

- Capabilities reused without changes.
- Capabilities extended.
- New capabilities implemented.
- Existing MCP and agent integrations reused.
- Known limitations and remaining dependencies.
