# HU_00002 — Application Home

**Status:** Proposed
**Priority:** High
**Type:** Core Feature / User Interface

---

# 1. Overview

The Animation Studio must provide an application home screen displayed when the application starts without an active project.

The Application Home is the entry point for the project-based workflow.

It must allow users to:

* Create a new project.
* Open an existing project.
* Access recently opened projects.
* Remove projects from the recent-project list.
* Identify unavailable recent projects.
* Open a project directly from the recent-project list.

The Application Home must use the Project Management functionality defined in `HU_00001`.

The application is implemented using **Electron and TypeScript**.

---

# 2. Goals

The implementation must provide a clean and reliable starting point for the Animation Studio.

The following goals are required:

1. Display the Application Home when no project is open.
2. Provide a New Project action.
3. Provide an Open Project action.
4. Display recently opened projects.
5. Allow users to open a recent project.
6. Clearly indicate unavailable recent projects.
7. Allow unavailable projects to be removed from the recent-project list.
8. Keep the Application Home independent from the project editor.
9. Use the Project Management API instead of accessing the filesystem directly from the UI.
10. Follow Electron security best practices.
11. Provide a foundation for future application-level features such as project templates and AI integrations.

---

# 3. Non-Goals

The following features are outside the scope of this user story:

* Scene editing.
* Canvas implementation.
* Timeline implementation.

* MCP integration.
* Project templates.

These features may be implemented in future user stories.

# 4. Application Startup Behavior

When the Electron application starts, it must determine whether a project should be opened automatically.

The initial implementation must follow this behavior:

```text
Application starts
       │
       ▼
Is a project explicitly being opened?
       │
       ├── Yes ──> Open Project
       │
       └── No
            │
            ▼
       Application Home
```

The application must not automatically open the most recently used project unless this behavior is explicitly enabled by a future application setting.

The default behavior is to display the Application Home.

# 6. Application Home States

The Application Home must support the following states.

## 6.1 No Recent Projects

When no recent projects exist, the interface should clearly communicate that the user has not opened any projects yet.

Example:

```text
No recent projects

Create a new project or open an existing project to get started.

[ Create New Project ]
[ Open Existing Project ]
```

---

## 6.2 Recent Projects Available

When recent projects exist, they must be displayed in a list or grid.

Each entry must display at least:

* Project name.
* Last opened date/time.
* Project location.

The UI may display additional information such as:

* Project thumbnail.
* Project dimensions.
* Frame rate.
* Number of scenes.

Additional information must not be required by this user story.

---

## 6.3 Unavailable Project

If a recent project is no longer accessible, it must remain visible but clearly marked as unavailable.

Example:

```text
My Animation
Unavailable

The project could not be found at its previous location.

[ Locate ] [ Remove ]
```

The initial implementation must support at least the `Remove` action.

A `Locate` action may be implemented if practical but is not mandatory for this user story.

---

# 7. New Project Workflow

Selecting **Create New Project** must initiate the project creation workflow defined by `HU_00001`.

The UI must request at least:

* Project name.
* Project location.

Example:

```text
Create New Project

Project Name:
[ My Animation                 ]

Location:
[ ~/Documents/Animation Studio ]

                 [ Cancel ] [ Create ]
```

The Application Home must not implement project creation logic itself.

The flow must call the Project Management API.

---

# 8. New Project Validation

The UI must provide appropriate feedback when project creation fails.

Examples include:

```text
A project with this name already exists.
```

```text
The selected location is not writable.
```

```text
Unable to create the project.
```

The UI must not expose raw filesystem errors or stack traces to the user.

Detailed technical errors may be logged internally.

---

# 9. Open Existing Project

Selecting **Open Existing Project** must open a native operating-system directory selection dialog.

The Electron main process must be responsible for interacting with native filesystem dialogs.

The renderer process must not directly access Node.js filesystem APIs.

The selected directory must be passed to the Project Management layer for validation.

Flow:

```text
User
 │
 ▼
Application Home
 │
 ▼
Open Existing Project
 │
 ▼
Electron Main Process
 │
 ▼
Native Directory Dialog
 │
 ▼
Selected Directory
 │
 ▼
Project Management API
 │
 ▼
Project Validation
 │
 ├── Valid ────────> Open Project
 │
 └── Invalid ──────> Display Error
```

---

# 10. Recent Projects

The Application Home must obtain recent projects through the application-level project registry defined by `HU_00001`.

The UI must not read the recent-project storage directly.

The preferred architecture is:

```text
Application Home
       │
       ▼
Project Management API
       │
       ▼
Recent Project Repository
       │
       ▼
Application State Storage
```

The exact storage implementation may be JSON, SQLite, or another local persistence mechanism.

The UI must remain independent from that implementation.

---

# 11. Recent Project Ordering

Recent projects must be ordered by:

```text
lastOpenedAt DESC
```

The most recently opened project must appear first.

When a project is opened successfully, its `lastOpenedAt` value must be updated.

The same project must not appear multiple times in the recent-project list.

Project identity must be determined using the project ID whenever possible rather than only the filesystem path.

---

# 12. Recent Project Removal

The user must be able to remove a project from the recent-project list.

Removing a project from the recent-project list must:

* Remove only the application-level reference.
* Not delete the project directory.
* Not delete project files.
* Not modify the project metadata.

The action should be clearly communicated to the user.

Example:

```text
Remove "My Animation" from recent projects?

This will not delete the project from your computer.

[ Cancel ] [ Remove ]
```

For unavailable projects, the confirmation may be simplified.

---

# 13. Project Opening

When a project is successfully opened:

```text
Application Home
       │
       ▼
Project Management
       │
       ▼
Project Loaded
       │
       ▼
Project Editor
```

The Application Home must no longer be visible as the primary application view.

The project editor itself is outside the scope of this user story.

A temporary placeholder/editor view may be used until the actual editor is implemented.

---

# 14. Closing a Project

When the current project is closed, the application must return to the Application Home.

Expected flow:

```text
Project Editor
      │
      │ Close Project
      ▼
Project Management
      │
      ▼
Application Home
```

The Application Home must refresh its recent-project list after returning from the project editor.

Project closing behavior must be implemented through the Project Management layer.

---

# 15. Electron Architecture

The application must follow Electron's process separation model.

The initial architecture must be:

```text
┌──────────────────────────────────────┐
│ Electron Main Process                │
│                                      │
│ - Application lifecycle              │
│ - Native dialogs                     │
│ - Window management                  │
│ - Filesystem access                  │
│ - Project management                 │
│ - Application state                  │
└─────────────────┬────────────────────┘
                  │
                  │ IPC
                  │
┌─────────────────▼────────────────────┐
│ Renderer Process                     │
│                                      │
│ - Application Home UI                │
│ - User interactions                  │
│ - Presentation state                 │
│ - UI components                      │
└──────────────────────────────────────┘
```

The renderer must not have unrestricted Node.js access.

---

# 16. Electron Security Requirements

The application must use secure Electron defaults.

The renderer process must not have direct access to Node.js APIs.

The following architecture is required:

```text
Renderer
   │
   ▼
Preload API
   │
   ▼
IPC
   │
   ▼
Main Process
```

The application should use:

```text
contextIsolation: true
```

The application should not enable:

```text
nodeIntegration: true
```

The preload script must expose only the minimum required API to the renderer.

---

# 17. Preload API

The renderer should interact with project functionality through a typed API exposed by the preload layer.

Example conceptual API:

```typescript
interface ProjectAPI {
    createProject(
        name: string,
        location: string
    ): Promise<ProjectMetadata>;

    openProject(
        path: string
    ): Promise<ProjectMetadata>;

    getRecentProjects(): Promise<RecentProject[]>;

    removeRecentProject(
        projectId: string
    ): Promise<void>;

    closeProject(): Promise<void>;
}
```

The exact API may evolve as the application grows.

The renderer must not directly manipulate project files.

---

# 18. TypeScript Requirements

The project must use TypeScript with strict type checking enabled.

Shared models should be defined independently from UI components.

Example:

```typescript
interface ProjectMetadata {
    formatVersion: number;
    id: string;
    name: string;
    createdAt: string;
    updatedAt: string;
}

interface RecentProject {
    projectId: string;
    name: string;
    path: string;
    lastOpenedAt: string;
    available: boolean;
}
```

Types used by IPC should be explicitly defined.

The implementation must avoid using `any` for project-related APIs unless technically unavoidable.

---

# 19. IPC Design

IPC channels must be explicit and typed.

Conceptually:

```text
project:create
project:open
project:close
project:get-recent
project:remove-recent
```

The application must avoid exposing a generic unrestricted IPC mechanism such as:

```text
execute(command, arbitraryArguments)
```

IPC operations must be limited to known application operations.

---

# 20. Error Handling

The Application Home must gracefully handle failures.

Possible errors include:

* Project creation failure.
* Project opening failure.
* Invalid project.
* Missing project directory.
* Permission denied.
* Project format not supported.
* Application state read failure.
* Application state write failure.
* IPC communication failure.

Errors shown to the user must be understandable.

Example:

```text
Unable to open project.

The selected folder is not a valid Animation Studio project.
```

Technical details may be logged separately.

---

# 21. Loading States

The UI must provide feedback during asynchronous operations.

Examples:

```text
Creating project...
```

```text
Opening project...
```

```text
Loading recent projects...
```

Actions that are currently executing must not be triggered repeatedly.

For example, clicking `Create` multiple times must not create multiple projects.

# 27. Platform Considerations

The application must support Electron's target desktop platforms.

The Application Home must not rely on platform-specific filesystem assumptions.

Filesystem paths must be handled using Electron/Node.js path utilities rather than manually concatenated strings.

The implementation must account for platform-specific path separators.

For example, the application must not assume:

```text
/
```

is always the filesystem separator.

# 33. Architectural Principle

The Application Home must follow this principle:

> **The Application Home is an entry point into the user's projects, not the owner of project data.**

The UI is responsible for presenting project-related actions and state.

The Project Management layer is responsible for project operations.

The Electron main process is responsible for privileged desktop operations.

The renderer process is responsible for presentation and user interaction.

The filesystem remains the persistent source of truth for project data.
