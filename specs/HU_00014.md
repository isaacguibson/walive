# HU_00014 — AI Agent Workspace and Provider Integration

## 1. Objective

Redesign and implement the application's existing AI Chat area as a fully functional AI Agent Workspace integrated into the animation editor.

The experience should be inspired by agentic coding tools such as OpenCode, adapted specifically for a 2D drawing and animation application.

Users must be able to configure AI providers, select models, submit natural-language instructions, attach files, inspect agent activity, and allow AI agents to perform supported operations on the current animation project through controlled application tools.

The system must support an extensible architecture for multiple AI providers, model capabilities, effort levels, tool execution, and MCP integrations.

Provider configuration, model selection, credentials, and MCP server configuration must be manageable entirely through the application's UI.

The first implementation must deliver a functional agent workflow rather than a visual-only chat placeholder.

## 2. Core Principles

The implementation must follow these principles:

1. **Provider independence:** AI functionality must not depend on a single provider or model.
2. **Explicit configuration:** Users configure providers and integrations within the application.
3. **Agentic execution:** Agents can inspect project state, plan tasks, invoke tools, observe results, and continue working within configured limits.
4. **Controlled access:** Agents can modify the project only through explicitly authorized tools and application services.
5. **User visibility:** Agent activity, tool execution, errors, and pending approvals must be visible.
6. **User control:** Users can stop an active task and approve or reject operations that require confirmation.
7. **Project awareness:** The agent must understand the active project, scene, frame, layers, and supported artwork types.
8. **Extensibility:** New providers, models, tools, and MCP servers can be added without redesigning the chat UI.
9. **Security:** Credentials and external integrations must not expose unrestricted filesystem access or arbitrary execution inside Electron.
10. **Graceful limitations:** The application must clearly explain unsupported models, unavailable capabilities, missing credentials, and failed tool operations.

## 3. AI Agent Workspace UI

Replace the current AI Chat placeholder with a functional AI Agent Workspace.

Retain the application's existing editor layout and integrate the workspace into the right-side panel, replacing the current chat placeholder or tab content.

The workspace must have three main areas:

- Conversation history.
- Agent activity and tool execution details.
- Message composer at the bottom.

### 3.1 Conversation area

Display user messages and assistant responses in a readable conversational layout.

Support:

- Text and Markdown responses.
- Code blocks where relevant.
- Tool execution status.
- Loading and reasoning status indicators where supported by the provider.
- Error messages and retry actions.
- User approval requests.
- Task completion and cancellation states.

Do not expose hidden chain-of-thought or private internal model reasoning. If supported by the provider, display concise progress updates, summaries, and explanations of the actions being performed.

Long responses must remain readable without forcing the entire editor layout to resize.

### 3.2 Message composer

Place the composer at the bottom of the workspace.

The composer must include:

1. A multiline text input.
2. A `+` button for attaching files and documents.
3. A model selector.
4. An effort selector when the selected model supports the feature.
5. A Send button.
6. A Stop button while an agent task is running.

The composer should follow familiar interaction patterns from modern AI chat and agent applications.

The message input must support:

- Multiline text.
- Enter to send, where appropriate.
- Shift+Enter for a new line.
- Clear visual feedback when a message is being submitted.
- Preservation of the draft when switching models or encountering a recoverable error.
- Disabled or adapted controls when the selected provider is not configured.

Avoid disrupting existing editor keyboard shortcuts while the composer has focus.

### 3.3 Provider and model selectors

Display the model selector close to the message input.

The selector must list models available through configured providers.

Each model entry should identify its provider and model name. Where useful, indicate relevant capabilities such as:

- Text input.
- Image input.
- Tool calling.
- Streaming.
- Extended context.
- Reasoning or effort controls.

Do not assume that all models support all capabilities.

When multiple providers expose models with the same display name, distinguish them by provider.

Changing the selected model must not silently discard the current message draft.

### 3.4 Effort selector

Display an effort selector next to the model selector when the selected model supports configurable reasoning effort.

Use provider-supported values and map them through a normalized internal representation where possible.

Typical options may include:

- Low.
- Medium.
- High.
- Maximum, when supported.

The actual options must be derived from the selected model's capabilities and provider adapter.

When the selected model does not support effort configuration, hide or disable the selector and explain why when appropriate.

Do not assume that reasoning effort is equivalent across providers. Preserve provider-specific settings when required.

### 3.5 Agent activity

Provide an expandable activity view for the current task.

Display useful status events such as:

- Analyzing the request.
- Inspecting the project.
- Preparing a plan.
- Requesting approval.
- Executing a tool.
- Waiting for a tool result.
- Updating artwork.
- Validating changes.
- Completed, canceled, or failed.

Show the name of each tool, a short description of its operation, its status, and a concise result summary.

Do not display credentials, raw authorization headers, private reasoning traces, or sensitive internal data.

## 4. Provider Management

Add an AI Providers section to the application's settings.

Users must be able to configure multiple provider connections and switch between them without editing external configuration files.

The architecture must support provider adapters for compatible APIs and official integrations where available.

### 4.1 Initial provider targets

Design the system to support the following provider categories:

- OpenAI models and supported account/API authentication methods.
- Anthropic Claude models and supported authentication methods.
- GitHub Copilot, where an authorized and technically supported integration is available.
- OpenAI-compatible API providers.
- Additional providers through future adapters.

Provider support must be implemented according to each provider's actual authentication, API, model, and tool-calling capabilities.

Do not assume that signing into a consumer ChatGPT, Claude, or Copilot subscription automatically grants API access.

Do not promise that every subscription can be reused through a third-party client. If a provider requires an API key, OAuth flow, official extension, or separate entitlement, explain that requirement in the UI.

For GitHub Copilot, use an officially supported integration path if available. Do not reverse-engineer private APIs, extract credentials from another application, or imitate undocumented authentication protocols.

### 4.2 Add provider workflow

Provide an Add Provider action.

The user must be able to:

1. Choose a provider type.
2. Enter or authorize the required credentials.
3. Configure an optional custom API endpoint where supported.
4. Validate the configuration.
5. Save the connection.
6. Discover or refresh available models.
7. Select a default model for future sessions.

Provider-specific fields must appear only when relevant.

### 4.3 API keys and authentication

Support API key configuration where the provider offers API access.

Credentials must be stored securely using an operating-system-backed secure credential store or an equivalent protected mechanism.

Never store API keys in:

- `project.json`.
- Scene files.
- Conversation transcripts.
- Ordinary application preferences.
- Debug logs.
- Renderer-accessible persistent storage.

The renderer must never receive unrestricted access to the credential store.

If a provider uses OAuth, implement the supported authorization flow and securely manage access and refresh tokens.

Provide actions to test, update, disconnect, and remove provider configurations.

Mask secret values in the UI.

Do not log full credentials or authorization tokens.

### 4.4 Model discovery

Retrieve models through provider-supported discovery endpoints when available.

If model discovery is unavailable, allow a controlled manual model identifier configuration where the provider supports it.

Maintain a normalized model registry containing information such as:

- Provider ID.
- Model ID.
- Display name.
- Supported input types.
- Tool-calling capability.
- Streaming capability.
- Effort configuration support.
- Context or output limits when available.
- Availability status.

The registry must distinguish verified capabilities from unknown capabilities.

Do not claim that a model supports tool calling, images, or effort configuration without evidence from provider metadata or validated configuration.

Handle unavailable models and provider errors without crashing the workspace.

## 5. Provider and Model Architecture

Implement a provider abstraction layer independent of the chat UI.

Suggested logical components:

- `AIProviderRegistry`: Registers and resolves provider adapters.
- `AIProviderAdapter`: Defines the common provider contract.
- `AIModelRegistry`: Stores discovered and configured model capabilities.
- `AIConnectionService`: Validates provider connectivity and manages model discovery.
- `AIConversationService`: Manages messages, streaming responses, and conversation state.
- `AIAgentRuntime`: Coordinates model requests, tool calls, approvals, and task lifecycle.
- `AISettingsService`: Manages non-secret provider preferences.
- `SecureCredentialService`: Stores and retrieves secrets securely.
- `AIToolRegistry`: Registers available application tools.
- `MCPClientService`: Connects to configured MCP servers.
- `AIEventService`: Delivers task progress events to the UI.

These names are suggestions. Reuse existing project conventions where equivalent components already exist.

### 5.1 Normalized provider contract

Define a typed internal contract that supports:

- Listing or refreshing models.
- Validating provider configuration.
- Sending conversation requests.
- Streaming responses where supported.
- Receiving structured tool calls.
- Returning tool results to the model.
- Applying supported model parameters.
- Reporting normalized errors and cancellation.
- Exposing model capabilities.

Provider-specific request and response formats must remain inside their adapters.

Do not force unsupported capabilities into the common contract. Represent unavailable or unknown features explicitly.

### 5.2 Streaming

Stream assistant responses to the UI when the provider supports streaming.

The user must be able to see the response being generated without waiting for the complete message.

Streaming must coexist with tool execution and task cancellation.

Handle interrupted streams, connection failures, and partial responses without corrupting the conversation history.

## 6. Agent Runtime and Execution Loop

The agent runtime must support an iterative tool-using workflow.

A typical task proceeds as follows:

1. Receive the user's request.
2. Resolve the selected provider and model.
3. Build the request context using authorized project information.
4. Send the request to the model.
5. Receive either a text response, a tool call, or another supported response type.
6. Validate requested tool calls against the registered tool definitions and permission policies.
7. Request user approval if required.
8. Execute authorized tools through application services.
9. Return tool results to the model.
10. Continue until the model finishes, the task is canceled, or a configured limit is reached.
11. Summarize completed work, errors, and any remaining limitations.

The runtime must not assume that a single model response completes every task.

### 6.1 Execution limits

Implement configurable safety limits for:

- Maximum agent iterations per task.
- Maximum tool calls per task.
- Maximum execution duration.
- Maximum tool input and output sizes.
- Maximum attached file sizes.
- Maximum accumulated conversation context where applicable.

Provide safe defaults and clear error messages when a limit is reached.

Prevent unbounded tool-call loops.

### 6.2 Task cancellation

The user must be able to stop a running task.

Cancellation must:

- Stop issuing new model requests.
- Abort cancellable network requests.
- Prevent queued tools from executing.
- Signal cancellation to active tools where supported.
- Clean up temporary resources.
- Preserve the conversation and report which operations completed.

Already committed project changes must not be silently rolled back unless they are part of an explicit transaction that can be safely reversed.

The UI must distinguish between completed work, canceled work, and operations that could not be interrupted immediately.

## 7. Animation Application Tools

The primary purpose of the agent is to interact with the animation application, not merely answer questions.

Provide an extensible registry of typed tools that expose supported application operations.

Agents must interact with the project through these tools rather than directly editing arbitrary application files.

### 7.1 Initial tool categories

Implement the architecture for the following tool categories.

**Project inspection:**

- Get active project metadata.
- List scenes.
- Get active scene details.
- List frames in a scene.
- Get frame and layer metadata.
- Get canvas dimensions and animation FPS.
- Read selected drawing and curve metadata where supported.

**Artwork inspection:**

- Obtain a rendered preview of a frame.
- Inspect supported drawing objects and vector curves.
- Read relevant asset metadata.
- Identify the active scene, frame, and layer.

**Scene and timeline operations:**

- Create, rename, and select scenes.
- Create, duplicate, and select frames.
- Query and modify supported animation settings.

**Artwork operations:**

- Create or update supported drawing objects.
- Modify supported vector curves and their properties.
- Apply supported transformations to artwork.
- Use existing drawing and selection services where available.

**Project resources:**

- List and inspect project assets.
- Import assets through authorized asset-management operations.
- Reference supported assets in the project.

Only implement tools for operations that the application currently supports through reliable internal services.

Do not expose a tool as functional if it is only a placeholder.

### 7.2 Tool definitions

Each tool must have:

- A stable tool ID.
- A human-readable name and description.
- A typed input schema.
- A typed result schema.
- A permission classification.
- Input validation.
- Execution status and error reporting.
- Cancellation behavior where applicable.

Tool schemas must be generated or maintained consistently for the agent runtime and any MCP server that exposes the same functionality.

### 7.3 Tool execution isolation

The model must not receive unrestricted Node.js, shell, filesystem, or Electron main-process access.

All application changes must go through explicit tool implementations and application services.

Tool arguments must be validated at runtime, even when the model claims they are valid.

Do not execute model-generated JavaScript or TypeScript inside the application as a shortcut for tool calling.

## 8. Permissions and User Approval

Implement a permission model for agent actions.

Classify tools into categories such as:

- **Read-only:** Inspecting project state and rendering previews.
- **Project modification:** Changing artwork, frames, scenes, or project settings.
- **External access:** Communicating with external MCP servers or other configured services.
- **Sensitive operations:** Deleting assets, removing scenes, overwriting files, or other destructive actions.

Read-only operations may run automatically when the required context is available.

Project modifications must follow a configurable approval policy.

Provide a default policy that allows low-risk, reversible edits to proceed within the active project while requiring confirmation for destructive operations and actions that affect data outside the project.

The user must be able to inspect pending approval requests before approving or rejecting them.

Approval requests must identify:

- The operation.
- The affected scene, frame, layer, asset, or file.
- The expected effect.
- Any relevant overwrite or deletion risk.

The agent must not bypass approval requirements by requesting an equivalent operation through a different tool.

### 8.1 Undo and recovery

Where possible, project modifications must integrate with the application's existing undo/redo system.

For multi-step tasks, group related changes into a logical transaction or clearly report which individual changes were committed.

If a task fails halfway through, report the changes that were completed and the changes that were not.

Do not claim that a task was fully reverted unless the application has verified that restoration succeeded.

## 9. MCP Integration

Implement MCP support as an extensible integration layer.

MCP connections must be configurable within the application without requiring users to manually edit JSON or JSONC files.

### 9.1 MCP server management

Add an MCP Servers section to settings.

Allow users to:

- Add an MCP server.
- Edit its configuration.
- Enable or disable it.
- Connect and disconnect.
- Test connectivity.
- Inspect available tools and resources where supported.
- Review connection errors.
- Remove the configuration.

Support MCP transports that are implemented and validated by the application, prioritizing the current official protocol and maintained SDKs.

Local process-based servers and remote servers may require different configuration fields and permissions.

For local process-based servers, allow an executable and arguments only through an explicit configuration workflow. Validate the executable and display the command that will be launched.

Do not silently execute downloaded programs or automatically trust newly added servers.

For remote servers, validate the endpoint and use supported authentication mechanisms.

### 9.2 MCP tools

Discover tools provided by connected servers and make them available to the agent only after applying the configured permission policy.

For each tool, show:

- Server name.
- Tool name.
- Description.
- Permission category.
- Connection status.

Validate tool inputs and outputs.

Treat tool results and remote server content as untrusted data.

MCP server output must never be interpreted as trusted system instructions or be allowed to modify the application's security policies.

### 9.3 Internal application tools and MCP

Keep the application's internal tool registry independent of MCP.

The same safe application operations may optionally be exposed through a future MCP server so external agent clients can control the animation application.

Do not make the application's internal tools depend on an active external MCP connection.

## 10. File Attachments

The `+` button in the composer must open a menu or file picker for attaching supported files and documents.

Support common formats relevant to animation work, subject to provider capability and file validation:

- PNG and JPEG images.
- Supported image formats already handled by the application.
- Text files.
- Markdown documents.
- JSON configuration and metadata files.
- Source code and other plain-text documents.
- PDFs where document extraction is available.

The architecture must allow additional attachment types later.

### 10.1 Attachment behavior

Display attached files as removable items associated with the draft message.

For each attachment, show its filename and, where useful, its type and size.

Allow the user to remove an attachment before sending.

Validate file existence, file type, and size before submission.

Do not send unsupported formats directly to a provider.

For providers that support image or document input, use the appropriate provider-specific attachment mechanism.

Where a provider does not support a given file type, use a controlled text extraction or image processing path only if implemented and safe. Otherwise, explain that the attachment is unsupported.

### 10.2 File access and privacy

Attachment selection must use controlled file-picker and preload APIs.

The renderer must not receive unrestricted filesystem access.

Only send attachments to the selected provider or MCP server when necessary for the requested task and permitted by the user.

Make it clear that attached content may be transmitted to the configured external provider.

Do not automatically attach the entire project directory.

## 11. Project Context Management

The agent must receive relevant project context without indiscriminately sending the entire project to the model.

Provide a context builder that can include:

- Project name and canvas dimensions.
- Active scene and frame.
- Animation FPS.
- Layer structure.
- Relevant drawing and curve metadata.
- Selected artwork information, where supported.
- Relevant asset metadata.
- User-selected attachments.
- Relevant tool results from the current task.

The context builder must respect provider limits and the task's requirements.

When visual understanding is required, use a rendered frame or a supported image representation if the selected model accepts it.

Do not assume every model supports image input.

Allow the user to understand which project or scene the agent is working on.

The agent must not silently switch to modifying another project or scene because of ambiguous context.

For potentially destructive or broad operations, require the agent to identify the intended target before execution.

## 12. Conversation and Session Management

Support multiple conversations within the application.

Users must be able to:

- Start a new conversation.
- View previous conversations.
- Rename a conversation.
- Delete a conversation.
- Continue a previous conversation where its context remains available.

Each conversation must have a stable ID and timestamps.

Conversation metadata must include the selected provider and model, subject to changes during the conversation.

When the model changes, preserve the conversation history where compatible, while clearly indicating the currently selected model.

If provider-specific conversation state cannot be reused across models, rebuild the request using the normalized conversation history and supported attachments.

Conversation history must not contain API keys, access tokens, or other credentials.

Store conversation data separately from the animation project's source files, using an appropriate application-level persistence mechanism.

Provide a way to clear conversation history and explain whether any separately stored attachments or cached data will also be removed.

## 13. Configuration Persistence

All configuration must be manageable from the application's UI.

Separate configuration into:

**Application-level settings:**

- Provider connections.
- Secure credential references.
- Model preferences.
- Effort preferences.
- Agent execution limits.
- Permission policies.
- MCP server configurations.
- Conversation history and workspace preferences.

**Project-level context:**

- Active project information.
- Scene, frame, and layer state.
- Project assets and drawing data.
- Any explicitly project-scoped agent configuration introduced in a future requirement.

Do not store provider credentials in project files.

Persist non-secret settings using the existing application settings architecture.

MCP configurations containing secrets must reference secure credential storage rather than storing plaintext secrets.

If the application later supports portable configuration export, secrets must be excluded by default.

## 14. Electron Security

Preserve the existing security requirements:

- `contextIsolation: true`.
- `nodeIntegration: false`.
- No unrestricted Node.js access in the renderer.
- No arbitrary shell execution from model responses.
- No unrestricted filesystem access from the model or renderer.

Use narrow, typed preload APIs and explicit IPC handlers.

Perform credential access, provider communication, MCP process management, and sensitive file operations in appropriately isolated services.

Validate all IPC arguments and external responses.

Protect against:

- Prompt injection through attachments, project files, rendered content, or MCP output.
- Malicious tool arguments.
- Unauthorized filesystem access.
- Credential leakage through logs or error messages.
- Untrusted MCP servers requesting excessive permissions.
- Tool-call loops and excessive resource consumption.
- Unsafe execution of model-generated code.

Treat instructions embedded in user-provided files, project assets, or remote tool output as untrusted content. Such content must not override application security rules or user approval policies.

## 15. Errors and Observability

Provide clear, actionable errors for:

- Missing or invalid provider credentials.
- Authentication failures.
- Unsupported models or capabilities.
- Provider rate limits.
- Network failures.
- Context or attachment limits.
- Unsupported attachment formats.
- MCP connection failures.
- Tool validation errors.
- Tool execution failures.
- Permission denials.
- Execution limit reached.
- Task cancellation.
- Unexpected runtime errors.

Use structured logs for diagnosing problems without recording secrets or unnecessarily logging private user content.

Allow users to retry recoverable operations.

A failed provider request must not crash the editor or corrupt the current project.

## 17. Acceptance Criteria

- The existing AI Chat placeholder is replaced with a functional AI Agent Workspace.
- Users can compose and submit messages from the bottom composer.
- Users can attach supported files using the `+` button.
- Users can select a configured provider and model.
- The effort selector reflects actual model capabilities.
- At least one supported provider adapter completes a real conversation successfully.
- The architecture allows additional provider adapters to be added independently.
- The agent can inspect relevant project state using registered tools.
- The agent can execute at least one supported, real project-modification workflow through validated application tools.
- Tool execution, approvals, progress, errors, and cancellation are visible to the user.
- Project changes respect the configured permission policy and integrate with undo/redo where supported.
- Users can configure providers and MCP servers through the application's UI.
- Credentials are stored securely and are never written to project files or ordinary logs.
- MCP tools are validated and subject to explicit permission policies.
- Agent failures do not freeze the editor or corrupt the project.
- The system can be extended with additional providers, models, tools, and MCP integrations without redesigning the core workspace.

## 18. Out of Scope

- Implementing every provider and every model in the initial release.
- Bypassing provider authentication, subscriptions, usage restrictions, or API requirements.
- Reproducing proprietary internal interfaces of other agent applications.
- Executing arbitrary model-generated scripts directly inside Electron.
- Giving agents unrestricted operating-system or filesystem access.
- Autonomous remote publishing or deployment.
- Unattended destructive operations without an explicit permission policy.
- Training or fine-tuning models.
- Guaranteeing compatibility with every third-party MCP server.
- Replacing the existing animation engine or project data model.

## 19. Recommended Implementation Phases

Implement the HU incrementally while keeping all phases within the same architectural design.

### Phase 1 — Workspace and Provider Foundation

- Rebuild the chat interface and composer.
- Add provider settings and secure credential storage.
- Implement one verified provider adapter.
- Add model selection and capability-aware effort settings.
- Implement streaming and conversation persistence.

### Phase 2 — Agent Runtime and Internal Tools

- Implement the agent execution loop.
- Add tool registry, validation, and execution events.
- Expose read-only project inspection tools.
- Implement one complete, controlled artwork-modification workflow.
- Integrate approval, cancellation, and undo/redo policies.

### Phase 3 — Attachments and MCP

- Add file attachment handling.
- Implement MCP server configuration and lifecycle.
- Discover and execute MCP tools through permission policies.
- Add connection diagnostics and security tests.

### Phase 4 — Provider Expansion and Hardening

- Add additional provider adapters.
- Expand model capability support.
- Improve context management, error handling, and resource limits.
- Validate supported integrations across the target operating systems.

The implementation must deliver a usable end-to-end workflow before expanding to every provider or MCP capability.

## 20. Implementation Notes

Before implementation, inspect the existing chat UI, Electron process architecture, settings persistence, drawing and scene services, undo/redo system, and any existing AI-related code.

Reuse reliable internal services and conventions. Avoid duplicating project state or introducing a second, conflicting mechanism for editing artwork.

Provider adapters must isolate external API differences. The agent runtime must remain independent of provider-specific request formats.

Treat MCP as a protocol integration layer rather than the application's entire agent architecture.

The application must retain control of project state, permissions, and execution. Models propose actions; validated application tools execute them.

The first functional milestone is a user selecting a configured model, requesting an operation in natural language, watching the agent inspect the project, approving any required changes, and seeing those changes applied correctly inside the editor.
