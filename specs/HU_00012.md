# HU_00012 — Frame and Animation Export

## 1. Objective

Implement a complete export workflow for the animation editor, allowing users to export:

- The currently selected frame as a single PNG image.
- All frames from a scene as individual PNG files.
- All frames from a scene as a single ZIP archive containing PNG files.
- An animation as a video file or animated GIF.

The export system must preserve the visual appearance of the artwork, provide configurable output settings, support multiple scenes, and avoid blocking the editor during export.

The architecture must allow additional image and video formats to be added without redesigning the export workflow.

## 2. Scope

### 2.1 Supported export formats

**Initial release:**

| Format | Purpose | Transparency |
|---|---|---|
| PNG | Single frame or image sequence | Supported |
| ZIP containing PNG files | Batch export of frames in one archive | Preserved in PNG files |
| MP4 (H.264) | Standard video playback and sharing | Not supported |
| GIF | Animated image, especially short looping animations | Limited transparency |

**Extensible formats:**

- WebM (VP9), including alpha transparency where supported by the selected encoder.
- MOV (ProRes 4444), including alpha transparency, as a future advanced format.

Only formats that are supported by the actual packaged encoder and verified on the target platform may be offered in the UI. Advanced formats must not be displayed as available until their encoding capabilities have been validated.

## 3. Export Entry Point

Add an **Export** button to the project editor's top toolbar.

Clicking the button opens an export dialog with the following options:

1. Current Frame — PNG.
2. All Frames — individual PNG files.
3. All Frames — ZIP archive containing PNG files.
4. Animation — MP4 or GIF.

The dialog must adapt its settings to the selected export type.

The default export scope is the currently active scene. Exporting all scenes must be supported where applicable, as described in Section 5.

## 4. Single-Frame Export

### 4.1 Behavior

The user can export the currently selected frame as a PNG image.

The exported image must:

- Match the project's canvas dimensions unless a custom resolution is explicitly supported and selected.
- Preserve transparency.
- Include the visible artwork from the selected frame and its layers.
- Exclude editor UI elements and editing overlays.

The export must not include selection outlines, Bézier anchors or handles, brush cursors, onion-skin references, grid overlays, or other editor-only visual elements.

### 4.2 Output destination

Allow the user to choose the output directory and filename.

Use the selected scene name and frame number as a suggested filename, for example:

`scene_name_frame_0001.png`

The user may change the filename before confirming the export.

Do not silently overwrite an existing file. Ask the user to confirm replacement or select another filename.

## 5. Batch PNG Export

### 5.1 Export modes

Provide two batch export modes:

- **Separate PNG Files:** Export every frame as an individual PNG file.
- **ZIP Archive:** Export every frame as an individual PNG file and package the resulting files into a single ZIP archive.

The user must not be required to manually export frames one at a time.

### 5.2 Scene scope

Support the following scene scopes:

- **Active Scene:** Export every frame in the currently active scene. This is the default.
- **All Scenes:** Export every frame from every scene in the project.

When exporting all scenes, create a separate directory for each scene inside the selected output directory, regardless of whether the output is a directory of files or a ZIP archive.

For ZIP exports, preserve this directory structure inside the archive.

Example:

`animation_export.zip`

- `Scene_A/frame_0001.png`
- `Scene_A/frame_0002.png`
- `Scene_B/frame_0001.png`
- `Scene_B/frame_0002.png`

For separate PNG exports, use the equivalent directory structure on disk.

### 5.3 File naming

Use zero-padded frame numbers to preserve the correct chronological order.

Examples:

- `frame_0001.png`
- `frame_0002.png`
- `frame_0010.png`

The number of digits should be sufficient for the largest frame number in the export.

Scene directory names and filenames must be sanitized for the target filesystem. If two scene names produce conflicting directory names, generate unique output directory names without changing the scene names stored in the project.

### 5.4 Frame order and content

Frames must be exported in their actual scene timeline order.

Each PNG must contain the complete rendered artwork for its corresponding frame, including all applicable layers.

The export process must use the project's rendering pipeline or an equivalent dedicated rendering service. It must not capture screenshots of the editor window.

PNG transparency must be preserved.

### 5.5 Existing files and conflicts

Do not silently overwrite existing PNG files or ZIP archives.

Before starting, validate the output destination and detect foreseeable filename conflicts.

Provide an appropriate conflict resolution option, such as confirming replacement or choosing another destination. If a conflict cannot be resolved safely, stop the export and explain the problem.

## 6. Animation Export

### 6.1 Supported initial formats

Provide the following choices:

- **MP4 (H.264):** Default format for broad compatibility.
- **GIF:** Alternative for animated images and short looping animations.

The export architecture must allow WebM and MOV encoders to be added later.

### 6.2 Scene scope

Allow the user to export:

- The active scene as one animation.
- All scenes as separate animation files.

When exporting all scenes, generate one file per scene. Never concatenate separate scenes into one animation unless a future feature explicitly supports that behavior.

Use the scene name in each output filename, for example:

- `Scene_A.mp4`
- `Scene_B.mp4`

### 6.3 Frame range

Provide frame range options:

- All frames.
- Custom range, using a starting and ending frame number.

The default is all frames in the selected scene.

Validate that the starting frame exists, the ending frame exists, and the starting frame does not occur after the ending frame.

Export frames in timeline order, including both endpoints of the selected range.

### 6.4 Frame rate

Provide a frame rate setting with:

- **Use Scene FPS:** Default; use the active scene's configured playback frame rate.
- **Custom FPS:** Allow the user to specify a positive integer frame rate.

Include common values such as 24, 30, 60, and 120 FPS, while allowing other valid positive integer values.

For video export, each exported frame must have a duration determined by the selected frame rate. The export must render frames according to the configured frame rate rather than recording real-time editor playback.

The exported duration must be consistent with the number of exported frames and the selected FPS.

### 6.5 Resolution

Provide the following resolution options:

- **Original Canvas Size:** Default; use the project's canvas dimensions.
- **Custom Resolution:** Allow the user to specify output width and height in positive integer pixels.

When custom resolution is selected, provide a Keep Aspect Ratio option. When enabled, changing one dimension must update the other dimension according to the configured ratio.

Reject invalid dimensions and handle unsupported or excessively large output dimensions with a clear validation message.

The export must render at the requested output resolution rather than resize a screenshot of the editor.

### 6.6 Background and transparency

Provide background options appropriate to the selected format.

**MP4:**

- Transparency is not supported.
- Allow the user to select a background color.
- If the source canvas contains transparent areas, composite the artwork over the selected background color.

**GIF:**

- Provide a background/transparency option when supported by the encoder.
- Explain that GIF transparency is limited and does not provide full alpha transparency.
- If the chosen encoder cannot preserve the requested transparency behavior, disable the option or clearly explain the limitation.

The default background behavior must be explicit in the UI. Never silently flatten transparent artwork against an unexpected color.

**Future alpha-capable formats:**

WebM VP9 with alpha and MOV ProRes 4444 may offer transparency when the selected encoder supports it. Their UI options must reflect actual encoder capabilities.

### 6.7 Quality and compression

Provide a simple quality setting for video export, using understandable presets such as:

- Low File Size.
- Balanced (default).
- High Quality.

Map these presets to appropriate encoder settings for each format.

For GIF, provide an appropriate quality or palette optimization option if supported. Explain that GIF uses a limited color palette and may not reproduce all original colors.

The user must not need to understand codec-specific parameters to obtain a reasonable result.

### 6.8 GIF looping

For GIF export, provide a Loop Animation option.

When enabled, configure the GIF to loop continuously if supported by the encoder.

When disabled, export the animation without an infinite loop, where supported.

This setting must be specific to GIF export and must not change the project's playback settings.

### 6.9 Audio

Audio-track export is outside the scope of this requirement.

Exported videos must not include audio unless a future requirement explicitly introduces audio timeline and mixing support.

## 7. Export Dialog UX

The export dialog must show only settings relevant to the selected export type.

Common fields:

- Export type.
- Scene scope.
- Output destination.
- Relevant format-specific settings.

Additional fields for batch and animation exports:

- Frame range, where applicable.
- Resolution, where applicable.
- Frame rate, where applicable.
- Background or transparency options, where applicable.
- Quality/compression settings, where applicable.
- GIF looping, where applicable.

Provide a clear summary before the user starts the export, including the selected scene scope, output format, frame range, resolution, and FPS when applicable.

Use sensible defaults so the user can complete a basic export with minimal configuration.

The dialog must allow the user to cancel before the export starts without modifying the project.

## 8. Export Progress and Cancellation

For exports involving multiple frames or video encoding, display an export progress interface.

The interface must include:

- Export type and destination.
- Current operation or stage.
- Progress indicator.
- Current frame number and total frame count when applicable.
- Cancel button.

Progress must reflect actual work and must not be simulated with a timer.

Cancellation must stop additional rendering and encoding work as soon as safely possible.

For ZIP export, cancellation must stop additional frame generation and archive creation.

For video export, cancellation must terminate the active encoding process safely.

Temporary files must be cleaned up when cancellation occurs, except where cleanup fails and requires an explicit warning.

Do not leave an incomplete output file under the final requested filename.

## 9. Export Completion and Error Handling

On successful completion, display a confirmation that includes the output location.

Provide an action to open the containing directory where supported by the desktop environment.

Handle errors such as:

- Invalid or inaccessible output paths.
- Permission errors.
- Insufficient disk space.
- Invalid export settings.
- Unsupported encoder or format.
- Rendering failures for individual frames.
- ZIP creation failures.
- Video encoding failures.
- Cancellation.
- Failure to clean temporary files.

Error messages must explain what failed and provide a useful next step where possible.

If a multi-file export fails partway through, clearly report whether any files were successfully exported. Prefer staging output in a temporary location and moving it into place only after successful completion.

Never report success when the output is incomplete or invalid.

## 10. Rendering and Encoding Architecture

Implement export as a dedicated application service, independent of the export dialog UI.

Suggested logical components:

- `ExportService`: Coordinates export requests and lifecycle.
- `FrameRenderService`: Renders a scene frame at the requested output resolution without editor overlays.
- `ImageExportAdapter`: Exports individual PNG images.
- `BatchExportService`: Manages multiple frames and output naming.
- `ArchiveExportAdapter`: Packages PNG files into ZIP archives.
- `VideoExportAdapter`: Encodes rendered frames into supported video formats.
- `ExportJob`: Tracks progress, cancellation, status, and errors.

These names are suggestions. Reuse existing services and conventions if equivalent components already exist.

Define typed export options and result models rather than passing unvalidated arbitrary objects between the renderer and the main process.

Keep format-specific behavior behind adapters so future formats can be added without rewriting the export workflow.

### 10.1 Performance

Export must not freeze or make the editor unresponsive.

Perform expensive rendering, archive generation, and video encoding in a worker or separate utility process where appropriate.

If FFmpeg is selected for video encoding, package and configure it explicitly for supported target platforms. Validate the actual packaged binary and required codecs during development and release testing.

Review FFmpeg licensing and redistribution obligations before bundling it with the application.

Do not assume that every FFmpeg build supports every codec or alpha-transparency mode.

The renderer must remain responsive enough to display progress and process cancellation requests.

### 10.2 Memory management

Do not load every full-resolution rendered frame into memory simultaneously.

Render and process frames incrementally, releasing buffers and temporary resources when they are no longer needed.

Use temporary storage where required for archive creation or encoding, with cleanup after success, failure, or cancellation.

Avoid retaining large encoded frame buffers unnecessarily.

## 11. Project State and Save Behavior

Export must reflect the current visible artwork and the latest valid scene state.

If the current scene contains unsaved changes, the application must use a consistent policy:

- Prefer exporting from the current in-memory scene state, including unsaved edits, if the rendering pipeline supports this safely.
- Otherwise, prompt the user to save before exporting.

Do not silently export stale data from disk when newer edits are visible in the editor.

Exporting must not change the selected frame, active scene, drawing tools, brush settings, playback settings, or project metadata.

The export process must not modify source frames or layers.

## 12. Electron Security and File Access

Preserve the existing Electron security architecture:

- `contextIsolation: true`.
- `nodeIntegration: false`.
- No unrestricted filesystem access in the renderer.
- No direct Node.js or child-process access from the renderer.

Expose export operations through a narrow, typed preload API and explicit IPC handlers.

The main process or an appropriately isolated export service must validate export options and destination paths.

Only permit supported output formats and valid destination paths.

Use controlled process execution when invoking an encoder. Do not construct unsafe shell commands from user-provided filenames or settings.

Ensure cancellation and cleanup operations cannot delete files outside the export job's temporary directory.

## 13. Compatibility and Persistence

Export is an output operation and must not require a project format migration unless an existing architectural constraint makes one necessary.

Reuse the scene, frame, layer, drawing, curve, and canvas dimension models established by previous HUs.

Ensure that supported drawing types and curve geometry are rendered consistently with the editor's normal artwork rendering.

If a drawing type cannot be exported correctly, report the issue rather than silently omitting it.

Project assets and source files must remain unchanged by export.

The default export directory may be the project's `exports/` directory, provided it exists or can be created safely. Always allow the user to choose a different destination.

## 14. Testing Requirements

Implement automated tests for:

- Exporting the selected frame to PNG.
- PNG transparency and canvas dimensions.
- Exporting all frames as individual PNG files.
- Exporting all frames into a ZIP archive.
- ZIP directory structure and filename ordering.
- Exporting all scenes into separate folders or files.
- Correct handling of custom frame ranges.
- FPS and output duration consistency.
- Original and custom output resolutions.
- Aspect ratio validation.
- Background compositing for MP4.
- GIF frame ordering, timing, and looping settings.
- Quality preset mapping.
- Filename sanitization and conflict handling.
- Cancellation during rendering, archive generation, and video encoding.
- Cleanup of temporary files.
- Failure handling for missing encoders and inaccessible paths.
- Rendering without editor overlays or onion references.
- Exporting current unsaved edits according to the chosen save policy.
- Ensuring export does not modify project data or editor state.
- Renderer responsiveness during large exports.
- Security validation for IPC arguments and output destinations.

Include integration tests using representative projects with multiple scenes, multiple frames, multiple layers, transparent content, and Bézier curves.

## 15. Acceptance Criteria

- The user can export the currently selected frame as a PNG.
- The user can export all frames from the active scene as separate PNG files.
- The user can export all frames from the active scene into one ZIP archive.
- The user can export every scene into appropriately separated output folders or animation files.
- Exported frame files have stable, sortable names.
- The user can export an animation as MP4 or GIF using the supported settings.
- Video export supports frame range, resolution, FPS, background behavior, and quality presets.
- GIF export supports loop configuration where available.
- Transparency is preserved for PNG and correctly handled for formats with limited or no alpha support.
- Export does not include editor-only UI overlays.
- Export progress and cancellation work without freezing the editor.
- Failed or cancelled exports do not masquerade as successful completed files.
- The user receives clear success and error feedback.
- Export does not modify the source project or current editor state.
- The implementation follows existing Electron security and project architecture.
- The export architecture supports future format adapters without requiring a redesign.

## 16. Out of Scope

- Audio-track mixing or audio export.
- Direct publishing to social networks or cloud services.
- Batch export of arbitrary selected frames, except through the defined frame range and scene scope.
- Export presets shared across projects or synchronized to the cloud.
- Advanced command-line encoder configuration.
- WebM and MOV availability before their encoder support has been verified.
- Importing video files as editable animation timelines.
- Recording the editor window or capturing real-time playback.

## 17. Implementation Notes

Before implementation, inspect the current project structure and the rendering pipeline established by the previous HUs.

Reuse existing models and services wherever possible. Do not introduce duplicate sources of truth for scenes, frames, layers, canvas dimensions, or animation FPS.

Implement the first release with PNG export, ZIP batch export, MP4 encoding, and GIF encoding. Keep the format adapter interfaces extensible for future WebM and MOV support.

The final implementation must be validated on each supported operating system, including encoder availability, file permissions, output correctness, and cancellation behavior.
