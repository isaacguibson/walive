# HU_00003 — Project Resolution and Aspect Ratio

**Status:** Proposed
**Priority:** High
**Type:** Feature Enhancement / Project Configuration
**Related HUs:** HU_00001, HU_00002

---

## 1. Overview

Enhance the **Create New Project** form by allowing the user to define the project's canvas dimensions in pixels and optionally configure a fixed aspect ratio.

The project dimensions will be used later to construct the animation workspace/canvas. Therefore, these values are part of the project's persistent metadata and must be stored in `project.json`.

The feature introduces:

* Project width in pixels.
* Project height in pixels.
* Optional **Keep Aspect Ratio** configuration.
* Aspect ratio width and height values.
* Dynamic dimension recalculation when aspect ratio locking is enabled.

---

## 2. Goals

This HU must:

1. Add width and height pixel fields to the project creation form.
2. Default the dimensions to `1920 x 1080`.
3. Accept only positive integer values.
4. Make width and height mandatory.
5. Add a **Keep Aspect Ratio** checkbox.
6. When enabled, display two aspect ratio fields.
7. Make aspect ratio fields mandatory only while **Keep Aspect Ratio** is enabled.
8. Dynamically maintain the configured aspect ratio when the project dimensions are changed.
9. Calculate the aspect ratio immediately when the user enables **Keep Aspect Ratio**.
10. Prefer width as the reference when enabling the option.
11. Fall back to height when width has not been filled.
12. Persist all project dimension and aspect ratio configuration in `project.json`.
13. Keep the feature compatible with the Project Management architecture defined in HU_00001.
14. Ensure the stored values are available to the future animation workspace/canvas.

---

## 3. Non-Goals

This HU does **not** implement:

* The animation canvas.
* Drawing tools.
* Timeline functionality.
* Scene editing.
* Layer management.
* Export resolution configuration.
* Image scaling algorithms.
* AI functionality.
* MCP functionality.
* Resolution presets.
* DPI configuration.
* Physical units such as inches, centimeters, or millimeters.
* Automatic project resizing after project creation.

The values defined here represent the project's logical pixel dimensions.

# 5. Keep Aspect Ratio

The form must include a checkbox:

```text
☐ Keep Aspect Ratio
```

Label:

```text
Keep Aspect Ratio
```

The checkbox is disabled by default.

When disabled:

* Width and height behave independently.
* Aspect ratio fields are hidden.
* Aspect ratio fields are not required.
* Changing width does not automatically change height.
* Changing height does not automatically change width.

When enabled:

* Aspect ratio fields become visible.
* Aspect ratio fields become required.
* Width and height become constrained by the configured aspect ratio.
* Changes to one pixel dimension must dynamically update the other dimension.

---

# 6. Aspect Ratio Fields

When **Keep Aspect Ratio** is enabled, display two additional numeric fields.

Example:

```text
Keep Aspect Ratio

[ 16 ] : [ 9 ]
```

The `:` character must be displayed between the fields.

Each field:

* Accepts only positive integers.
* Must be greater than `0`.
* Is required while **Keep Aspect Ratio** is enabled.

The fields represent:

```text
Aspect Ratio Width : Aspect Ratio Height
```

For example:

```text
16 : 9
```

represents:

```text
width / height = 16 / 9
```

Other valid examples include:

```text
1 : 1
4 : 3
3 : 2
9 : 16
21 : 9
```

---

# 7. Aspect Ratio Field Visibility

The aspect ratio fields must only be displayed when:

```text
Keep Aspect Ratio = checked
```

Example when disabled:

```text
Width        Height
[ 1920 ] px x [ 1080 ] px

☐ Keep Aspect Ratio
```

Example when enabled:

```text
Width        Height
[ 1920 ] px x [ 1080 ] px

☑ Keep Aspect Ratio

Aspect Ratio
[ 16 ] : [ 9 ]
```

The transition should happen dynamically without requiring the user to reopen the form.

---

# 8. Default Aspect Ratio

The aspect ratio fields do not need to be populated while **Keep Aspect Ratio** is disabled.

When the user enables **Keep Aspect Ratio**, the application must determine an appropriate aspect ratio from the currently entered pixel dimensions.

For example:

```text
Width  = 1920
Height = 1080
```

When the user checks:

```text
Keep Aspect Ratio
```

the application should calculate:

```text
1920 : 1080
```

and normalize it to:

```text
16 : 9
```

The greatest common divisor (GCD) should be used to reduce the ratio to its simplest integer representation.

---

# 9. Enabling Keep Aspect Ratio

When the user checks **Keep Aspect Ratio**, the application must immediately initialize the aspect ratio.

The current pixel dimensions must be used.

## 9.1 Width Has Priority

If both width and height contain valid values, width must be preferred as the reference dimension when applying the aspect ratio.

For example:

```text
Width  = 1920
Height = 1080
```

and the user enables:

```text
Keep Aspect Ratio
```

The application calculates:

```text
1920 / 1080 = 16 / 9
```

The aspect ratio fields become:

```text
16 : 9
```

The current width remains the reference value:

```text
Width = 1920
```

and height is recalculated from the ratio:

```text
Height = 1920 × 9 / 16
Height = 1080
```

---

## 9.2 Width Missing

If the width is not filled with a valid value but the height contains a valid value, the height must be used as the reference.

For example:

```text
Width  = empty
Height = 1080
```

When the user enables **Keep Aspect Ratio**, the application must:

1. Determine the available aspect ratio if one can be established.
2. Use height as the reference dimension.
3. Calculate width from the aspect ratio.

If the aspect ratio cannot yet be determined because there are insufficient valid values, the form must remain in a validation state until the user provides enough information.

---

## 9.3 Invalid or Missing Dimensions

The application must not attempt to perform mathematical calculations using:

* `0`
* Negative numbers
* Decimal numbers
* Non-numeric values
* Empty values

Validation must occur before aspect ratio calculations are performed.

---

# 10. Dynamic Aspect Ratio Behavior

When **Keep Aspect Ratio** is enabled, changing one pixel dimension must automatically recalculate the other dimension.

The ratio is:

```text
width / height = ratioWidth / ratioHeight
```

Therefore:

```text
height = width × ratioHeight / ratioWidth
```

and:

```text
width = height × ratioWidth / ratioHeight
```

---

## 10.1 Width Changes

When the user changes the width:

```text
Width = new value
```

the height must be recalculated using:

```text
height = width × ratioHeight / ratioWidth
```

Example:

```text
Aspect Ratio = 16 : 9
Width = 1280
```

Result:

```text
Height = 720
```

---

## 10.2 Height Changes

When the user changes the height:

```text
Height = new value
```

the width must be recalculated using:

```text
width = height × ratioWidth / ratioHeight
```

Example:

```text
Aspect Ratio = 16 : 9
Height = 720
```

Result:

```text
Width = 1280
```

---

# 11. Integer Requirements During Recalculation

All pixel dimensions must remain positive integers.

Aspect ratio calculations may mathematically produce fractional values.

The implementation must therefore apply a deterministic integer rounding strategy.

The default strategy should be:

```text
round()
```

to the nearest integer.

After rounding, the resulting value must still be greater than `0`.

Example:

```text
Ratio = 16 : 9
Width = 1000

Height = round(1000 × 9 / 16)
Height = round(562.5)
Height = 563
```

The implementation must prevent values such as:

```text
562.5
```

from being stored in pixel fields.

---

# 12. Editing the Aspect Ratio

When **Keep Aspect Ratio** is enabled, the user may modify the aspect ratio fields.

For example:

```text
16 : 9
```

may be changed to:

```text
4 : 3
```

After a valid aspect ratio change, the current pixel dimensions must be recalculated immediately.

The width should remain the preferred reference dimension when possible.

For example:

```text
Current dimensions:
1920 x 1080

Current ratio:
16 : 9

User changes ratio to:
4 : 3
```

The application should calculate:

```text
Width = 1920
Height = 1920 × 3 / 4
Height = 1440
```

Result:

```text
1920 x 1440
```

---

# 13. Preventing Update Loops

The dynamic recalculation must not create an infinite update loop.

For example:

```text
Width changes
    ↓
Height recalculates
    ↓
Height change event
    ↓
Width recalculates
    ↓
Height recalculates
    ↓
...
```

The implementation must ensure that a calculated field update does not recursively trigger another dimension recalculation.

The behavior should conceptually be:

```text
User changes Width
        ↓
Calculate Height
        ↓
Update Height without triggering
another user-originated dimension calculation
```

The same principle applies when the user changes Height.

---

# 14. Disabling Keep Aspect Ratio

When the user unchecks:

```text
Keep Aspect Ratio
```

the aspect ratio fields must:

* Stop affecting width and height.
* No longer be required.
* Become hidden.
* Preserve their current values internally until the form is submitted or reset, if useful to the implementation.

Width and height must once again be independently editable.

Example:

```text
☐ Keep Aspect Ratio

Width  = 1920
Height = 1080
```

Changing width to:

```text
1280
```

must not automatically change height.

---

# 15. Project Metadata

The project metadata stored in `project.json` must be extended to include the project's dimensions.

The existing metadata from HU_00001 remains unchanged.

Example:

```json
{
  "formatVersion": 1,
  "id": "uuid",
  "name": "My Animation",
  "createdAt": "2026-10-08T12:00:00.000Z",
  "updatedAt": "2026-10-08T12:00:00.000Z",
  "canvas": {
    "width": 1920,
    "height": 1080,
    "keepAspectRatio": true,
    "aspectRatio": {
      "width": 16,
      "height": 9
    }
  }
}
```

---

# 16. Metadata Structure

The following structure should be used:

```ts
interface ProjectCanvas {
  width: number;
  height: number;
  keepAspectRatio: boolean;
  aspectRatio?: {
    width: number;
    height: number;
  };
}
```

The project metadata should then contain:

```ts
interface ProjectMetadata {
  formatVersion: number;
  id: string;
  name: string;
  createdAt: string;
  updatedAt: string;
  canvas: ProjectCanvas;
}
```

The exact internal TypeScript organization may differ according to the existing architecture, but the persisted JSON structure must remain compatible with this model.

---

# 17. Aspect Ratio Persistence Rules

When `keepAspectRatio` is `false`, the aspect ratio configuration is not required.

The preferred persisted representation is:

```json
{
  "canvas": {
    "width": 1920,
    "height": 1080,
    "keepAspectRatio": false
  }
}
```

When `keepAspectRatio` is `true`, the aspect ratio must be persisted:

```json
{
  "canvas": {
    "width": 1920,
    "height": 1080,
    "keepAspectRatio": true,
    "aspectRatio": {
      "width": 16,
      "height": 9
    }
  }
}
```

The application must never persist an enabled aspect ratio configuration without valid positive integer ratio values.

# 19. Validation

The Create Project form must prevent project creation when required values are invalid.

## Width

Invalid when:

* Empty.
* Not an integer.
* Less than or equal to `0`.

## Height

Invalid when:

* Empty.
* Not an integer.
* Less than or equal to `0`.

## Aspect Ratio Width

Invalid when `Keep Aspect Ratio` is enabled and:

* Empty.
* Not an integer.
* Less than or equal to `0`.

## Aspect Ratio Height

Invalid when `Keep Aspect Ratio` is enabled and:

* Empty.
* Not an integer.
* Less than or equal to `0`.

The user must receive clear validation feedback.

# 22. Architecture Requirements

The implementation must respect the architecture established by HU_00001 and HU_00002.

The Create Project UI must not directly manipulate the filesystem.

The responsibility boundaries remain:

```text
Renderer
    ↓
Preload API
    ↓
IPC
    ↓
Project Management
    ↓
Project Repository
    ↓
Filesystem
```

The form is responsible for:

* User interaction.
* Local form state.
* Validation feedback.
* Aspect ratio calculations.
* Sending the validated project configuration to the Project Management API.

Project Management is responsible for:

* Creating the project.
* Persisting metadata.
* Validating project metadata.
* Reading/writing `project.json`.

---

# 23. API Changes

The project creation operation must accept the new canvas configuration.

Conceptually:

```ts
interface CreateProjectOptions {
  name: string;
  location: string;
  canvas: ProjectCanvas;
}
```

The existing:

```ts

```

operation must be extended rather than creating a separate project creation mechanism.

The API must remain reusable by:

* Application Home.
* Future Project Editor.
* Automated tests.
* Future plugins.
* Future AI integrations.
* Future MCP integration.

---

# 24. Future Animation Workspace Compatibility

The values defined by this HU will later be used by the animation workspace.

The future animation workspace must be able to obtain:

```text
canvas.width
canvas.height
```

from the active project's metadata.

For example:

```text
Project:
My Animation

Canvas:
1920 x 1080
```

The canvas dimensions must therefore be treated as project configuration rather than temporary form state.

No animation workspace implementation is required by this HU.

---

# 25. Backward Compatibility

Existing projects created under HU_00001 that do not contain the `canvas` property must be handled safely.

The implementation must not corrupt or invalidate otherwise valid projects solely because they were created before HU_00003.

If an existing project is opened without canvas metadata, the application should use a migration/default strategy consistent with the project's metadata versioning architecture.

The preferred default is:

```json
{
  "width": 1920,
  "height": 1080,
  "keepAspectRatio": false
}
```

However, the migration must be implemented through the existing Project Management layer rather than directly by the renderer.

If the project format version needs to change, the implementation must follow the existing versioning strategy established by HU_00001.

# 28. Architectural Principle

The project's pixel dimensions are **project configuration**, not UI state.

The Create Project form is responsible for collecting and validating this configuration, while the Project Management layer is responsible for persisting it.

The resulting architecture must remain:

```text
Application Home
       ↓
Create Project Form
       ↓
Project Management API
       ↓
Project Repository
       ↓
project.json
```

The persisted configuration will later be consumed by:

```text
Project
   ↓
Scene
   ↓
Animation Workspace
   ↓
Canvas
   ↓
Timeline / Drawing / Layers
```

This ensures that the project's canvas dimensions are established at project creation and remain available as a stable foundation for the future animation system.

# 29. Implementation Constraint

This HU modifies the behavior defined by HU_00002 but does not replace or rewrite the previous HU.

HU_00002 remains a historical record of the original Application Home implementation.

HU_00003 represents the subsequent architectural/product change and must be implemented as an incremental modification on top of the existing system.

Future changes to project dimensions or aspect-ratio behavior must be represented by new HUs rather than rewriting this document.
