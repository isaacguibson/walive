# HU_00001 — Project Management

**Status:** Proposed
**Priority:** Critical
**Type:** Architecture / Core Feature

---

## 1. Overview

The Animation Studio must provide a project-based workflow similar to professional creative applications and development environments such as Unity and Android Studio.

A project represents an independent animation workspace containing its own scenes, assets, drawings, configuration, and other production data.

The application must allow users to:

* Create a new project.
* Open an existing project.
* Open a recently used project.
* Rename a project.
* Close the current project.
* Validate whether a directory is a valid Animation Studio project.
* Persist project metadata.
* Maintain a clear separation between project data and application-level data.

The project format must be designed to support future features such as scenes, timelines, layers, animation frames, asset management, undo/redo, exporting, versioning, and AI integrations.

---

# 2. Goals

The implementation must establish the foundation for the Animation Studio project system.

The following goals are required:

1. Define a standard project directory structure.
2. Define the project metadata format.
3. Create and open projects.
4. Persist project metadata.
5. Maintain a list of recently opened projects.
6. Validate existing projects.
7. Use relative paths for project-owned resources whenever possible.
8. Separate source data from generated/cache data.
9. Make the project format portable between machines.
10. Design the project architecture so it can later be exposed through the internal Animation Studio API and MCP-based AI integrations.

---

# 3. Non-Goals

The following features are explicitly outside the scope of this user story:

* Scene editing.
* Timeline editing.
* Drawing tools.
* Layer management.
* Asset browser UI.
* Image generation.
* AI integrations.
* MCP implementation.
* Cloud synchronization.
* Project collaboration.
* Version control.
* Project packaging.
* Project publishing.
* Exporting animations.

These features may be implemented by future user stories.

---

# 4. Project Concept

An Animation Studio project is a directory on the user's filesystem.

The directory itself represents the project.

A project must contain a root metadata file named:

```text
project.json
```

The application must use this file to identify a valid Animation Studio project.

A project must not depend on the application's installation directory.

A project must be movable to another location without requiring its internal paths to be manually updated, provided that all project-owned resources remain inside the project directory.

---

# 5. Project Directory Structure

A newly created project must use the following structure:

```text
<ProjectName>/
│
├── project.json
│
├── scenes/
│
├── assets/
│   ├── images/
│   ├── audio/
│   ├── video/
│   └── fonts/
│
├── drawings/
│
├── exports/
│
└── .cache/
```

The implementation must allow additional directories to be introduced by future features without breaking existing projects.

### 5.1 Project root

The project root is the directory selected by the user when creating or opening a project.

Example:

```text
Documents/Animation Studio/My First Animation/
```

### 5.2 `project.json`

Contains project-level metadata and configuration.

### 5.3 `scenes/`

Contains scene-specific data.

Scene structure is outside the scope of this user story but the directory must be created when a new project is created.

### 5.4 `assets/`

Contains project-owned external resources.

The following initial categories must exist:

```text
assets/images/
assets/audio/
assets/video/
assets/fonts/
```

Additional asset categories may be added in future user stories.

### 5.5 `drawings/`

Reserved for project drawing data.

The internal drawing format is outside the scope of this user story.

### 5.6 `exports/`

Contains files explicitly exported by the user.

The application must not treat files in this directory as source project data.

### 5.7 `.cache/`

Contains generated data that can safely be deleted and regenerated.

Examples include:

* Thumbnails.
* Preview images.
* Temporary imported data.
* Waveform data.
* Generated previews.
* AI-generated temporary data.
* Other derived resources.

Deleting `.cache/` must never make the project invalid.

---

# 6. Project Metadata

The `project.json` file must contain, at minimum:

```json
{
  "formatVersion": 1,
  "id": "uuid",
  "name": "My Animation",
  "createdAt": "2026-10-06T12:00:00.000Z",
  "updatedAt": "2026-10-06T12:00:00.000Z"
}
```

## 6.1 `formatVersion`

Defines the version of the project file format.

This value must be incremented when breaking changes are introduced to the project format.

The application must be able to detect unsupported project versions.

## 6.2 `id`

A globally unique identifier for the project.

The project ID must remain unchanged when the project directory is renamed or moved.

UUID is the preferred identifier format.

## 6.3 `name`

Human-readable project name.

The project name is independent from the physical directory name.

## 6.4 `createdAt`

UTC timestamp indicating when the project was created.

## 6.5 `updatedAt`

UTC timestamp indicating when project metadata was last modified.

---

# 7. Project Name and Directory Name

The project name and directory name must not be considered the same concept.

For example:

```text
Directory:
My-Animation-Project/

Project name:
My Animation Project
```

The application may sanitize the directory name when creating a project.

The project name must support spaces and common Unicode characters.

The physical directory name must comply with the operating system's filesystem restrictions.

---

# 8. Project Creation

The application must provide a New Project workflow.

The workflow must request at least:

* Project name.
* Project location.

The application must then:

1. Validate the project name.
2. Validate the destination directory.
3. Create the project directory.
4. Create the required project subdirectories.
5. Generate a unique project ID.
6. Generate `project.json`.
7. Register the project as a recently opened project.
8. Open the newly created project.

Example:

```text
User selects:

Name:
My First Animation

Location:
~/Documents/Animation Studio/

Result:

~/Documents/Animation Studio/My First Animation/
```

---

# 9. Existing Directory Handling

When creating a project, the application must not silently overwrite an existing directory.

If the selected directory already exists and contains files, the application must warn the user.

The application may allow creation inside an existing empty directory.

The application must never delete unrelated user files as part of project creation.

---

# 10. Opening an Existing Project

The application must provide an Open Project workflow.

The user may select a project directory.

The application must search for:

```text
project.json
```

at the selected directory root.

If the file exists, the application must validate it before opening the project.

If the file does not exist, the application must report that the selected directory is not a valid Animation Studio project.

The application must not automatically create a `project.json` inside an arbitrary existing directory during the Open Project operation.

---

# 11. Project Validation

The application must validate at least the following:

* `project.json` exists.
* `project.json` contains a supported `formatVersion`.
* `project.json` contains a valid project ID.
* `project.json` contains a valid project name.
* Required project directories exist.

If required directories are missing, the application may offer to repair the project structure.

Repairing a project must never delete existing user data.

---

# 12. Project Repair

The application should support repairing incomplete project structures.

For example, if:

```text
scenes/
```

is missing, the application may recreate it.

If:

```text
assets/images/
```

is missing, the application may recreate it.

The repair process must not modify unrelated files.

Project repair must be explicit and must not silently overwrite existing files.

---

# 13. Recently Opened Projects

Recently opened projects are application-level data and must not be stored inside individual project directories.

The application must maintain a local registry of recently opened projects.

The registry may initially be implemented as JSON or SQLite.

The implementation must abstract the storage mechanism so that it can be replaced in the future.

A recent project entry must contain at least:

```json
{
  "projectId": "uuid",
  "name": "My Animation",
  "path": "/absolute/path/to/project",
  "lastOpenedAt": "2026-10-06T12:00:00.000Z"
}
```

The application must not copy project metadata into the recent-project registry unnecessarily.

The registry is only a reference to the project.

---

# 14. Recent Project Validation

When displaying recent projects, the application must determine whether each project is still accessible.

A project may be marked as unavailable when:

* The directory no longer exists.
* The user moved the project.
* The user renamed the project directory.
* The project was deleted.
* The project format is unsupported.

The application must not automatically delete unavailable entries.

The UI may allow the user to remove unavailable projects from the recent-project list.

---

# 15. Project Portability

Projects must use relative paths when referencing project-owned resources.

For example:

```text
assets/images/character.png
```

is valid.

The following must not be used for project-owned resources:

```text
C:\Users\User\Documents\Animation Studio\My Project\assets\images\character.png
```

or:

```text
/Users/user/Documents/Animation Studio/My Project/assets/images/character.png
```

Absolute paths may be stored separately for external resources when required by a future feature.

---

# 16. External Resources

Future features may allow users to reference resources outside the project directory.

External resources must be treated differently from project-owned resources.

The project format must be capable of distinguishing:

```text
PROJECT_RESOURCE
```

from:

```text
EXTERNAL_RESOURCE
```

This user story does not implement external resource management.

---

# 17. Source Data vs Generated Data

The project architecture must distinguish between source data and generated data.

Source data includes:

* Project metadata.
* Scenes.
* Drawings.
* Imported project assets.
* User-created animation data.

Generated data includes:

* Thumbnails.
* Previews.
* Temporary processing files.
* Cached image data.
* Cached audio waveforms.
* Other derived data.

Generated data must be stored under:

```text
.cache/
```

Generated data must never be required for the project to open successfully.

---

# 18. Application State vs Project State

The implementation must clearly distinguish application-level state from project-level state.

### Application state

Examples:

* Recently opened projects.
* Application preferences.
* Window dimensions.
* Theme.
* Last opened project.
* UI preferences.

### Project state

Examples:

* Project name.
* Scenes.
* Assets.
* Drawings.
* Animation data.
* Project configuration.

Application state must not be stored inside project directories unless explicitly required by a future feature.

Project state must not be stored only in application-level storage.

A project must remain self-contained and portable.

---

# 19. Architecture Requirements

The project system must be implemented through a dedicated Project Management layer.

UI components must not directly manipulate `project.json`.

The architecture should follow:

```text
UI
 ↓
Project Management API
 ↓
Project Repository
 ↓
Filesystem
```

The Project Management layer must expose operations such as:

```text
createProject()
openProject()
closeProject()
validateProject()
repairProject()
renameProject()
getProjectMetadata()
saveProjectMetadata()
```

The exact implementation language and class names may follow the project's existing architecture.

---

# 20. Internal API

The Project Management layer must expose a clean internal API that can later be consumed by:

* The application UI.
* Other application modules.
* Automated tests.
* AI integrations.
* MCP tools.
* Future plugins.

The AI integration must not access project files directly when an equivalent Project Management API operation exists.

For example, an AI agent should eventually be able to request:

```text
getCurrentProject()
```

instead of reading:

```text
project.json
```

directly.

This establishes a stable abstraction between the AI layer and the filesystem.

---

# 21. AI Integration Compatibility

No AI functionality is implemented in this user story.

However, the architecture must not prevent future AI integrations.

Future AI agents must be able to operate through controlled application APIs.

The project system should therefore support future operations such as:

```text
getProject()
getScenes()
getAssets()
getCurrentScene()
getCurrentFrame()
getSelectedLayer()
```

These operations must be implemented by future user stories.

This requirement exists only to ensure that the project architecture does not couple future AI integrations directly to filesystem implementation details.

---

# 22. Error Handling

The application must provide meaningful errors for at least:

* Invalid project directory.
* Missing `project.json`.
* Invalid JSON.
* Unsupported project format version.
* Invalid project ID.
* Invalid project name.
* Permission denied.
* Unable to create directory.
* Unable to write project metadata.
* Project directory unavailable.

Errors must not expose internal stack traces or implementation details to end users.

Technical details may be logged for debugging purposes.

---

# 23. Data Integrity

Project metadata must be written safely.

The implementation should avoid leaving a corrupted `project.json` when the application is interrupted during a write operation.

The preferred approach is an atomic write strategy:

```text
project.json
     ↓
project.json.tmp
     ↓
atomic replacement
```

The exact implementation is platform-dependent.

---

# 24. Testing Requirements

Automated tests must cover at least:

### Project creation

* Creates a valid project.
* Creates the required directory structure.
* Generates a unique project ID.
* Generates valid `project.json`.

### Project opening

* Opens a valid project.
* Rejects an invalid project.
* Rejects malformed JSON.
* Rejects unsupported format versions.

### Project validation

* Detects missing metadata.
* Detects invalid metadata.
* Detects missing directories.

### Project metadata

* Saves metadata correctly.
* Preserves project ID.
* Updates modification timestamps correctly.

### Recent projects

* Registers newly opened projects.
* Updates `lastOpenedAt`.
* Detects unavailable projects.
* Does not duplicate the same project unnecessarily.

### Portability

* Project paths remain valid when the project directory is moved.
* Project-owned resources use relative paths.

### Cache

* Missing `.cache/` does not prevent opening the project.
* Cache data is not required for project validity.

# 27. Architectural Principle

The Animation Studio project format must follow this principle:

> **A project should contain everything required to reproduce the user's work, while generated data, application preferences, and temporary data remain outside the project's source-of-truth model.**

The project filesystem is the persistent source of truth.

The application database is only responsible for application-level state and references to projects.

The Project Management API is the abstraction layer between the application and the project filesystem.

Future AI agents and plugins must interact with the application through stable APIs rather than depending on internal filesystem implementation details.
