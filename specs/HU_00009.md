# HU_00009 — Extensible Brush Engine and Artistic Brush Types

## 1. User Story

**As an** artist using the 2D animation editor,
**I want** to select different brush types and customize their properties from the Tool Options panel,
**So that** I can create a variety of artistic strokes, textures, and visual effects instead of being limited to simple solid lines.

## 2. Objective

Introduce an extensible Brush Engine that supports multiple brush implementations through a common interface.

The feature must preserve the existing drawing workflow, integrate with the current canvas, layers, frames, undo/redo, project persistence, and export systems, and allow new brush types to be added without redesigning the editor.

The brush type selector must be displayed in the existing **Tool Options** panel whenever the Brush tool is selected.

This implementation must not require a specific external rendering library. The initial implementation should use native Canvas 2D capabilities where appropriate, with an architecture that allows specialized rendering backends to be introduced later.

## 3. Scope

### 3.1. In Scope

* Introduce the Brush Engine architecture.
* Add a brush type selector to Tool Options.
* Implement the following brush types:

  1. Basic Brush.
  2. Textured Pencil.
  3. Charcoal Brush.
  4. Chalk Brush.
  5. Particle Brush.
* Provide brush-specific configuration controls.
* Support mouse and compatible pressure-sensitive input devices.
* Integrate with existing pen pressure, pressure-sensitive opacity, and stroke stabilization features.
* Persist stroke appearance and brush configuration as required by the existing project architecture.
* Support undo/redo, frame duplication, save/reopen, and export.
* Keep the architecture independent of any particular rendering library.

### 3.2. Out of Scope

* Bézier curve drawing and editing tools.
* Watercolor simulation or physically accurate pigment blending.
* Smudge, blur, and wet-paint simulation.
* Custom brush creation through an external plugin API.
* Downloading brushes from online libraries.
* AI-generated brushes or textures.
* Third-party renderer integration as a mandatory dependency.
* A complete brush preset marketplace or brush import/export system.

These features may be considered in future user stories.

## 4. User Interface

### 4.1. Brush Type Selector

When the Brush tool is selected, the Tool Options panel must display a **Brush Type** selector above the brush-specific settings.

The selector must support the following options:

| Brush Type      | Description                                                            |
| --------------- | ---------------------------------------------------------------------- |
| Basic Brush     | Produces a continuous, solid stroke.                                   |
| Textured Pencil | Produces a pencil-like stroke with visible grain and irregular edges.  |
| Charcoal Brush  | Produces a rough, grainy stroke with irregular density and soft edges. |
| Chalk Brush     | Produces a dry, powdery stroke with granular texture.                  |
| Particle Brush  | Produces a stroke composed of scattered marks along the pointer path.  |

The selected brush type must determine which additional configuration controls are displayed.

Changing the brush type must not change the selected drawing tool or affect existing strokes.

### 4.2. Common Brush Options

All brush types must support the common options below where applicable:

* **Size:** brush diameter in pixels.
* **Color:** selected stroke color.
* **Opacity:** base stroke opacity, from 0% to 100%.
* **Use Pen Pressure:** use input pressure to control brush size, according to HU_00006.
* **Use Pen Pressure for Opacity:** use input pressure to control opacity, according to HU_00008.
* **Stabilize Stroke:** reduce unwanted pointer movement, according to HU_00007.

The existing implementations of pen pressure and stroke stabilization must be reused instead of introducing duplicate, conflicting controls.

Brush-specific settings must be displayed below the common options.

When a feature is unsupported by the current input device, the editor must preserve its existing fallback behavior.

### 4.3. Brush Settings Persistence

Each brush type must maintain its own configuration.

Switching from one brush type to another and then returning to the previous type must restore its last-used settings for the current editing session.

The selected brush type and its configuration must be persisted according to the existing application and project preference architecture.

The implementation must distinguish between:

* Application-level default brush preferences, if supported by the existing architecture.
* Current editing-session settings.
* Brush properties stored in individual strokes.

Changing the current brush configuration must not retroactively modify previously created strokes.

## 5. Brush Type Specifications

### 5.1. Basic Brush

**Purpose:** Provide a predictable, smooth, continuous brush for general drawing.

**Behavior:**

* Render a continuous stroke following the pointer path.
* Use the configured color, size, and opacity.
* Support pen pressure for size and opacity when enabled.
* Support stroke stabilization.
* Avoid visible gaps when pointer movement is fast.
* Render consistently at different canvas zoom levels.

**Options:**

* Size.
* Color.
* Opacity.
* Use Pen Pressure.
* Use Pen Pressure for Opacity.
* Stabilize Stroke.

The Basic Brush must preserve the behavior of the existing Brush tool as closely as possible.

### 5.2. Textured Pencil

**Purpose:** Simulate a traditional graphite pencil with visible grain and slightly irregular edges.

**Behavior:**

* Render a textured stroke rather than a perfectly uniform solid line.
* Preserve the selected color while introducing controlled texture variation.
* Produce subtle grain and irregular edges.
* Support continuous strokes without visible gaps.
* Maintain a recognizable pencil-like appearance at different brush sizes.
* Support pressure-sensitive size and opacity.
* Support stroke stabilization.

**Brush-specific options:**

* **Texture Intensity:** controls the visibility of the grain.
* **Edge Roughness:** controls irregularity along the stroke edges.

Both options must have sensible defaults and validated ranges.

The visual result must remain consistent when a saved project is reopened.

### 5.3. Charcoal Brush

**Purpose:** Simulate a rough charcoal mark with stronger grain and uneven coverage.

**Behavior:**

* Produce a coarse, irregular texture.
* Allow controlled variation in local density and edge softness.
* Preserve a natural, hand-drawn appearance.
* Avoid excessive random variation that makes the stroke visually disconnected.
* Support pressure-sensitive size and opacity.
* Support stroke stabilization.

**Brush-specific options:**

* **Texture Intensity:** controls the prominence of charcoal grain.
* **Density:** controls the coverage of the stroke.
* **Edge Softness:** controls the softness of the stroke boundaries.

The Charcoal Brush must remain visually distinguishable from the Textured Pencil at comparable sizes.

### 5.4. Chalk Brush

**Purpose:** Simulate dry chalk or pastel marks with a powdery, granular appearance.

**Behavior:**

* Render granular marks with a dry, powder-like texture.
* Allow subtle gaps and variations in coverage.
* Preserve the configured base color.
* Avoid making every stroke look identical.
* Support pressure-sensitive size and opacity.
* Support stroke stabilization.

**Brush-specific options:**

* **Grain Size:** controls the apparent size of individual texture elements.
* **Texture Intensity:** controls the prominence of the granular pattern.
* **Coverage:** controls how densely the texture fills the stroke.

The Chalk Brush must have a visibly different texture and coverage pattern from the Charcoal Brush.

### 5.5. Particle Brush

**Purpose:** Create expressive strokes composed of small marks distributed along the pointer path.

**Behavior:**

* Generate particles along the stroke trajectory.
* Distribute particles with sufficient density to create a continuous-looking stroke when desired.
* Support controlled randomness in particle placement.
* Respect the selected base color and opacity.
* Support pressure-sensitive size and opacity.
* Support stroke stabilization.
* Avoid visible gaps caused by fast pointer movement.

**Brush-specific options:**

* **Particle Size:** controls the size of individual particles.
* **Spacing:** controls the distance between successive particle placements, relative to brush size.
* **Scatter:** controls the distance particles may deviate from the stroke centerline.
* **Size Variation:** controls the variation in particle sizes.
* **Random Seed:** an internal deterministic value used to reproduce the same particle distribution when rendering an existing stroke.

The Random Seed may be generated automatically when a stroke begins. It does not need to be exposed as an editable control in the initial UI.

Particle placement must be based on stroke distance or another deterministic sampling method, rather than depending exclusively on pointer event frequency. This is required to prevent materially different results when the same path is captured at different event rates.

## 6. Brush Engine Architecture

### 6.1. General Requirements

Implement a dedicated Brush Engine between the Brush tool interaction layer and the canvas rendering system.

The architecture must separate:

1. Pointer and pen input collection.
2. Stroke processing and stabilization.
3. Brush-specific rendering.
4. Stroke data persistence.
5. Canvas and layer integration.

The Brush Engine must not depend directly on React components, UI panel state, or a specific external rendering library.

### 6.2. Common Brush Contract

All brush implementations must conform to a common TypeScript interface or equivalent abstraction.

The following is a conceptual contract. It must be adapted to the existing codebase rather than copied blindly if equivalent abstractions already exist.

```ts
interface BrushDefinition<TSettings> {
  id: string;
  name: string;
  defaultSettings: TSettings;

  beginStroke(
    input: StrokeInput,
    settings: TSettings,
    context: BrushRenderContext
  ): void;

  continueStroke(
    input: StrokeInput,
    context: BrushRenderContext
  ): void;

  endStroke(context: BrushRenderContext): void;
}
```

The implementation must ensure that the settings used for an active stroke remain stable for that stroke's lifetime. Changes to Tool Options must apply to subsequent strokes unless the existing application explicitly supports live editing of an in-progress stroke.

The interface may be refined to accommodate typed settings, rendering lifecycle management, cancellation, and replay.

### 6.3. Stroke Input Data

Each stroke must capture enough information to reproduce its visual appearance.

The data model should support:

* Canvas-space X and Y coordinates.
* Input pressure when available.
* Relative or absolute timestamps when needed for the existing stroke-processing pipeline.
* Brush configuration snapshot.
* Deterministic random seed for randomized brushes.
* Any additional per-sample data required by existing pressure or stabilization features.

Mouse input must continue to work without a pressure-sensitive device.

Default mouse pressure values must not be interpreted as genuine pen pressure when the device does not provide pressure information.

### 6.4. Rendering Abstraction

The Brush Engine must use a rendering abstraction that allows different brush implementations to share the same editing workflow.

Native Canvas 2D may be used for the initial implementation.

Future implementations may use another rendering backend, including a GPU-accelerated renderer, without requiring changes to:

* Brush selection UI.
* Frame management.
* Layer management.
* Project file management.
* Undo/redo commands.
* Brush configuration semantics.

The initial implementation must not introduce p5.js, PixiJS, or another rendering library as a mandatory dependency without a separate architectural justification.

## 7. Stroke Data, Persistence, and Rendering

### 7.1. Stroke Reproducibility

The editor must preserve the visual appearance of strokes when:

* Undoing and redoing an operation.
* Duplicating a frame.
* Saving and reopening a project.
* Exporting the animation.
* Rebuilding cached rendering data.

Randomized brushes must use deterministic stroke data or persist an equivalent representation that prevents their appearance from changing unexpectedly during replay.

The application must not depend on the current Tool Options configuration to reconstruct the appearance of an older stroke.

### 7.2. Vector-Like Stroke Data and Rasterization

The implementation should preserve the original stroke samples and brush settings whenever feasible.

If the existing drawing architecture stores layer content as raster images, the Brush Engine must integrate with that architecture without forcing a complete replacement of the layer system.

Intermediate rendering surfaces, cached textures, or other derived resources may be used to improve performance. Such resources must be rebuildable when possible and must not become the sole source of truth unless the existing architecture explicitly defines them as persistent layer data.

The chosen representation must preserve the visual result of textured and particle strokes during export.

### 7.3. Layer and Frame Integration

* A brush stroke must be applied only to the currently selected editable layer.
* Existing layer stacking order must remain unchanged.
* A stroke must belong to the currently selected frame.
* Duplicating a frame must preserve the appearance of its strokes.
* Removing a frame or layer must follow the existing editor behavior.
* Onion Reference imagery must remain visual-only and must not be incorporated into new strokes.

### 7.4. Coordinate System and Zoom

Brush size must be expressed in project canvas pixels.

Canvas zoom and panning must not change the actual stored dimensions or positions of strokes.

Texture size, particle spacing, and scatter must be calculated consistently in canvas coordinates unless an option explicitly defines a screen-space effect.

## 8. Performance and Resource Management

* Brush rendering must remain responsive during normal drawing.
* Brush implementations must avoid allocating unnecessary graphics resources for every pointer event.
* Reusable textures and buffers should be cached where appropriate.
* Particle generation must be bounded by stroke length, spacing, and configured settings.
* Long strokes must not cause unbounded memory growth.
* Temporary rendering resources must be released when no longer needed.
* The application must avoid repeatedly rasterizing the entire project when only a small portion of a layer changes.
* Rendering optimizations must not alter the deterministic appearance of existing strokes.
* If performance becomes insufficient, the architecture must allow selected brush implementations to move to an optimized rendering backend.

Performance tests must include long strokes, rapid pointer movement, high zoom levels, and frame switching.

## 9. Error Handling and Compatibility

* Invalid or missing brush settings must fall back to valid defaults.
* Unknown brush types in an existing project must not cause the project to fail to open.
* If a brush type cannot be reconstructed, the application must provide a clear fallback or recovery path rather than silently corrupting the project.
* The application must remain usable with a mouse when no pressure-sensitive input device is available.
* Existing Basic Brush projects and strokes must remain compatible with the current project format.
* Any required project schema migration must follow the application's existing versioning and migration strategy.
* The editor must not silently discard stroke data during migration.

## 10. Acceptance Criteria

### Brush Selection and Configuration

* [ ] The Brush Type selector appears in Tool Options when the Brush tool is selected.
* [ ] All five specified brush types are available.
* [ ] Selecting a brush type displays the corresponding brush-specific options.
* [ ] Switching between brush types preserves each type's last-used settings for the editing session.
* [ ] Common brush options integrate with existing pressure and stabilization controls.
* [ ] Changing the current brush settings does not alter existing strokes.

### Visual Behavior

* [ ] The Basic Brush produces a smooth, continuous stroke.
* [ ] The Textured Pencil produces visible pencil-like grain.
* [ ] The Charcoal Brush produces a rough, irregular, high-grain stroke.
* [ ] The Chalk Brush produces a dry, powdery, granular stroke.
* [ ] The Particle Brush produces configurable scattered marks along the stroke path.
* [ ] The three textured brushes remain visually distinguishable at comparable sizes.
* [ ] Fast pointer movement does not produce unintended gaps in strokes.
* [ ] Mouse input remains functional without pen pressure support.

### Persistence and Editing

* [ ] Undo and redo preserve the correct appearance of every brush type.
* [ ] Duplicating a frame preserves all brush strokes and their visual properties.
* [ ] Saving and reopening a project preserves stroke appearance.
* [ ] Exported frames preserve the appearance of textured and particle strokes.
* [ ] Randomized strokes render deterministically when reconstructed.
* [ ] Brush strokes are applied to the correct active layer and frame.
* [ ] Canvas zoom and panning do not alter stored stroke geometry or dimensions.

### Architecture and Performance

* [ ] Brush implementations conform to a common engine contract.
* [ ] The Brush Engine does not depend on UI components.
* [ ] A new brush can be introduced without redesigning the frame or layer systems.
* [ ] No external rendering library is required for the initial implementation.
* [ ] Temporary rendering resources are properly managed.
* [ ] Performance remains acceptable during continuous drawing and frame navigation.
* [ ] Existing projects remain compatible or are migrated safely.

## 11. Testing Requirements

The implementation must include automated tests for:

* Brush registration and selection.
* Default settings and settings validation.
* Per-brush configuration persistence.
* Stroke input sampling and deterministic particle placement.
* Pressure-size and pressure-opacity combinations.
* Stabilization compatibility.
* Undo/redo integration.
* Frame duplication.
* Save/reopen consistency.
* Export rendering.
* Unknown brush type recovery.
* Project migration, if applicable.

Visual regression tests or reference-image comparisons should be used where practical to verify that each brush produces a distinct and repeatable appearance.

Manual tests must cover mouse input and a compatible pressure-sensitive pen when available.

## 12. Implementation Notes

* Inspect the existing Brush tool, Tool Options panel, stroke representation, layer renderer, project persistence, and export pipeline before implementing this feature.
* Reuse the existing drawing architecture wherever possible.
* Do not introduce duplicate pressure or stabilization implementations.
* Keep brush-specific settings strongly typed.
* Prefer deterministic rendering over uncontrolled randomness.
* Keep the rendering backend replaceable.
* Do not refactor unrelated editor features as part of this user story.
* Preserve existing user workflows and project compatibility.
* Record any unavoidable architectural changes and migration decisions in the implementation notes.

## 13. Definition of Done

This user story is complete when all five brush types can be selected and configured through Tool Options, strokes are correctly integrated with the existing editor workflow, stroke appearance survives save/reopen and export, the acceptance criteria pass, and the Brush Engine is structured to support future artistic brush types without requiring a redesign of the core editor.
