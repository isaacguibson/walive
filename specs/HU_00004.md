# HU_00004 — Animation Project Editor

**Status:** Proposed
**Priority:** Critical
**Type:** Core Feature / Editor
**Related HUs:** HU_00001, HU_00002, HU_00003

---

# 1. Overview

Implement the first functional version of the **Animation Project Editor**.

After a project is created or opened, the application must display an editor workspace where the user can create and edit animation frames.

The editor must be organized into four primary areas:

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│                                                                              │
│  AREA 1       │                    AREA 4                     │    AREA 2    │
│  Tools        │              Canvas / Workspace              │ Tool Options │
│  Toolbar      │                                              │      +       │
│               │                                              │    Layers    │
│               │                                              │              │
│               │                                              │              │
├───────────────┴──────────────────────────────────────────────┴──────────────┤
│                              AREA 3                                         │
│                    Timeline / Frame Management                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

The four areas are:

1. **Left Tool Panel** — drawing and editing tools.
2. **Right Inspector Panel** — selected tool properties and layer management.
3. **Frame Management Area** — animation frames and frame operations.
4. **Main Workspace** — canvas, playback controls, zoom and fullscreen.

This HU establishes the fundamental editor architecture that future HUs will extend.

---

# 2. Goals

This HU must:

* Replace the existing placeholder Project Editor with a functional editor workspace.
* Display the project canvas using the dimensions stored in project metadata.
* Provide a left-side tool panel.
* Provide a right-side tool/layer panel.
* Provide a frame management/timeline area.
* Provide a central drawing canvas.
* Allow users to create and edit drawings on animation frames.
* Allow multiple layers per frame.
* Allow layer reordering.
* Allow frame creation and manipulation.
* Allow frame copy, cut, paste, duplication, clearing and removal.
* Provide keyboard shortcuts for common frame operations.
* Provide undo functionality.
* Provide canvas zoom.
* Provide animation playback.
* Provide configurable FPS.
* Provide loop playback.
* Provide fullscreen mode.
* Provide tooltips for buttons and icon-only controls.
* Establish a modular architecture suitable for future animation features.

---

# 3. Non-Goals

This HU does not implement:

* Onion skinning.
* Advanced vector drawing.
* Bézier/path editing.
* Advanced selection tools.
* Transform handles.
* Rotation/scale editing of individual drawing objects.
* Audio tracks.
* Video tracks.
* Camera animation.
* Scene management.
* Character rigs.
* Bone systems.
* Advanced keyframe interpolation.
* Motion tweening.
* AI generation.
* MCP integration.
* Plugin marketplace.
* Cloud synchronization.
* Collaboration.
* Export/render pipeline.

These features may be introduced by future HUs.

# 4. Editor Layout

The editor must consist of four persistent areas.

```text
┌────────────┬──────────────────────────────────────────┬─────────────────────┐
│            │                                          │                     │
│            │                                          │   Tool Options      │
│   Tools    │                                          │   ─────────────     │
│            │                Canvas                    │                     │
│            │                                          │                     │
│            │                                          │   Layers            │
│            │                                          │                     │
├────────────┴──────────────────────────────────────────┴─────────────────────┤
│                           Frame Management                                  │
└─────────────────────────────────────────────────────────────────────────────┘
```

The exact visual design is implementation-dependent, but the four functional areas must remain clearly identifiable.

# 5. Area 1 — Tool Panel

The left side of the editor must contain the drawing and editing tools.

The panel must support, at minimum:

* Brush.
* Eraser.
* Fill Tool.
* Eyedropper / Color Picker.
* Selection Tool.

Additional basic tools may be included when useful for the initial editor implementation.

---

## 5.1 Brush Tool

The Brush tool is used to draw directly onto the active layer of the selected frame.

The brush must support at minimum:

* Drawing with mouse input.
* Drawing with pointer input.
* Brush size.
* Brush color.
* Continuous strokes.
* Undo support.

The brush must draw only on the currently active layer.

---

## 5.2 Eraser Tool

The Eraser removes pixels from the active layer.

The eraser must support:

* Mouse/pointer drawing.
* Eraser size.
* Continuous strokes.
* Undo support.

The eraser must affect only the active layer.

---

## 5.3 Fill Tool

The Fill Tool must allow the user to fill a contiguous area with the currently selected color.

The implementation may use a standard flood-fill algorithm.

The fill operation must affect only the active layer unless a future HU explicitly introduces multi-layer fill behavior.

---

## 5.4 Eyedropper / Color Picker

The color picker must allow the user to select a color from the canvas.

When the user clicks a pixel, the corresponding color becomes the active drawing color.

The selected color must become available to the Brush and Fill Tool.

---

## 5.5 Selection Tool

The initial Selection Tool may provide basic rectangular selection behavior.

At minimum, it should allow the user to identify/select an area of the canvas.

Advanced transformation functionality is outside the scope of this HU.

---

# 6. Tool Selection

Only one primary tool should be active at a time.

The selected tool must have a clear visual state.

Example:

```text
Brush       ← selected
Eraser
Fill
Eyedropper
Selection
```

Changing the selected tool must immediately update the Tool Options area.

---

# 7. Tooltips

Every interactive button must provide a tooltip describing its action.

This is particularly important for icon-only buttons.

Examples:

```text
Brush       → "Brush"
Eraser      → "Eraser"
Fill        → "Fill Tool"
Undo        → "Undo"
Copy        → "Copy Frame"
Cut         → "Cut Frame"
Duplicate   → "Duplicate Frame"
Clear       → "Clear Frame"
Remove      → "Remove Frame"
Play        → "Play Animation"
Fullscreen  → "Fullscreen"
```

Tooltips must appear when the pointer remains over the control for the platform/UI framework's standard tooltip delay.

The tooltip must not require a click.

# 8. Area 2 — Right Inspector and Layers Panel

The right side of the editor must be divided vertically into two sections.

```text
┌─────────────────────────┐
│                         │
│     Tool Options        │
│                         │
├─────────────────────────┤
│                         │
│                         │
│        Layers           │
│                         │
│                         │
└─────────────────────────┘
```

The upper section contains properties for the selected tool.

The lower section manages layers.

---

# 9. Tool Options

The Tool Options section must dynamically display properties associated with the selected tool.

For example, when Brush is selected:

```text
Brush

Size
[ 12 ] px

Color
[ ███████████ ]

Opacity
[ 100 ] %
```

The exact properties may evolve in future HUs.

At minimum, Brush must provide:

* Size in pixels.
* Color.

The size value must be a positive number appropriate for the implementation.

---

# 10. Brush Size

The Brush size must be expressed in pixels.

Example:

```text
Size
[ 12 ] px
```

The implementation must prevent invalid values.

The default brush size should be a reasonable value suitable for initial drawing.

The exact default value may be chosen by the implementation as long as it is clearly documented in code and can be changed later.

---

# 11. Color

The editor must provide a color control for drawing tools.

The active color must be shared by tools that use a color, including:

* Brush.
* Fill Tool.

The color picker may use the browser/native color picker or an equivalent UI component.

---

# 12. Layers

The bottom section of the right panel manages the layers of the currently selected frame.

Each frame must be able to contain multiple layers.

Example:

```text
Layers

┌──────────────────────────┐
│ 👁  Character            │
│ 👁  Details              │
│ 👁  Sketch               │
│ 👁  Background           │
└──────────────────────────┘

[ + Add Layer ]
```

The layer order determines visual stacking.

The first/top layer in the layer list is rendered above the layers below it.

For example:

```text
Character
Details
Sketch
Background
```

means:

```text
Character
   ↓
Details
   ↓
Sketch
   ↓
Background
```

---

# 13. Layer Operations

The layer system must support at minimum:

* Add layer.
* Select layer.
* Rename layer.
* Remove layer.
* Reorder layers.

The user must be able to change the active layer.

Drawing operations must always target the currently active layer.

---

# 14. Layer Ordering

The user must be able to reorder layers.

The implementation may use:

* Drag and drop.
* Up/down controls.
* Another intuitive interaction.

The chosen implementation must make the visual stacking order clear.

Changing the layer order must immediately update the canvas rendering.

---

# 15. Layer Defaults

When a new frame is created, it must contain at least one editable layer.

A reasonable default is:

```text
Layer 1
```

The exact default naming strategy may be refined in a future HU.

A frame must not be left without an active editable layer unless the user explicitly removes all layers and the implementation supports that state.

---

# 16. Frame-Specific Layers

Layers belong to individual frames in this initial architecture.

Therefore:

```text
Frame 1
 ├── Background
 ├── Sketch
 └── Character

Frame 2
 ├── Background
 ├── Sketch
 └── Character
```

does not imply that the layers are automatically shared between frames.

Future HUs may introduce persistent/shared layers, but this HU treats layers as frame content.

---

# 17. Area 3 — Frame Management

The bottom portion of the editor is the frame management area.

It represents the animation sequence.

Example:

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ [+ ▼] [Copy] [Cut] [Duplicate] [Clear] [Remove]                         │
├──────────────────────────────────────────────────────────────────────────┤
│  Frame 1   Frame 2   Frame 3   Frame 4   Frame 5                        │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐                      │
│  │      │  │      │  │      │  │      │  │      │                      │
│  │      │  │      │  │      │  │      │  │      │                      │
│  └──────┘  └──────┘  └──────┘  └──────┘  └──────┘                      │
└──────────────────────────────────────────────────────────────────────────┘
```

The user must be able to select a frame for editing.

---

# 18. Frame Selection

Clicking a frame selects it.

The selected frame must have a clear visual state.

Selecting a frame must:

1. Change the active frame.
2. Load its layers.
3. Load its drawing content into the canvas.
4. Update the layer panel.
5. Update the tool/editor state as necessary.

Only one frame can be selected at a time.

---

# 19. Add Frame Button

The frame toolbar must contain a primary button with a `+` icon.

Example:

```text
[ + ▼ ]
```

The main `+` action adds a new frame.

The new frame should be inserted after the currently selected frame.

If no frame is selected, the new frame should be appended to the end of the sequence.

---

# 20. Add Multiple Frames

The Add Frame button must contain a secondary dropdown area represented by a downward arrow.

Example:

```text
[ + ▼ ]
```

Clicking the arrow must open a floating menu/popover.

The popover must contain an integer input.

Example:

```text
┌─────────────────────────┐
│ Add Frames               │
│                         │
│ Quantity                │
│ [ 5 ]                   │
│                         │
│ [ Add ]                 │
└─────────────────────────┘
```

The quantity:

* Must be an integer.
* Must be greater than `0`.
* Is required.

Clicking Add must create the requested number of frames.

The frames must be inserted immediately after the currently selected frame.

If no frame is selected, they must be appended to the end.

---

# 21. Frame Action Toolbar

Next to the Add Frame button, the frame toolbar must contain icon-only buttons for:

1. Copy.
2. Cut.
3. Duplicate.
4. Clear.
5. Remove.

Example:

```text
[ + ▼ ] [ Copy ] [ Cut ] [ Duplicate ] [ Clear ] [ Remove ]
```

The actual UI should use icons rather than text labels.

Each button must have a tooltip.

---

# 22. Copy Frame

Copy must copy the complete content of the selected frame.

This includes:

* All layers.
* Layer order.
* Layer names.
* Layer visibility/state where applicable.
* Drawing data.

Copy must not modify the source frame.

The copied frame data should be stored in an application/editor clipboard abstraction rather than relying exclusively on the operating system clipboard.

---

# 23. Cut Frame

Cut must:

1. Copy the selected frame's complete content.
2. Remove the selected frame from the animation.
3. Select an appropriate neighboring frame.

The copied content must remain available for Paste.

---

# 24. Paste Frame

Paste must replace the content of the currently selected frame with the copied/cut frame content.

Paste must not create a new frame.

Example:

```text
Frame 1
Frame 2 ← selected
Frame 3

Ctrl + V

Frame 2 receives the copied frame content.
```

The destination frame remains in the same position in the timeline.

---

# 25. Duplicate Frame

Duplicate must create a new frame containing an exact copy of the selected frame.

The duplicated frame must be inserted immediately after the selected frame.

Example:

```text
Before:

Frame 1
Frame 2 ← selected
Frame 3

After:

Frame 1
Frame 2
Frame 2 Copy ← selected
Frame 3
```

The duplicated frame must have independent drawing data.

Editing the duplicate must not modify the original.

---

# 26. Clear Frame

Clear removes the drawing content from the selected frame while keeping the frame itself.

The frame remains in the animation sequence.

Example:

```text
Before:

Frame 1
Frame 2 ← selected
Frame 3

After:

Frame 1
Frame 2 ← empty
Frame 3
```

The frame's layer structure may remain intact.

The clear operation must be undoable.

---

# 27. Remove Frame

Remove deletes the selected frame from the animation.

The frame and its associated layer/drawing data are removed from the sequence.

After removal, another frame should be selected automatically when available.

Preferred behavior:

1. Select the next frame if one exists.
2. Otherwise select the previous frame.
3. If no frames remain, create a new empty frame.

The application must not allow the editor to remain without a valid editable frame.

---

# 28. Frame Context Menu

Right-clicking a frame must open a floating context menu.

The menu must contain:

```text
Copy
Cut
Duplicate
Clear
Remove
```

The actions must behave exactly like the corresponding toolbar buttons.

The context menu must be associated with the frame that was right-clicked.

If the right-clicked frame was not already selected, the application should select that frame before displaying its actions.

---

# 29. Frame Clipboard

The editor must maintain an internal frame clipboard.

Conceptually:

```ts
interface FrameClipboard {
  operation: "copy" | "cut";
  frame: FrameData;
}
```

The clipboard must be independent of the operating system text clipboard.

This is necessary because frames contain structured drawing/layer data rather than text.

The clipboard should exist at the application/editor level.

---

# 31. Undo Architecture

Undo must be implemented through an editor-level command/history abstraction rather than individually handling `Ctrl + Z` in every component.

Conceptually:

```text
User Action
    ↓
Editor Command
    ↓
Execute
    ↓
History Stack
```

Undo:

```text
Ctrl + Z
    ↓
Undo Manager
    ↓
Reverse last command
```

This architecture should allow future commands to participate in the same history system.

# 32. Canvas

Area 4 contains the primary canvas/workspace.

The canvas must use the dimensions defined by HU_00003.

For example, if:

```text
canvas.width = 1920
canvas.height = 1080
```

the logical drawing surface must be:

```text
1920 × 1080 pixels
```

The canvas may be visually scaled to fit the available workspace.

The visual scaling must not modify the project's logical pixel dimensions.

---

# 33. Canvas Interaction

The user must be able to:

* Draw.
* Erase.
* Fill.
* Pick colors.
* Use the selected tool.
* See the active frame's layers.
* See changes immediately.

Drawing must respect the current canvas zoom.

Input coordinates must be correctly transformed from screen coordinates to logical canvas coordinates.

---

# 34. Canvas Zoom

The editor must provide a manual zoom control.

Example:

```text
Zoom
[ 100 ] %
```

The user must be able to type a numeric zoom value.

The zoom value must be greater than `0`.

The exact maximum zoom may be constrained by the implementation, but the value must never be zero or negative.

---

# 35. Mouse Wheel Zoom

The user must be able to zoom using:

```text
Ctrl + Mouse Wheel
```

Scrolling upward should zoom in.

Scrolling downward should zoom out.

The canvas must not scroll/zoom the entire application when the pointer is over the canvas and Ctrl is pressed.

The zoom operation should feel centered around the pointer position when practical.

---

# 36. Playback Controls

A small playback control bar must be displayed above the canvas.

Example:

```text
┌─────────────────────────────────────────────────────────────┐
│   ▶    [ Loop ]    FPS [ 24 ▼ ]       Zoom [ 100 ]%  ⛶   │
└─────────────────────────────────────────────────────────────┘
```

The exact arrangement may vary.

---

# 37. Play Button

The Play button must:

* Be rounded.
* Display an icon only.
* Have a tooltip.
* Start animation playback.

Example:

```text
▶
```

When playback is active, the button should change to an appropriate stop/pause state.

For example:

```text
▶ → ⏸
```

The exact icon may depend on the chosen icon library.

---

# 38. Playback Sequence

When playback starts, frames must be displayed sequentially.

Example:

```text
Frame 1
   ↓
Frame 2
   ↓
Frame 3
   ↓
Frame 4
   ↓
Frame 1
```

The playback speed must be determined by the configured FPS.

---

# 39. Loop Playback

The playback controls must contain a toggle for loop playback.

Example:

```text
[ Loop ]
```

When enabled:

```text
Last Frame → First Frame
```

When disabled:

```text
Last Frame → Stop
```

The toggle must have a tooltip explaining its function.

---

# 40. FPS Control

The user must be able to configure playback speed.

The control must combine:

* A predefined options list.
* A manually editable numeric value.

Example:

```text
FPS
[ 24 ▼ ]
```

Suggested predefined values:

```text
24
30
60
120
```

The user must also be able to manually enter any positive integer.

Examples:

```text
1
12
24
30
48
60
120
240
```

The default FPS is:

```text
24
```

The value must be validated as a positive integer.

---

# 41. FPS Validation

Invalid FPS values include:

```text
0
-1
1.5
abc
empty
```

The application must prevent playback from using invalid FPS values.

---

# 42. Fullscreen Mode

The editor must provide a fullscreen control.

The control should be icon-only and have a tooltip:

```text
Fullscreen
```

When activated, the editor should enter fullscreen mode.

Fullscreen mode must hide unnecessary application chrome while preserving the editor workspace.

Pressing:

```text
Esc
```

must exit fullscreen mode.

# 43. Project Editor State

The editor must maintain the following state at minimum:

```ts
interface EditorState {
  activeFrameId: string | null;
  activeLayerId: string | null;
  selectedTool: ToolType;
  zoom: number;
  fps: number;
  loopPlayback: boolean;
  isPlaying: boolean;
}
```

The exact architecture may differ, but these concepts must exist.

---

# 44. Frame Model

The editor requires a structured frame model.

Conceptually:

```ts
interface Frame {
  id: string;
  layers: Layer[];
}
```

The frame must have a stable identifier.

Frames should not depend exclusively on their array index because indexes change when frames are inserted or removed.

---

# 45. Layer Model

Conceptually:

```ts
interface Layer {
  id: string;
  name: string;
  visible: boolean;
  drawing: DrawingData;
}
```

The exact drawing representation is implementation-dependent.

The important architectural requirement is that drawing data belongs to a layer, and layers belong to a frame.

---

# 46. Drawing Data

Drawing data must be represented in a way that can be persisted and reconstructed.

The implementation may initially use raster-based drawing data.

The exact binary/storage format may be decided during implementation.

However, the architecture must avoid coupling the renderer directly to raw filesystem operations.

The Project Engine/Repository must remain responsible for persistence.

---

# 47. Persistence

Editor changes must eventually be persisted as project data.

The editor must not treat the canvas as temporary-only UI state.

The project must retain:

* Frames.
* Frame order.
* Layers.
* Layer order.
* Layer names.
* Drawing data.
* Relevant editor configuration.

The exact file organization for scene/frame/drawing data may be refined by a future dedicated persistence HU.

This HU should establish the necessary domain abstractions without unnecessarily locking the project into one storage format.

---

# 48. Project Canvas Integration

The editor must obtain the canvas dimensions from the project metadata defined in HU_00003.

Example:

```json
{
  "canvas": {
    "width": 1920,
    "height": 1080,
    "keepAspectRatio": true,
    "aspectRatio": {
      "width": 16,
      "height": 9
    }
  }
}
```

The editor must use:

```text
canvas.width
canvas.height
```

as the logical canvas dimensions.

The `keepAspectRatio` setting is project configuration and does not mean that the editor must prevent all future canvas operations. It represents the project configuration established during creation.

---

# 49. Rendering Architecture

The editor should separate:

```text
Editor UI
     ↓
Editor State
     ↓
Animation Engine
     ↓
Canvas Renderer
```

The canvas renderer should not contain frame-management business logic.

Similarly:

* Timeline should not own drawing algorithms.
* Tool buttons should not directly manipulate filesystem data.
* Layer UI should not directly manage persistence.
* Playback should not directly manipulate the canvas DOM without going through editor state.

# 51. Animation Engine

The animation functionality should be represented by an internal domain/service layer.

Conceptually:

```ts
interface AnimationEngine {
  getFrames(): Frame[];
  getActiveFrame(): Frame | null;
  addFrame(): Frame;
  addFrames(count: number): Frame[];
  duplicateFrame(frameId: string): Frame;
  removeFrame(frameId: string): void;
  clearFrame(frameId: string): void;
  copyFrame(frameId: string): void;
  cutFrame(frameId: string): void;
  pasteFrame(frameId: string): void;
}
```

The exact API may differ, but the responsibilities should remain centralized.

---

# 52. Tool Architecture

Drawing tools should use a common abstraction.

Conceptually:

```ts
interface EditorTool {
  id: string;
  name: string;
  activate(): void;
  deactivate(): void;
  pointerDown(event: PointerEvent): void;
  pointerMove(event: PointerEvent): void;
  pointerUp(event: PointerEvent): void;
}
```

Tools should not directly manipulate unrelated editor state.

The Brush, Eraser, Fill and other tools should operate through drawing/canvas services.

This architecture will make it possible to add future tools without rewriting the editor.

---

# 53. Playback Architecture

Playback should be independent of the visual timeline component.

Conceptually:

```text
Timeline
    ↓
Animation State
    ↓
Playback Controller
    ↓
Current Frame
    ↓
Canvas Renderer
```

The playback controller should use the configured FPS.

It should not create a separate copy of the animation data.

---

# 54. Keyboard Shortcut Architecture

Keyboard shortcuts should be centralized.

Conceptually:

```ts
interface Shortcut {
  key: string;
  modifiers: string[];
  action: string;
}
```

The application should map:

```text
Ctrl + C → copy frame
Ctrl + V → paste frame
Ctrl + X → cut frame
Ctrl + D → duplicate frame
Ctrl + Z → undo
```

The implementation must account for text input controls.

For example, `Ctrl + C` while editing a text field should not unexpectedly copy a frame if the user is actually selecting text.

Editor shortcuts should be active when the editor has focus and should respect native text-editing behavior where appropriate.

---

# 55. Mouse and Pointer Input

The editor should use pointer events where practical so that future support for:

* Mouse.
* Pen/tablet.
* Stylus.
* Touch.

can be introduced without redesigning the tool system.

Drawing tools must correctly distinguish:

```text
pointerDown
pointerMove
pointerUp
```

and must not generate unintended strokes when the pointer leaves the canvas.

---

# 56. Responsive Layout

The editor should support different window sizes.

The four areas must remain usable when the application window changes size.

The central canvas area should receive the majority of available space.

The left and right panels should have reasonable minimum widths.

The frame management area should remain accessible without overlapping the canvas.

---

# 57. Panel Resizing

If practical within the selected UI architecture, the left and right panels should support resizing.

However, panel resizing is not mandatory for completion of this HU.

The architecture should not prevent adding resizable panels in a future HU.

---

# 58. Empty Project State

If the project contains no frames when the editor is opened, the application must create an initial frame automatically.

The initial state should be:

```text
Frame 1
 └── Layer 1
```

with an empty canvas.

This ensures that the user can immediately begin drawing.

---

# 59. Active Frame and Layer

At all times during normal editing:

```text
Active Project
    ↓
Active Frame
    ↓
Active Layer
```

must be clearly defined.

Drawing operations without an active frame or active editable layer must not silently fail.

The editor should automatically create the required initial frame/layer when necessary.

---

# 60. Error Handling

The editor must handle failures gracefully.

Examples:

* Unable to load project data.
* Unable to save drawing data.
* Invalid frame data.
* Invalid layer data.
* Invalid FPS.
* Invalid zoom.
* Canvas initialization failure.

The application must not silently discard user changes.

Errors should be surfaced through the existing application error-handling mechanism.

---

# 61. Performance Considerations

The architecture must avoid unnecessary complete-canvas redraws when possible.

The implementation should be designed so that future projects can contain:

* Many frames.
* Multiple layers.
* Large canvas dimensions.

The initial implementation does not need advanced GPU optimization, but it must avoid obviously inefficient approaches such as repeatedly serializing the entire project on every pointer movement.

Drawing interactions should remain responsive.

---

# 62. Persistence Strategy

The editor should not write project files on every individual pointer event.

Instead, the editor should maintain in-memory state and persist meaningful state changes through an appropriate persistence mechanism.

For example:

```text
Pointer events
    ↓
Canvas state
    ↓
Drawing command/history
    ↓
Dirty state
    ↓
Persistence
```

The exact autosave strategy may be introduced by a future HU.

---

# 63. Dirty State

The editor should be able to determine whether the project contains unsaved changes.

Conceptually:

```ts
interface EditorDocumentState {
  isDirty: boolean;
}
```

Any modification such as:

* Drawing.
* Erasing.
* Filling.
* Layer changes.
* Frame changes.

should mark the project as dirty.

The visual indication of unsaved changes may be implemented in this HU if practical.

---

# 64. Closing the Project

When the user closes the project from the editor, the application must use the existing Project Management flow established by HU_00001/HU_00002.

The editor must not directly delete or manipulate project directories.

If unsaved changes exist, the application should eventually ask the user whether to save/discard/cancel.

If a complete save-confirmation workflow is not implemented in this HU, the architecture must expose the dirty state so that it can be implemented safely in a future HU.

---

# 65. Tool and Frame Interaction

Tools always operate on:

```text
Current Frame
    +
Current Layer
```

For example:

```text
Brush
  ↓
Active Frame
  ↓
Active Layer
  ↓
Drawing
```

Changing the selected frame automatically changes the drawing context.

Changing the active layer changes the target of drawing operations.

---

# 66. Right Panel Synchronization

When the active frame changes:

* Its layers must be loaded into the layer panel.
* Its active layer should be selected.
* The canvas must display the frame.
* Tool options must remain available.

When the active layer changes:

* The canvas must immediately update the active drawing target.

When a layer is reordered:

* The canvas rendering order must update.

---

# 67. Timeline Synchronization

The timeline/frame area and canvas must represent the same animation state.

Selecting a frame in the timeline must update the canvas.

Changing the current frame during playback must update the canvas.

Creating/removing/duplicating frames must update the timeline and animation engine consistently.

There must be a single source of truth for the animation state.

---

* Accessible labels.
* Tooltips where applicable.
* Keyboard focus where practical.
* Clear selected/active states.
* Sufficient visual distinction between selected and inactive controls.

Icon-only buttons must always have an accessible name in addition to their visual icon.

# 70. Project Data Ownership

The editor must follow the project/application separation established by HU_00001.

### Project State

Includes:

* Canvas dimensions.
* Frames.
* Layers.
* Drawing data.
* Animation data.

### Application State

Includes:

* Window state.
* Recent projects.
* Application preferences.

Editor-specific transient state such as:

* Current tool.
* Current zoom.
* Playback state.

may remain application/editor state unless explicitly designated as project configuration.

# 76. Architectural Principle

The Animation Project Editor is a composition of specialized systems rather than one monolithic component.

The intended architecture is:

```text
                    Animation Project Editor
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
       Tool System       Frame System        Layer System
          │                   │                   │
          └───────────────────┼───────────────────┘
                              │
                        Animation State
                              │
                 ┌────────────┴────────────┐
                 │                         │
           Canvas Renderer            Playback Engine
                 │                         │
                 └────────────┬────────────┘
                              │
                       Project Persistence
```

The UI is responsible for interaction and presentation.

The editor/domain layer is responsible for animation state and operations.

The project layer is responsible for persistence.

The canvas renderer is responsible for displaying drawing data.

The playback engine is responsible for sequencing frames.

This separation is essential because the same underlying capabilities will later need to be consumed by automated workflows, plugins, AI agents and MCP tools.
